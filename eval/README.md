# eval — перевірка якості

Власник: Аня.

Вимірювальний прилад: чим міряємо, що пайплайн витягнув правильно. Самі
документи й еталонні відповіді лежать не тут, а в `data/eval/` — тут лише
інструмент.

## Що тут лежить

| Файл | Що це |
|---|---|
| `evaluate.py` | прогін набору + звіт по полях: `python -m eval.evaluate --input <папка>` |
| `field-mapping.yaml` | як поле виводу зіставляється з ключем еталона і яким порівнянням |
| `tests/` | регресійні тести пайплайна й тести на сам прилад |
| `check_all.py` | **п'ять цифр одною командою**: `python -m eval.check_all` |
| `baseline.json` | очікувані цифри, з якими порівнює `check_all` |

## «Не ламає» — це діф п'яти цифр, не відчуття

```
python -m eval.check_all              # порівняти з baseline.json
python -m eval.check_all --only tests,leave    # підмножина під час роботи
python -m eval.check_all --save       # оновити базову лінію (свідомо!)
```

Міряє: тести, `leave` docx, `deployment` docx, нормативний корпус, валідатор
демо-набору. Код виходу `1`, якщо хоч одна цифра стала гіршою — отже скрипт
можна ставити перед комітом.

Правило Ані від 23.08.2026: після кожної правки перевіряти, чи не зламалось
щось в іншому місці. Доти ці заміри збирались руками, по одному, з різними
прапорцями — тобто перевірка була дорога, а дорогу перевірку пропускають.

`baseline.json` лежить **у репо**, а не в `data/eval/reports/` (той каталог
`.gitignore` не пускає): очікувані цифри мусять бути в історії коду, щоб зміна
цифри була видна в діффі, а оновлення базової лінії — окремий коміт із
причиною, а не тихий перезапис на чиємусь диску.

**Зростання не є погіршенням.** Скрипт свідомо не вимагає рівності: нова
перевірка збільшує знаменник, і це нормально. Провалом вважається лише падіння
(менше пройдених тестів, менше правильних полів, менше нормативних) і поява
нових проблем (провалені тести, проблеми мапінгу, необґрунтовані відмови).

## Код виходу (для CI)

`0` — вимірювання пройшло; `2` — у папці немає файлів, чиї назви містять ID
еталона; `1` — **провал вимірювання**: проблеми мапінгу, поле на нулі,
провалений інваріант або прогін без жодної польової перевірки. Плюс
`--fail-under N` — провал, якщо загальний відсоток нижчий за N.

Доти `main` беззастережно повертав `0` (A-15 + C-11, рев'ю 22.08.2026), тобто
прилад казав «успіх» і на прогоні з половиною полів на нулі: у CI його
поставити було неможливо.

## Як запускати тести

```
pip install -r requirements.txt -r requirements-dev.txt
python -m pytest eval/tests -q
```

З кореня репозиторію, не з `eval/`: тести самі додають корінь у `sys.path`, але
шляхи до зразків і еталона рахують від нього.

`requirements-dev.txt` існує тому, що 14.08.2026 виявилось: `pytest` не
встановлений і тести не запускались **узагалі** — тобто всі правки до того дня
йшли без сітки безпеки. Деталі й числа — `docs/known-weak-spots.md`, розд. 6.

| Файл тестів | Що фіксує | Чи потрібна модель |
|---|---|---|
| `tests/test_regressions.py` | регресії пайплайна: нормалізація, екстракція, ідентифікація | ні |
| `tests/test_evaluator.py` | регресії самого ПРИЛАДУ (помилка приладу дорожча) | ні |
| `tests/test_ocr_selfheal.py` | перезапуск сервера розпізнавання: коли треба й коли навмисно НЕ треба | ні, surya підставна |
| `tests/test_review_2026_08_22.py` | виправлення за рев'ю 22.08.2026: обидва напрямки інваріанта статусу, склад знаменника, коди виходу, holdout, freeform, чутливість мірки редакції бланка | ні |

Жоден тест не вантажить surya, ваги чи LLM — це вимога, не зручність: умова
перезапуску OCR мусить перевірятись на кожному прогоні, а не раз на пів дня
разом із 3,2-хвилинним OCR-прогоном.

Дані, на яких він працює: `data/eval/samples/<домен>/` — зразки документів,
`data/eval/synthetic-2026-05/per-document/<ID>.json` — правильні відповіді.
Звіти прогонів пишуться в `data/eval/reports/` і в git не їдуть.

Дві РОЗКЛАДКИ еталона читаються однаково: `per-document/<ID>.json` (ключ `id`
всередині) і `<назва>.expected.json` (holdout — ключа `id` немає, ID береться з
назви файлу). Друга додана 22.08.2026: доти holdout-еталони не міряв жоден
прогін (A-06). Holdout без моделі не міряє ЖОДНОГО значення — прилад тепер
називає такий прогін провалом, а не 100%.

## Що прилад міряє, а що ні

Знаменник складається з трьох різних речей, і вони друкуються окремо
(A-09, 22.08.2026): **польові** перевірки (витягнуте значення проти еталона),
**інваріанти** (статус, зв'язок скасування, суперечність діапазону) і
**порожні на бланку** (очікується null). Частина перевірок позначена
`trivial` — вони проходять і на пайплайні, який цього не вміє взагалі
(документ без пари → «зв'язків немає»), і без цієї позначки «224/224» звучало
сильніше, ніж є.

Окремим блоком друкуються **відповіді еталона, яких прилад не питає** —
дзеркало розділу `unmeasured:` у мапінгу. На корпусі leave таких 8 ключів.

## Прилад мусить падати в ОБА боки

Найдорожча знахідка рев'ю 22.08.2026 (A-01): пайплайн, у якого КОЖЕН запис
переведено в `needs_review` з `facts[*].confirmed=False` — тобто який
перестав підтверджувати будь-що, — отримував ті самі 224/224 = 100.0%.
`чернетка_не_факт` карала лише брехню в бік довіри; масова відмова її
проходила.

Тому додано зворотний бік: `відмова_обґрунтована`. **Запис мусить сам
пояснювати свій статус** — відмова зараховується лише коли в записі є
об'єктивна підстава для сумніву (`unknown_critical_fields`,
`unresolved_values`, `consistency_problems`, `date_range_error`, `warnings`,
`template=None`, `facts=[]`, або провалена польова перевірка того ж запису).
Той самий мутований прогін тепер дає 225/240 = 93.8%.

Правило на майбутнє: **кожна нова перевірка мусить мати відповідь на питання
«який зіпсований пайплайн її провалить?»**. Якщо такого пайплайна немає,
перевірка декоративна.

## Прилад окремо від пайплайна — навмисно

`eval/` не всередині `pipeline/` тому, що прилад мусить лишатися незалежним від
того, що міряє. Приклад: в `evaluate.py` свідомо тримається ВЛАСНА копія таблиці
гомогліфів, а не імпорт з `pipeline.normalization`. Якби прилад брав її з
пайплайна, обидва помилялися б однаково, і порівняння сходилося б за побудовою.
Цей «дубляж» прибирати не можна.

## Еталон не редагується, щоб цифри зійшлися

`data/eval/synthetic-2026-05/` — це відповіді. Коли результат не збігається,
змінюють правило порівняння або код, але **не** відповіді.

Живий приклад: 13.08.2026 виявилось, що прилад карав пайплайн за чесний `null` і
зарахував би вигадане значення — еталон на документах із порожніми полями
очікував значення зі сценарію, а не з паперу. Виправили правило порівняння
(читаємо блок «надруковано» самого еталона), відповідей не чіпали — і те саме
виправлення одразу виявило справжній баг у пайплайні, який м'яке порівняння
приховувало.

Другий такий випадок, 14.08.2026: те саме правило («очікуємо надруковане»)
закрило значення на документі з переставленими датами, але не закрило
**позначку**. Прилад міряв лише два числа, тому пайплайн, який віддав
надруковані дати й промовчав про суперечність, отримував ті самі 10/10, що
пайплайн, який її позначив. Додано перевірку `суперечність_діапазону`
(`range_checks` у `field-mapping.yaml`): правильна відповідь на такому
документі — надруковане **плюс** `date_range_error` **плюс** `confirmed: false`.
Умова читається з блоку «надруковано», а не з поля «вада» еталона, — інакше
перевірка спрацьовувала б лише на навмисних дефектах набору й не спрацювала б
на реальному бланку з опискою.

## Синтетика — не анонімізовані реальні документи

Це різні речі. Синтетичний зразок складається з вигаданих даних за структурою
реального документа. Реальний документ із замазаним прізвищем — усе ще реальний
документ: у ньому лишаються дати, номери частин, формулювання.

Кладемо тільки перше.
