# БД milidoc — огляд для команди чат-бота/UI

Для підключення: [`schema_dump.sql`](schema_dump.sql) (повна DDL, `pg_dump
--schema-only`) + [`seed_data.sql`](seed_data.sql) (довідникові таблиці з
реальними значеннями). Обидва — актуальний стан на 2026-08-13.

## 1. Три компоненти, три власники

```
Документ (скан/docx) → [Аня: пайплайн]  → structured YAML/MD
                              ↓
                        [Ми: завантажувач] → PostgreSQL (ця БД)
                              ↓
                        [Ви: чат-бот/UI]  → відповідь користувачу
```

Аня і ми з'єднані через файловий формат (її `.md`-вивід), не через мережевий
виклик. Ви з нами з'єднані напряму через цю БД — SQL, не файл.

## 2. Головне архітектурне правило — прочитати перед усім іншим

**LLM НІКОЛИ не пише SQL сам.** Модель обирає готовий SQL-шаблон і
підставляє в нього параметри з тексту питання користувача — сам шаблон
написаний і перевірений людиною заздалегідь. Це не наше самовільне
рішення — це прямо зафіксовано в ТЗ проєкту
(`project-expectations.md`, п.6): "LLM обирає готовий шаблон запиту... і
підставляє параметри; шаблони читають лише підтверджені факти — сам текст
запиту фіксований заздалегідь, LLM лише вибирає його і заповнює
параметри."

**Наслідок:** router/маршрутизатор чат-бота — це щось типа "яке з N
заздалегідь написаних питань це нагадує" + "які параметри витягнути з
тексту користувача", а не "згенеруй SQL". Ми ще НЕ писали жодного такого
шаблону — це і є той шар, який має сенс проєктувати спільно з вами, а не
передавати вже готовим.

## 3. Схема — три шари

### Реєстр документів
`documents` — кожен файл і його тип. Ключові колонки:
- `status` — стадія КОНВЕЄРА (`uploaded`/`text_ready`/`classified`/
  `extracted`/`failed`), НЕ статус довіри до змісту (той — на рівні факту).
- `domain` — `deployment`/`leave`/`equipment`/`staffing`/`normative`.
- `text_content` — повний розпізнаний текст (для FTS і цитування, розд. 5).
- `raw_uri` — де лежить оригінал (`file:///.../data/originals/...`). Файл
  видаляється через 30 днів (`documents.expires_at`, прибирання —
  `db/scripts/purge_expired_originals.py`), і разом із ним `raw_uri`
  занулюється. Текст і факти лишаються — зникає тільки сам файл, тож на
  `raw_uri` не варто спиратись як на завжди наявне поле.
- `pipeline_meta` (JSONB) — аудит-метадані пайплайна (як саме розпізнано,
  що не вдалось), рідко потрібне чат-боту напряму.

### Реєстр об'єктів
`objects` (id, `kind_id` → `object_kinds`: `person`/`equipment`/`task`/
`unit`, `canonical_name`) + типізовані розширення `people` (ПІБ, РНОКПП,
дати служби...) і `equipment`. `object_aliases` — історія псевдонімів
(та сама людина може бути записана по-різному в різних документах).

### Факти — це найважливіше для запитів
`facts` — ОДНА спільна таблиця для всіх вимірів (звання, відпустка,
місцезнаходження...), не окрема таблиця на кожен тип. Колонки:

| Колонка | Значення |
|---|---|
| `object_id` | про кого/що факт |
| `dimension_id` → `dimensions.code` | який вимір (`rank`, `leave`, `deployment_location`...) |
| `value` | значення (текст) |
| `valid_from`/`valid_to` | період чинності; `valid_to IS NULL` = досі чинний |
| `status` | `confirmed`/`unconfirmed`/`rejected` — **дивись розділ 4** |
| `confidence` | 0.0-1.0, від пайплайна |
| `source_doc_id` | документ-джерело (для цитати "звідки це відомо") |
| `additional_info` (JSONB) | поля, специфічні для конкретного типу документа, різні для кожного шаблону |

`dimensions.validity_model` пояснює, як читати `valid_from`/`valid_to`:
- `ranged` — має початок і кінець (відпустка: активна, поки сьогодні в межах діапазону)
- `current_state` — чинно, доки не з'явиться новіший факт того самого виміру для того самого об'єкта (звання, посада: підвищили → старий факт отримав `valid_to`, новий став чинним)
- `permanent_event` — разова подія, не "спливає" сама (номер наказу, дата документа)

### Маршрутизація/аудит
`review_queue` (документ/факт очікує ручної перевірки, `queue_type` каже
чому) + `review_log` (історія змін факту — старе значення/нове/чому).

## 4. Найважливіше правило для будь-якого запиту чат-бота

**Рахувати/відповідати лише по `facts.status = 'confirmed'`.** Незасіяний
факт (`unconfirmed`) — це значення, яке пайплайн не зміг витягнути
впевнено; `rejected` — значення, яке виявилось помилковим при повторній
обробці й замінене новим. Обидва не мають потрапляти в жодну відповідь
користувачу без явного зазначення "непідтверджено".

Станом на зараз (2026-08-13) у базі: **4 документи, 16 фактів, з них 10
`confirmed`.** Це тестові дані з демо-прогонів пайплайна, не продакшн-обсяг
— зручно для розробки запитів, не для оцінки продуктивності на масштабі.

## 5. Два шляхи пошуку відповіді

1. **Структуроване питання** ("скільки людей у відпустці зараз") →
   SQL-шаблон над `facts`/`dimensions`/`objects` (розділ 3).
2. **Пошук по нормативному тексту** ("що каже інструкція про...") →
   `documents.text_content` через Ukrainian FTS:
   ```sql
   SELECT id, ts_rank(to_tsvector('ukrainian', text_content), q) AS rank
   FROM documents, to_tsquery('ukrainian', 'наказ & звільнення') q
   WHERE to_tsvector('ukrainian', text_content) @@ q
   ORDER BY rank DESC;
   ```
   Морфологія працює (Hunspell-словник, стемінг: "наказом"/"наказу"/
   "наказів" → один лексем). Векторний пошук (embeddings) — свідомо НЕ
   зроблено: FTS дешевший і достатній, поки не доведено інше на реальному
   корпусі (`milidoc-project-context.md`, розд. 4).

Обидва шляхи читають ту саму БД — вибір між ними робить маршрутизатор чат-
бота за типом питання, не за окремим сховищем.

## 6. Підключення

```
host: localhost (поза Docker) / postgres (усередині docker-compose мережі)
port: 5433
db:   milidoc
user: milidoc_readonly   (read-only, саме для таких споживачів)
```
Пароль — у `.env` цього репозиторію (`READONLY_DB_PASSWORD`), не в цьому
файлі. Перевірено щойно — read-only користувач реально працює і бачить
дані.

## 8. Що ще НЕ вирішено (щоб не витрачали час на очевидне)

- Жодного SQL-шаблону для чат-бота ще не написано — це відкрита робота.
- `unit_to_report` (частина, до якої прибути) зараз лежить як текст у
  `facts.value`, не як зв'язок з об'єктом `unit` — якщо демо-запитам треба
  реальний join "скільки людей у частині Х", це окрема структурна зміна.
- PostgreSQL vs SQLite для цього проєкту — досі відкрите питання команди
  (розбір статті UNLP від Дениса), не остаточне рішення.
