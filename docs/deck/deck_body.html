01 · Limits of what already works

Six things we would tell the unit before they rely on it.

contradictionsA person cannot be on leave and away on duty at the same time. When the system creates a document it refuses to do that. When it receives one, it does not check — so a contradictory paper still enters the archive.
replacementsA slip issued to replace a cancelled one looks exactly like a contradiction. The form says "issued instead of №118"; we read that line but do not keep it.
referencesEvery answer names the record it came from. Asking for that record by name does not work yet — the identifier we show is one we cannot search by.
paper realityThe official leave form has no line for a slip number. Our documents print one, so our extraction relies on it. A real unit's slip may not have it at all.
waiting timeA question about a regulation takes about half a minute: the system searches, re-ranks, checks that the quote is really in the document, and only then answers.
unconfirmedSome records are still unconfirmed. They stay out of every count and are shown as a separate number — never quietly folded in.

02 · What we did not build in time

Named, not hidden — with the reason each one was left.

Missing for the user

  • A place to come back to a draft. Today you can confirm only the document you are uploading right now.
  • Contradiction check on upload. Agreed, designed, not wired in.
  • Two rules in one question. "Which of these two applies?" is not answered.
  • Adding a new form yourself. A new document type still needs a developer.

Missing for the operator

  • A one-page runbook exists, but the deployment itself is still manual: the running copy is not tied to a version.
  • Automatic deletion of stored files when their retention date passes.
  • Role separation. A guest with the QR code sees the same statistics page as an operator.
  • Stripping instructions planted inside a document body before the system reads it.

Everything on both slides is either measured or reproducible on the live system.

04 · Architecture

document→ reading & field extraction→ a person confirms→ facts & regulation texts→ answer

Reading a document

  • the form is recognised by its printed captions, not guessed from the layout
  • each field is taken by caption, by format, by arithmetic, or — last — by the model
  • every field carries how it was obtained and how certain we are
  • one weak critical field makes the whole document a draft

Answering a question

  • 31 pre-written, verified queries. The model never talks to the database
  • four tiers, cheapest first: rules → similarity → the model picks a query → the model writes one under rails
  • regulations take a second road: search, re-rank, gate, and two checks that the quote is literal
  • the sentence you read is assembled by code from database rows

Model, database and site run on one machine of ours. Nothing leaves the network.

06 · How we tested it

We attacked our own system first — and wrote down what broke.

The hard part

  • an audit of three full runs, about eighty questions — 31 defects found by us, before anyone asked
  • a golden set of 32 questions whose answers were proven by hand
  • two independent checks: a script, and a model that never saw the expected answer
  • a re-run after every round of fixes, so a fix cannot quietly break a neighbour

What holds today

  • 35 of 35 chat queries agree with an independent count made from the source files
  • 953 of 953 fields read correctly on 82 documents with known answers
  • zero confidently wrong routings across 127 test questions
  • over 1200 tests; almost every one written for a specific defect that once happened

Each of these is one command. A third party can reproduce the numbers without us.

07 · Protecting the data

Nothing leaves this network.

In place

  • the model, the database and the site are on one machine of ours; no external service is in the path
  • the site cannot write to the database at all — it connects as a read-only user
  • a query written by the model is checked before it runs: one read, a fixed list of tables, a row limit and a time limit
  • our pages make no external requests — even the fonts are local, so no third party learns who is looking
  • a guest with the QR code can ask and read, but cannot upload

Open

  • role separation is coarse: a guest sees the same statistics as an operator
  • personal data is reachable through the chat by design — the people this is built for already work with those documents daily
  • stored files have a delete-by date, but the deletion is not yet automatic
  • the stand runs on synthetic data; no real personal data has ever been in this repository

08 · What needs a developer

A new form is a day of work — not a setting.

Needs a developer

  • a new document type — a description of the form and a copy of the blank: about a day
  • a new kind of question — one more verified query: about an hour
  • an officer cannot add either one alone

Already changeable without code

  • ranks, kinds of facts, keywords that decide a document's domain
  • the topic list for regulations — documents match themselves against it, so a new act needs no editing
  • what the model is told, and the example questions it learns from

Said plainly: this is a working system for two document types, not a configurable platform.

09 · Keeping the model in its lane

The model chooses and extracts. It never writes the answer.

Measured against 48 attacks

  • the part that picks a query: held every time — its reply must fit a fixed shape, leaving no room for a free sentence
  • the part that approves a quote: held every time — a quote must appear word for word in the document
  • the raw model on its own does break under role-play framing. That is a known weakness of the model, and it sits outside our path

Why the product holds anyway

  • there is no channel where free model text reaches a person: answers are written by code from database rows
  • a quote is verified twice — literally, and by whether it shares words with the question
  • an unconfirmed record never enters a count, whatever the model said
  • two roles: an operator with a password can upload; a guest cannot
  • remaining risk: an instruction hidden inside a document's own text. Stripping it is the next task
