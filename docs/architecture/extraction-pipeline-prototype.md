# Пайплайн екстракції полів з документів

Реалізація кроку 2 з `docs/architecture/architecture-proposal.md` ("Обробка вхідних документів") — не окрема ініціатива, а робочий код погодженого підходу (regex-first + LLM зі схемою для шумних полів), перевірений на реальних зразках з `data/eval/samples/`.

**Запускається локально, без Colab:** `python run_pipeline.py`. Код: `pipeline/*.py`, схеми `schemas/*.yaml`, довідники `dictionaries/*.yaml`, конфіг `config.yaml`.

**Межі цієї частини роботи:** файл на вході → структурований запис у локальному сховищі. Зовнішнє сховище (MinIO) і база даних — не тут; вихід спроєктований так, щоб їх можна було приєднати пізніше, але жодного коду під них у цій частині немає.

## Мета

Перетворити вхідний файл (фото/скан бланка або `.docx`) на структурований запис для БД: `subject` (особа), `facts` (тип, значення, діапазон дат, `additional_info`), `document_meta` (повна YAML-шапка з провенансом кожного поля). Двигун генеричний — новий тип бланка додається новим `schemas/<template>.yaml`, без нового Python-коду.

## Потік

```
файл (.docx / .pdf / фото) з папки-приймача (config: paths.input_dir)
  → хеш вмісту (SHA-256) → якщо такий уже оброблено: status=duplicate, далі не йдемо
  → інжест (pipeline/ingestion/ingest.py)
      docx  → параграфи + клітинки таблиць + header/footer (без OCR)
      pdf   → текстовий шар: блоки З КООРДИНАТАМИ через PyMuPDF (без OCR)
              скан у PDF: рендер сторінок → OCR
      фото  → Surya OCR → впорядкування блоків за bbox (зверху-вниз, зліва-направо)
  → визначення ШАБЛОНУ (pipeline/identification.py)
      скоринг усіх схем за їхніми блоками identification: (заголовок ×5, якорі ×2)
      нічия за балом            → unresolved (рівний бал = жоден не підтверджений)
      кілька схем >= min_score  → unresolved: multiple_templates_matched
                                  (документ-контейнер, напр. інструкція з
                                   додатками, а не сам бланк)
      нижче min_score, але хоч один анкор → LLM-тайбрейк (grammar, з "unknown");
                                  обраний МОДЕЛЛЮ шаблон ніколи не дає confirmed
      жодного анкора → status=unresolved, у чергу, без спроби екстракції
  → екстракція (pipeline/extraction/extract.py + schema_grammar.py)
      1) детермінований прохід: regex / значення-перед-лейблом / токенізація звання+ПІБ
      2) прогалини → групи по batch_size → grammar-constrained LLM-виклик на групу
  → нормалізація (pipeline/normalization/normalize.py): дати → ISO, категорія → {code,label}
  → збірка (pipeline/build_record.py): subject + facts[] + field_provenance
  → вихід: YAML-шапка + текст → .md у локальне сховище (data/output)
  → сам вхідний файл переноситься з приймача: data/processed/<дата>/ або,
    якщо unresolved, data/failed/<дата>/ -- щоб приймач спорожнявся
```

Папка-приймач сканується **не рекурсивно**, і про пропущене (підпапки, файли
непідтримуваного типу) CLI повідомляє явно — раніше такі файли зникали
безслідно, і людина, що поклала папку з документами, бачила лише «не знайдено
файлів» без пояснення. Оброблені файли переносяться **лише з налаштованої папки-приймача**
(`paths.input_dir`). Раніше умовою було просто «target — це папка», тому
прогін на `data/eval/samples/` фізично виносив зразки з репозиторію; захист
працював лише для одного файла, переданого через `--input`.

## Очікування (інваріанти)

- **Вихід існує завжди** — `confirmed` / `needs_review` / `unresolved` / `duplicate`, ніколи голий крах без сліду.
- **Категоріальні поля** — завжди `{code, label}` з довідника, незалежно від того, яким шляхом отримані (LLM під grammar видає код, детермінований шлях — алиас; `resolve_category` приводить обидва до однієї форми).
- **`confirmed` рахується лише по КРИТИЧНИХ полях** — некритична прогалина (вільнотекстовий опис) не блокує запис, інакше в черзі ручного рев'ю опинявся б кожен документ і черга стала б безглуздою. Але `confirmed` **неможливий**, якщо: шаблон обрала модель, а не анкори; діапазон дат суперечливий; морфологія ПІБ не спрацювала (значення лишилось у відмінку джерела). Похідні факти (поля з `dimension:`) успадковують підтвердження основного, а не рахують його самі.
- **Збій одного LLM-виклику ізольований** до своєї групи полів; детерміновані значення й інші групи не втрачаються.
- **Провенанс кожного поля** (`matched` / `llm` / `no_value` / `llm_error:*` / `deferred` + критичність) зберігається в записі — без цього неможливо ні таргетувати 5%-аудит, ні перерахувати документи після виправлення схеми.

## Ключові технічні рішення

**Ідентифікація на рівні ШАБЛОНУ, не домену.** Схема прив'язана до `template`, а один домен містить багато бланків — перевірка "домен схеми == домен класифікації" не відрізнить "правильний домен, неправильний бланк". Кожна схема сама описує, як її впізнати (блок `identification`), тому вибір схеми став частиною пайплайна, а не ручною дією людини в діалозі завантаження. Це те, що робить пакетний режим (папка-приймач із `docs/spec/project-expectations.md`) можливим. Рівний бал двох схем — це `ambiguous`, а не перемога того, хто перший у списку.

**Гібрид: детермінований прохід, потім LLM лише на прогалини.** Regex/label-пошук дешевий і детерміністичний там, де верстка бланка стабільна й підтверджена на реальному зразку. LLM підключається вибірково.

**Групи по `batch_size` полів, не "по одному" й не "все одразу".** Один виклик на поле — багато викликів (повільно на CPU); один виклик на весь документ — збій одного виклику втрачає всі LLM-поля разом. Групи ізолюють збій до кількох полів.

**Два види прогалин з різним контекстом.** Локалізовані (місце знайдено, не вдався лише розбір рядка — напр. прізвище не ВЕЛИКИМИ літерами) отримують у промпт **лише цей рядок**: на реальному прогоні це 34 символи проти 227 символів повного тексту, а на справжньому документі різниця ще більша. На CPU довжина промпту — головна стаття витрат. Нелокалізовані (місце не знайдено взагалі) отримують повний текст, бо іншого немає. Кандидат, відхилений denylist-ом, підказкою **не** стає — це саме неправильний текст, і передавати його означало б підштовхувати модель до тієї самої помилки.

**JSON Schema → GBNF grammar замість вільного тексту.** Категоріальне поле фізично не може отримати неіснуючий код. Кожне поле nullable навмисно — інакше модель під grammar змушена вигадати значення там, де його немає. Grammar гарантує **форму**, не правдивість.

**Дедуплікація за хешем вмісту.** Ручний експорт людиною з АСКОД/Армія+ гарантує повторні завантаження того самого документа; подвійні факти подвоюють саме ті підрахунки, заради яких будується система. Реалізовано як append-only індекс `index/processed.jsonl` (хеш вмісту → ключ запису).

**5%-вибірка на аудит — детерміністична від хешу**, не `random`: те саме рішення при повторному прогоні того самого документа, жодного стану генератора між запусками.

## Виправлені баги (усі підтверджені прогоном, не гіпотетичні)

### За зовнішнім код-рев'ю (08.08.2026)

Крахи, що валили ВЕСЬ пакетний прогін, а не один документ:
- `int(year)`/`int(day)` без перевірки на цифри: grammar не обмежує дати
  шаблоном цифр, тож `{"day": "невідомо"}` від LLM кидало `ValueError` вгору;
- `KeyError` на неповному записі в `domain_keyphrases.yaml`;
- виклик LLM під час ідентифікації шаблону без `try/except`;
- відсутність `try/except` навколо обробки одного файлу в батчі — тепер це
  остання лінія захисту гарантії «вихід існує завжди».

Мовчки неправильні значення (найгірший клас для проєкту, де людина
підтверджує факти):
- **нічия при self-consistency** тепер видима як `llm_split_vote`: переможець
  при рівних голосах визначався порядком у списку, а виглядав як одноголосний;
- **неоднозначний лейбл** (два схожі лейбли в документі — звання заявника й
  звання командира) більше не «беремо перше входження», а `ambiguous_label`;
- **денай-лист** порівнював кандидата точним рівнянням, тому багаторядковий
  кандидат (заголовок + номер наступним рядком) мовчки проходив — тепер
  перевіряється кожен рядок;
- **підказки різних полів** склеювались в один контекст без прив'язки, і LLM
  могла приписати підказку одного поля іншому — тепер групування за самою
  підказкою;
- **прізвище видалялось зі списку імені за значенням, не позицією**: дубльований
  OCR-токен прибирав обидва входження й зсував по батькові в поле імені;
- **підрядкові збіги без межі слова** в анкерах схем і фразах доменів;
  межа вимагається на початку, але не в кінці — інакше зламались би свідомі
  стеми довідника («відрядж», «особов»);
- **нічия домену** взагалі не детектувалась — брався перший за порядком YAML.

Покриття й інжест:
- дати без «р./року» і числові (`15.05.2025`, `01/06/2025`) не розпізнавались
  узагалі — систематична прогалина, не окремий випадок;
- дедуплікація header/footer через `id()` без сильних посилань — той самий
  клас бага, який уже був знайдений і виправлений для клітинок таблиць;
- рішення «текстовий шар чи скан» у PDF приймалось на весь документ, тому
  сторінка-скан усередині текстового PDF ніколи не йшла в OCR;
- вкладені таблиці всередині клітинок не читались;
- багатосторінковий TIFF читався лише першим кадром.

Інше: мертвий LLM-фолбек класифікації домену прибрано (template-level
tie-break у `identification.py` — і є той LLM-шлях); `inference_parallel`
піднято в конфіг; `config.yaml` тепер шукається і відносно кореня проєкту, а
не лише CWD (запуск із планувальника мовчки падав у дефолтний режим);
stdout/stderr примусово UTF-8 (редірект у файл на Windows міг кинути
`UnicodeEncodeError` ПІСЛЯ успішної обробки); лок у `LlamaClient`; верхні межі
версій у `requirements.txt`; `download_model.py` більше не вибирає файл
алфавітно й обробляє обрив мережі.

### Наскрізне рев'ю всього пайплайна (12.08.2026)

За явним запитом ("пройдися по всьому пайплайну... виправ помилки") -- чотири
паралельні агенти по всіх модулях, з фокусом на "тихо неправильно". 10
підтверджених багів, повний перелік і сценарії відмови -- `docs/known-weak-spots.md`
розд. 4. Найважливіші:

- **Геометрична прив'язка значення до лейбла за bbox** (замість порядку
  блоків): `_geometric_candidate`, `_is_mega_block`, детермінований
  "сендвіч"-парсер для значень, склеєних з лейблом без розриву. Виявлено й
  виправлено ПІД ЧАС розробки: bbox рахується ОКРЕМО на кожній сторінці
  PDF/кадрі TIFF (з нуля), тому геометричне порівняння МІЖ сторінками --
  нуль-сенс, який давав спорадичні неправильні збіги; кожен блок тепер несе
  мітку сторінки.
- **`label_before` тепер у промпті LLM** (`pipeline/llm/client.py`) -- раніше
  модель бачила лише внутрішню англомовну назву поля.
- **Гліосарій код=термін для категоріальних полів** (`_category_glossary`,
  `schema_grammar.py`) -- усунуто розрив між латинськими кодами довідника
  (`soldier`, `captain`) і українським текстом документа; виправило виміряну
  категоріальну галюцинацію LLM ("капітан" замість "рядовий", коли це звання
  в документі не згадувалось узагалі).
- **`_extend_across_block_boundary`** -- значення, розірване PDF на межі двох
  блоків (PyMuPDF розбиває параграф не за змістом), збирається назад за
  ознакою незбалансованої дужки.
- **Системний промпт приведено у відповідність контракту виводу**
  (`pipeline/llm_context/document_processing_guidelines.md`) -- раніше писав
  "відповідай одним словом «невідомо»", а реальний вивід -- JSON з кількома
  полями і `null`.
- Дрібніші: `glob` з квадратними дужками в назвах файлів, `н/д`/`б/н` у
  плейсхолдерах, блокування `index/processed.jsonl` при записі, верхня межа
  для `number_from_words`, `process_file` з власним try/except, локальний (не
  UTC) день у назві архівної теки.

**Результат на реальних документах (з LLM), до/після сьогоднішніх фіксів:**
LEAVE-001.png 54.5% -> **90.9%**, згодом **100%** (після гліосарія категорій);
TRIP-002.docx **100%**; TRIP-004.pdf 90% (одне поле обрізане на межі блоків,
виправлено, тепер точне значення); LEAVE-003.pdf і TRIP-003.png -- по два
поля виправлено фіксом геометрії. **PDF-база без LLM зросла двічі поспіль:
62.5% -> 67.6% -> 69.3% (leave), 57.9% -> 63.6% -> 65.0% (trip)** -- ефект
ширший за конкретні тестові документи. Тести: 34 -> 36 (два нових
регресійних). docx-регресія (96.6%/75.7%) незмінна протягом усіх змін.

**Найважливіша знахідка, ЛИШИЛАСЬ невиправленою:** значення `"matched"` від
`block_before_label` ніколи не перевіряється на правдоподібність і не
отримує другого шансу через LLM-фолбек -- корінь кількох різних поверхневих
симптомів одразу. Потребує окремого дизайн-раунду (як валідувати "чи схоже
на тип поля" всередині генеричного двигуна), не патча. Деталі --
`docs/known-weak-spots.md`, розд. "matched" від block_before_label.

### Раніше


- **`regex`-поля не мали LLM-фолбеку взагалі** — найкрихкіший режим (паттерн під конкретну верстку) був єдиним без страховки. Тепер їхні провали теж ідуть у прогалини.
- **`rank` мав дві різні форми** залежно від шляху: `{code,label}` з довідника проти `'soldier'` (рядок) від LLM — у БД це два різні типи в одній колонці. Виправлено `resolve_category`.
- **Текст клітинок docx дублювався 4-6 разів**: `python-docx` повертає об'єднану клітинку окремо для кожної колонки сітки. Тіло реального посвідчення: 104 → 60 рядків. Це не косметика — роздутий текст це довший промпт, тобто прямі витрати часу на CPU.
- **Перша версія цього ж фіксу зламала дати**: дедуплікація через `id()` на lxml-елементі ненадійна, бо проксі може бути зібраний GC, а `id` перевикористаний іншим елементом. Виправлено утриманням сильних посилань.
- Раніше: багаторядкове значення перед лейблом обрізалось до одного рядка; заголовок документа потрапляв у поле "прізвище"; прізвище малими літерами зсувало `given_name`/`patronymic` на тихо неправильні значення; схема/довідники визначались за назвою файлу; `.lstrip(prefix)` замість зняття префікса-рядка; docx header/footer не читались.

## Локальний запуск

```bash
python run_pipeline.py                      # уся папка data/inbox
python run_pipeline.py --input <файл>        # один документ
python run_pipeline.py --no-llm              # лише детермінований прохід
python run_pipeline.py --template leave_ticket   # примусова схема (для тестів)
python run_pipeline.py --dry-run             # нічого не зберігати
```

Пайплайн **працює й без моделі** (`--no-llm` або `llm.enabled: false`) — детермінований прохід дає результат, прогалини чесно позначені. Це корисно для швидкої перевірки логіки, але це НЕ повний режим: поля з `extraction: llm` (напр. `destination_points`, `purpose`) лишаються порожніми, тому запис виходить `needs_review`, а не `confirmed`.

### Швидкість: ЗАМІРЯНО НА ПОВНИХ ПРОГОНАХ 11.08.2026

**Попередня оцінка «~56 с на документ» була неправильною в ~25 разів.** Вона
походила з одного документа з ОДНІЄЮ LLM-групою; на повному прогоні картина
інша. Хронометраж за часом запису звітів (CPU, MamayLM-12B Q4_K_M,
`n_gpu_layers: 0`, 12 логічних ядер):

| прогін | тривалість | на документ |
|---|---|---|
| 14 посвідчень, docx + LLM | 11:10 → 17:21, **6 год 11 хв** | **~26 хв** |
| 2 відпускних, png + Surya + LLM | 17:21 → 17:56 | **~17 хв** |
| 3 посвідчення, png + Surya + LLM | 17:56 → 18:59 | **~21 хв** |
| завантаження ваг (6.8 ГБ, одноразово на процес) | ~257 с | -- |

Бюджет, підтверджений Анною, -- пара хвилин на документ, до ~5 хв норма.
Заміряне перевищує його в **5-10 разів**. Отже теза «час не є обмеженням»,
на яку спиралися рішення 10-11.08 (зокрема аргумент, що додаткові LLM-проходи
«вкладаються в бюджет»), **неправильна** й вимагає перегляду.

### Залізо (перевірено 11.08.2026, раніше не було зафіксоване)

**Intel i5-1235U, 10 фізичних / 12 логічних ядер, 15.6 ГБ RAM** -- 15-ватний
ноутбучний чип з 2 сильними та 8 слабкими ядрами. Під час прогону машина була
**у свопі**: вільної RAM 0.37 ГБ, пік pagefile 25 ГБ. Тобто вузьке місце
щонайменше частково -- ПАМ'ЯТЬ, не обчислення, і це змінює порядок дій.

### Куди йде час -- за приоритетом множників (порядок виправлено)

1. **Розмір моделі -- ПЕРШЕ.** 12B Q4_K_M це 6.8 ГБ ваг плюс KV-кеш, плюс
   torch під Surya, плюс браузер -- на 15.6 ГБ це своп. Перехід на ~2.5 ГБ
   прибирає своп, а не лише дає ~3x за параметрами. (Раніше цей пункт стояв
   третім -- див. п. 3.)
2. **Нелокалізовані прогалини отримують ПОВНИЙ текст документа** (до
   `max_context_chars`, 6000). На CPU довжина промпту -- головна стаття
   витрат, і кожна група платить її окремо. Показово: `leave_ticket` не має
   жодного `extraction: llm` поля, але прогін відпускних по фото коштував
   ~17 хв на документ -- бо OCR зламав лейбли, поля впали в global_gaps і
   поїхали в модель з повним текстом. Тобто **та сама причина дає і 54.5%
   точності, і сімнадцять хвилин**; виправлення п. 2.11a
   (`docs/known-weak-spots.md`) здешевлює прогін, а не лише підвищує якість.
3. **`n_threads` не задано в конфізі** -> llama.cpp бере свій дефолт. Я
   ставила це першим пунктом як «втрачаємо 12 ядер», а потім (11.08) підозрювала
   протилежне -- що на гетерогенному чипі примусові 12 потоків гірше за дефолт.
   **СПРОСТОВАНО заміром 12.08.2026** (`llama-bench`, реальні ваги): пропускна
   здатність зростає МОНОТОННО з 2 до 10-12 потоків, і для prefill, і для
   generation -- 12 потоків не гірше за 10. Причина, чому це все одно не
   пріоритет: `llama-cpp-python` ставить `n_threads_batch` (prefill, 85% часу
   виклику) у `cpu_count()` ЗАВЖДИ, незалежно від конфігу -- найдорожча фаза
   вже йде на всіх ядрах без нашого втручання. Деталі: `docs/known-weak-spots.md`,
   `docs/research/2026-08-12_ocr-geometry-speed/research-round-2026-08-12.md`.
4. `n_ctx: 4096` проти `max_context_chars: 6000`: для кирилиці 6000 символів
   можуть не вміститись у контекст (див. `docs/known-weak-spots.md` п. 2.3).

### Перехід на меншу модель: тепер це вимірюване питання, а не спір

`MamayLM-Gemma-3-4B-IT-v1.0-GGUF` (~2.5 ГБ) -- **але це НЕ просто менша
модель**: v2.0 існує лише в 12B і 27B, тож перехід на 4B означає відкат на
weights v1.0, тобто зміну і розміру, і версії тюнінгу одночасно. Мій
попередній коментар у конфізі («зміна одного рядка») цього не враховував.
Раніше вибір розміру обґрунтувати було нічим: якість MamayLM на українській у
малих розмірах незалежно не підтверджена (`docs/open-questions.md`, «Юридичне» і
«Архітектура»). **З появою еталонного набору це стало вимірюваним**: ті самі
документи, ті самі по-польові правильні відповіді, `eval/evaluate.py`
пише порівнюваний JSON. Тобто рішення приймається за цифрами точності, а не
за міркуванням про розмір.

Порядок, який має сенс: спершу (1) і (2) -- вони безкоштовні й дають більший
множник, ніж заміна моделі, -- і лише потім порівняння 12B проти 4-8B на
однаковому наборі.

## Вихід, придатний до приєднання сховища й БД пізніше

Ключі пласкі й передбачувані (`documents/<domain>/<id>.md`), а вся витягнута
інформація лежить у YAML-шапці одним об'єктом (`subject`, `facts`,
`field_provenance`), не розкидана по тілу файлу. Тому `data/output` можна
перелити в зовнішнє сховище або розкласти в таблиці, коли за це візьметься
відповідна частина команди — без змін у самому пайплайні.

`facts` — список: основний факт шаблону завжди перший (`facts[0]`), далі по
одному факту на кожне поле схеми, що оголосило `dimension:`. Форма також
передбачає майбутні `multiple: true` поля (зупинки в посвідченні, рядки книги
обліку).

**Форма шапки однакова для всіх статусів.** `confirmed`, `needs_review`,
`unresolved` і `duplicate` віддають той самий набір ключів; відсутнє значення
— `null` або порожня колекція. Раніше форм було шість (у дублікаті не було ні
`template`, ні `facts`), і завантажувач БД падав `KeyError` на першому ж
дублікаті в папці.

Повний контракт полів, відображення на таблиці БД і **перелік питань до
команди БД** — у `docs/contracts/2026-08-11_database-handoff.md`. Там же те, що на їхньому боці зараз
губиться (`confidence` не вставляється, `unresolved` не потрапляє в
`review_queue`, `resolve_or_create_object` не викликається).

## Визначення суб'єкта документа (РЕАЛІЗОВАНО 13.08.2026)

**Реалізація:** `pipeline/subject_kind.py` (порядок рівнів, закритий перелік,
гейт), `schemas/*.yaml` (`subject_kind:` — оголошення схеми),
`dictionaries/domain_keyphrases.yaml` (мапінг «домен → вид»),
`pipeline/run.py` (`blank_meta` + гейт у `process_file`),
`pipeline/identification.py:validate_schema` (відхиляє невідомий вид).
Контракт із БД — `docs/contracts/2026-08-11_database-handoff.md`, розд. 1.1. Заміряно: усі чотири
корпуси `--no-llm` до і після — звіти БАЙТ-ІДЕНТИЧНІ (обидві схеми про людей,
тому зміни виходу не мало бути, і її немає). Нижче — обґрунтування рішень,
воно лишається чинним.

Було до цього: пайплайн не віддавав вид суб'єкта взагалі, `subject` плаский і
припускає ПІБ. Схеми оголошують `registry: person` / `military_unit`, і цей
ключ код не читає (нуль входжень у `pipeline/`; лишилось так — `registry` і далі
у `DECLARED_BUT_UNREAD_KEYS`, бо це вид ПОЛЯ, а `subject_kind` — вид
ДОКУМЕНТА, і одне через інше не виводиться: у відпускному квитку є поле з
`registry: military_unit`, але суб'єкт документа — `person`). На боці БД місце
є — `object_kinds` містить `person` / `equipment` / `task` / `unit` (`unit`
додано на нашу пропозицію), а `objects.kind_id` NOT NULL — але їхній
завантажувач жорстко бере `code = 'person'`.

Це блокує і роботу з не-людськими суб'єктами (книга обліку техніки), і
фільтрацію в базі за видом об'єкта.

**Порядок розв'язання (запропоновано Анною, уточнено тут) -- три рівні,
від найнадійнішого до найслабшого:**

```
є схема                → subject_kind зі схеми (це ОГОЛОШЕННЯ, не висновок)
немає схеми:
  домен визначений      → мапінг домен -> вид, з YAML; значення може бути "none"
  домен не визначений   → LLM, ЗАКРИТИЙ enum + "unknown"
вид none / unknown      → об'єкт у БД НЕ створюється, документ у чергу рев'ю
```

**Чому схема вище домену.** Схема прямо оголошує, що описує; домен -- результат
підрахунку ключових фраз, який може з нею не збігтися. Виводити вид із домену
при наявній схемі означає додати індирекцію, здатну суперечити оголошенню.

**Чому мапінгу потрібне значення "none", а не лише person/equipment.** Домен
не тотожний виду суб'єкта, і в репозиторії вже є документ, на якому мапінг
дав би впевнено неправильну відповідь: нормативна інструкція з діловодства.
(Уточнення після реалізації: домен `normative` тепер у довіднику Є, з
`kind: procedural`, тому інструкція вже не впізнається як `equipment` — але це
робить `none` не менш, а БІЛЬШ потрібним: домен визначається правильно, і
мапінг мусить мати чим на нього відповісти.) Мапінг без `none` створив би на
неї об'єкт, якого в документі нема.
Окремо `staffing`: вид -- людина, але **багато людей**. Вид суб'єкта й
кількість суб'єктів -- різні питання, мапінг відповідає лише на перше.

**Чому відповідь LLM мусить бути закритим переліком.** Той самий аргумент, що
для `fact_type`: вільна відповідь створює види, яких у `object_kinds` немає, і
`kind_id` отримує сміття. Плюс обов'язковий варіант "unknown" -- інакше модель,
обмежена лише реальними видами, змушена вибрати щось навіть коли суб'єкта в
документі немає.

**Чому "немає виду -> немає об'єкта".** Інакше нормативна інструкція й будь-який
непізнаний документ породжують фантомні об'єкти в реєстрі. Це той самий клас
проблеми, що "одна людина двома об'єктами", але гірший: об'єкт вигаданий
цілком, і він назавжди лишається в `objects` (шляху видалення в завантажувачі
немає).

**Де живе мапінг:** у `dictionaries/domain_keyphrases.yaml`, поруч з описом
домену -- не в коді. Інакше ми знімаємо один хардкод і одразу додаємо інший.
ЗАКРИТИЙ ПЕРЕЛІК допустимих видів при цьому лишається в коді
(`subject_kind.py:KNOWN_SUBJECT_KINDS`), і це не суперечність: перелік -- не
наше налаштування, а копія рядків чужої таблиці `object_kinds`, тому місце
йому там, де вже живуть `KNOWN_DB_TARGETS` і `NAME_PART_ROLES`. У YAML живе
ВІДПОВІДНІСТЬ, у коді -- ДОПУСТИМІ ЗНАЧЕННЯ, і кожен із двох файлів
валідується проти переліку.

**Що вирішено при реалізації (не було в пропозиції):**

- **Схема без `subject_kind:` -- попередження, не помилка.** Помилка виключає
  схему з набору (`run.py:build_resources`), тобто ВСІ документи цього шаблону
  пішли б в `unresolved` через один відсутній рядок YAML, тоді як робочий
  фолбек (мапінг домену) існує: `domain:` схема оголошує завжди. Тихо це не
  проходить -- попередження при завантаженні плюс `subject_kind_reason` у
  кожному записі.
- **Домен визначено, мапінгу для нього немає -> `unknown`, і модель НЕ
  питають.** Домен уже відомий, тобто відповідь мусить дати рядок у YAML;
  відповідь моделі замаскувала б прогалину в довіднику, причому ТИХО, бо вид
  виглядав би визначеним. LLM -- рівень для випадку «домену немає», не
  «довідник неповний».
- **`none` не псує статус документа, `unknown` -- псує.** `none` -- це
  відповідь, і примусове рев'ю там означало б, що кожен нормативний документ
  назавжди висить у черзі без жодної дії, яку людина може виконати. `unknown`
  -- відсутність відповіді, тобто той самий клас, що `template_by_llm`: спершу
  скажи, ПРО ЩО документ, і лише потім дивись на поля. Тому й черга та сама,
  `unknown_type`, а не `unconfirmed_fact`.
- **`create_subject_object` -- окрема вісь від `subject.person_complete`,
  не кон'юнкція.** У техніки прізвища немає за визначенням, тому
  `person_complete: false` для неї -- норма, а не перешкода створенню об'єкта.
  Один прапорець відповідає «чи треба об'єкт і в якому реєстрі», другий -- «чи
  вставиться рядок `people`».

**Точка розширення під LLM (рівень 3) реалізована, але вимкнена:**
`resolve_subject_kind(llm_choose=...)` + `build_subject_kind_prompt`, вибір
обмежений `LLM_SUBJECT_CHOICES`. Підключення в `run.py:_subject_kind_llm`
прикріплене до окремого прапорця `llm.subject_kind` (за замовчуванням `false`),
а НЕ до загального `llm.enabled`. Причина: рівень 3 запускається саме на
документах без схеми й без домену, тобто на найдовших і найчужіших текстах
батчу (інструкція -- 402898 символів), і кожен такий документ додав би повний
виклик моделі до прогону, який зараз обходиться майже без неї. Увімкнення має
бути окремим рішенням із власним заміром.

**Закрито:** `object_kinds` тепер має вид `unit` (додано командою БД на нашу
пропозицію). Лишається окрема, не пов'язана з видом задача: `registry:
military_unit` (`destination_org`, `unit_to_report`) не робить із частини
окремий об'єкт, бо `subject` плаский і тримає одного суб'єкта на документ.

Мапінг «ключ еталона -> поле схеми» -- у `eval/field-mapping.yaml`, не в

1. **Дата видачі -- 13 з 16 неправильні, і завжди правдоподібні.** Брали дату
   початку відпустки: `document_date` був загальним regex і забирав ПЕРШИЙ
   збіг у тексті. Виправлено паттерном, прив'язаним до «№ ... від <дата>».
2. **Номер документа -- 0 з 16.** У схемі стояв `deferred` з коментарем «в
   бланку немає реального номера». У заповнених документах номер і дата --
   одним рядком: `№ 102    від 09.05.2026`.
3. **Населений пункт -- 0 з 16.** Лейбл розрізаний на два блоки, а значення
   стоїть МІЖ ними, тому об'єднане поле віддавало лише вид відпустки. Окреме
   поле `destination_place` з лейблом «до якого звільнено військовослужбовця».
4. **Кількість днів -- 9 з 16 порожні.** На бланку вона надрукована ЛИШЕ
   прописом («терміном на / тринадцять / (кількість днів прописом)») -- цифри
   в документі немає взагалі. Додано `number_from_words`.
5. **Звання -- 50%.** «Старшина» і «старший прапорщик» (стара система звань)
   відсутні в довіднику. Додано разом із «прапорщик».

### Підтверджено проти еталона

- `swapped_dates` -> `date_range_error`, документ не `confirmed`;
- `empty_fields` -> `needs_review`;
- шаблон визначено правильно 30 з 30;
- прогін на папку `samples` більше не ВИНОСИТЬ зразки з репозиторію (переносимо
  лише з налаштованої папки-приймача -- раніше захист працював лише для
  одного файла, переданого через `--input`, не для папки).

### Що еталон показує як нерозв'язане

- **`unknown_person` (LEAVE-012) виходить `confirmed` з 11/11 правильних
  полів.** Документ читабельний і повний; те, що особи немає в реєстрі, з
  самого документа невідомо. Це задача `resolve_or_create_object` на боці БД,
  але наслідок наш: такий запис створить нову особу мовчки.
- **Пари «документ + той, що скасовує» не розпізнаються.** Обидва документи
  виходять однаково `confirmed`. Зв'язку документ->документ у контракті немає,
  а в таблиці `facts` споживача немає колонки `superseded_by`.
- **`ocr_noise` (TRIP-012)** -- 4 з 10 полів; найгірший результат серед
  посвідчень, і саме він показує стелю regex-підходу на шумі.

## Обмеження, що свідомо лишаються

- **Жоден реальний заповнений `leave_ticket` не перевірений** (лише порожній шаблон), на відміну від `deployment_certificate`.
- **ЗАКРИТО 11.08.2026:** раніше тут стояло «один документ, один прогін — не статистика». З'явився еталонний набір на 30 документів із по-польовими правильними відповідями, і точність тепер вимірюється (див. розділ вище), а не оцінюється на око.
- **Один документ → один факт.** `facts` уже список (форма запису правильна), але екстракція `multiple: true` полів не реалізована. Для `deployment` це зупинки на звороті — у реальному зразку вони **заповнені** ("Вибув із в/ч UNIT-0252, м. Київ" / "Прибув до смт Десна"), тобто дані є й їх можна дістати. Для домену `equipment` (книга обліку техніки) багато рядків на документ буде нормою, не винятком — це наступна велика переробка.
- **`object_ref`-поля не резолвляться** проти реєстру осіб/частин — немає заповненого реєстру. Ототожнення осіб навмисно НЕ автоматичне: вгадувати "той самий Іваненко чи інший" за ПІБ означало б саме той клас тихої помилки, від якого застерігає `docs/architecture/architecture-proposal.md` розд. 7.
- **Морфологічна нормалізація ПІБ** реалізована через `pymorphy3` (словник uk):
  «БЕВЗЕНКА Юстима Едуардовича» → «БЕВЗЕНКО Юстим Едуардович», регістр джерела
  зберігається. Статус іде в провенанс (`morphology`): `normalized` /
  `already_nominative` / `not_a_name` / `inflect_failed` / `no_morphology` —
  останні три означають, що значення лишилось у відмінку джерела, і це видно,
  а не виглядає як успішна нормалізація. Український словник pymorphy3 датований
  2022 р., тож на рідких прізвищах якість не гарантована — саме тому статус
  зберігається пофайлово.
- **Багатосторінкові документи** як єдина логічна одиниця не підтримуються: кожен файл обробляється незалежно.
- **5%-вибірка на аудит існує лише як позначка в записі** (`review_reason: random_audit`); окремої черги/таблиці немає — це вже частина роботи з БД.
- Colab-ноутбук пайплайна **видалено 11.08.2026** — він викликав старий API `extract_document` і вводив в оману. Канонічний шлях: `run_pipeline.py`, оцінка: `eval/evaluate.py`. У `notebooks/` лишились лише експерименти з моделями й OCR, на які є посилання як на джерело рішень.
