# ТЕХНІЧНЕ ЗАВДАННЯ: Чатбот для зведених запитів по документообігу

## 1. ЗАГАЛЬНІ ВІДОМОСТІ

Система призначена для організацій із великим обсягом паперового й електронного документообігу. Замовник — військова частина, що веде облік особового складу, техніки та місій.

## 2. МЕТА ТА ПРИЗНАЧЕННЯ СИСТЕМИ

### 2.1. Проблема

Інформація зафіксована в документах — рапортах, наказах, довідках, актах. Отримання зведеної картини вимагає послідовного звернення до кількох людей та ручного підрахунку, що займає години або дні.

### 2.2. Що робить система

Система читає документи, дістає з них ключові дані у структурований вигляд і зберігає в базі даних. Ключова відмінність: система не просто знаходить потрібний документ, а **рахує й зводить дані з багатьох документів одразу**.

### 2.3. Приклади використання

**Приклад 1 — облік особового складу**

- Запит: «Скільки людей зараз у відпустці?»
- Відповідь: «Пʼятеро: [імена]. Проаналізовано 47 записів, 3 очікують підтвердження. Дані станом на 24.07.»

**Приклад 2 — облік техніки**

- Запит: «Скільки одиниць техніки зараз на ремонті?»
- Відповідь: «Девʼять: [перелік]. Проаналізовано 120 записів, 5 очікують підтвердження. Дані станом на 24.07.»

### 2.4. Цінність для замовника

- Відповідь на зведене запитання за секунди замість годин
- Єдине джерело даних
- Кожна цифра має посилання на документи-джерела
- Історія станів зберігається для запитів про минулі періоди

### 2.5. Користувачі

- 100–300 користувачів (керівний склад та персонал підрозділу)
- Доступ із робочих місць у внутрішній мережі та мобільних пристроїв

### 2.6. Типи документів у межах проєкту

- Відпустки (рапорти на відпустку)
- Штатна книжка (авторитетне джерело переліку особового складу)
- Облік техніки (стан і місцезнаходження)
- Відрядження (місцезнаходження людини)
- Грошове забезпечення / бойові виплати (з щоденною фіксацією)

## 3. АРХІТЕКТУРА СИСТЕМИ

### 3.1. Обробка документа

Пʼять етапів:

1. **Завантаження** — людина з відповідним рівнем доступу завантажує файл або фотографію
2. **Розпізнавання тексту** — OCR для сканів і фото, пряме читання для цифрових файлів
3. **Визначення типу документа** — за заголовком, номером бланка або змістом
4. **Витягування даних** — дістання конкретних значень (прізвища, дати, статуси)
5. **Запис результату в базу даних**

На етапі витягування: поля з передбачуваним форматом (дати, номери, кількість) розпізнаються за формальними правилами; довільнотекстові поля обробляє мовна модель.

Принципова умова: якщо якесь значення прочитати впевнено не вдалося, система записує «невідомо» і **не намагається підставити правдоподібне**.

### 3.2. Структура бази даних

Три рівні:

1. **Реєстр документів** — облік кожного завантаженого файлу та його типу
2. **Реєстр обʼєктів** — облік людей, техніки чи інших обʼєктів з історією змін позначень
3. **Факти і стани** — спільна таблиця всіх типів станів: обʼєкт, тип, значення, дати, посилання на документ-джерело

### 3.3. Підтвердження записів

Якщо всі поля документа прочитано впевнено, запис підтверджується автоматично. Записи з позначкою «невідомо» очікують ручної перевірки і **не враховуються в підрахунках**.

### 3.4. Як формується відповідь на запит

Мовна модель не пише запити самостійно. Замість цього:

1. Модель визначає, який шаблон відповідає запитанню
2. Заповнює параметри шаблону значеннями з тексту запитання
3. Звіряє параметри з довідником допустимих значень
4. Якщо жоден шаблон не підходить — повідомляє про це прямо

### 3.5. Етапи, що потребують участі людини

- Рукописні документи автоматично не обробляються
- Документи невизначеного типу йдуть на ручний розгляд
- Непідтверджені записи очікують ручної перевірки
- Випадкова вибірка ~5% уже підтверджених записів додатково перевіряється
- Кожна зведена відповідь супроводжується можливістю ручної перевірки й оскарження

## 4. ВИМОГИ ТА МЕЖІ ДЕМОНСТРАЦІЙНОЇ ВЕРСІЇ

### 4.1. Склад демонстраційної версії

- Вебзастосунок із дашбордом ключових показників і чатботом
- Базовий вхід за логіном
- Обробка документів за конвеєром
- Відповіді за фіксованим набором шаблонів із посиланнями на джерела
- Припущення: вхідні скани й фотографії достатньо якісні для прямого визначення типу за заголовком

### 4.2. Зберігання даних

- Оригінальний файл: 30 днів, потім видаляється
- Розпізнаний текст і витягнуті дані: зберігаються безстроково

### 4.3. Вимоги до безпеки

- **Реальні документи не передаються в жоден хмарний сервіс за жодних обставин**
- Продуктивна система розгортається локально, без підключення до інтернету
- У повній версії: розмежування прав доступу за ролями, мітки рівня доступу, незмінний журнал дій

### 4.4. Поза межами робіт команди розробки

- Офіційна сертифікація системи (атестація КСЗІ)
- Фізичне розміщення серверного обладнання й мережева ізоляція
- Захищений канал для доступу з мобільних пристроїв поза мережею
- Юридична перевірка ліцензійних умов
- Пряма програмна інтеграція з наявними системами (за відсутності API — ручне завантаження)

### 4.5. Модель і серверна інфраструктура

Мовна модель розгортається локально. За замовчуванням розглядається модель з ліцензією, що не обмежує використання. Орієнтовно достатньо одного сервера з однією графічною картою.

## 5. ПИТАННЯ, ЩО ПОТРЕБУЮТЬ УТОЧНЕННЯ ЗАМОВНИКОМ

1. **Модель доступу** — перелік ролей користувачів і обсяг прав для кожної
2. **Рукописні документи** — частота появи й порядок роботи з ними
3. **Структура даних:**
   - Приблизна кількість типів документів і екземплярів
   - Наявність документа зі штатним розписом як авторитетного джерела
   - Наявність стабільного унікального ідентифікатора обʼєкта
   - Можливість одночасного перебування обʼєкта у двох станах одного типу
   - Повторне використання позивних або номерів
   - Дата скасування наказу
   - Уповноважена особа для підтвердження записів

## 6. НАПРЯМКИ ПОДАЛЬШОГО РОЗВИТКУ

### 6.1. Обробка нормативних документів (second brain)

Для правил, інструкцій, порядків, регламентів:

- **Зберігання** — окремий файл із машинночитаною JSON-шапкою
- **Чинність** — система ніколи не позначає документ чинним самостійно
- **Пошук** — знаходить 1–3 документи-кандидати, потім читає обраний повністю
- **Відповідь** — цитата відповідного пункту з джерелом, датою й станом перевірки
- **Маршрутизація запиту** — якщо підпадає під шаблон підрахунку, працює наявний конвеєр; якщо ні — пошук у нормативних документах
- Один документ може водночас давати факти для підрахунку й текст для цитування
- **Курація** — під час завантаження документа

### 6.2. Створення документів за шаблонами

- Користувач формулює текстом, який документ потрібен
- Система добирає шаблон, заповнює поля з відомим значенням, формулює довільнотекстові поля
- Згенерований документ проходить перевірку людиною перед використанням
- Потребує визначення: перелік шаблонів, права доступу, формат вихідного файлу

## ВИНОСКА ЩОДО ТЕХНІЧНИХ ТЕРМІНІВ

| Термін | Пояснення |
|---|---|
| **OCR** | Технологія, що перетворює зображення тексту у текст, придатний для обробки |
| **Мовна модель (LLM)** | Модель, здатна працювати з текстом у довільній формі; застосовується на вузьких ділянках витягування й розбору запитів |
| **PostgreSQL** | Реляційна СУБД з відкритим кодом — безкоштовна й придатна до локального розгортання |
| **Локальне розгортання (self-hosted)** | Програмне забезпечення на власному обладнанні замовника |
| **КСЗІ** | Комплексна система захисту інформації; атестація обовʼязкова для систем, що обробляють інформацію з обмеженим доступом |
| **API** | Програмний інтерфейс для автоматичного обміну даними між програмами |
| **Apache 2.0** | Вільна ліцензія, що дозволяє комерційне використання, зміну й розповсюдження |
