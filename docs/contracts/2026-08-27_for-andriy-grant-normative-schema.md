# Андрію: доступ на читання до схеми `andriy_test` для `milidoc_readonly`

**Від:** Аня (`pipeline/`, `eval/`, апка-завантажувач і чат)
**Дата:** 27.08.2026
**Що потрібно:** одна команда SQL. Нічого не створювати й не змінювати.

## Команда

```sql
GRANT USAGE ON SCHEMA andriy_test TO milidoc_readonly;
GRANT SELECT ON ALL TABLES IN SCHEMA andriy_test TO milidoc_readonly;

-- Щоб не повторювати після кожної нової таблиці:
ALTER DEFAULT PRIVILEGES IN SCHEMA andriy_test
  GRANT SELECT ON TABLES TO milidoc_readonly;
```

Перевірити, що подіяло:

```sql
SET ROLE milidoc_readonly;
SELECT count(*) FROM andriy_test.document_units;   -- очікуємо 12123
RESET ROLE;
```

## Навіщо

Твій ланцюг пошуку по нормативці (одиниці з адресними мітками → реранкер
`bge-reranker-v2-m3` → ворота на моделі по top-2 → перевірки цитати:
входження підрядка + перекриття лем через Hunspell) працює **у твоїй схемі**
`andriy_test`. Чат читає базу під роллю `milidoc_readonly`, і цій ролі схема
`andriy_test` зараз недоступна — тобто ланцюг існує, але чат до нього не
дістає.

З нашого боку все вже написано й лежить у гілці:
`demos/upload_app/chat_gradio/normative_chain.py` — пошук одиниць, реранкер,
ворота, обидві перевірки цитати, з деградацією до наявного FTS-пошуку, якщо
схема недоступна. Не підключений і не протестований рівно через відсутність
доступу.

## Що це відкриває

1. **Відповіді на питання про норми** перестають бути пошуком по всьому
   документу і починають називати адресу («Стаття 26 / 5»), як у твоєму
   ланцюгу.
2. **Метрика «підходящих цитат»** на сторінці статистики. Зараз там прочерк:
   двох інших мірок якості чата ми вже показуємо (правильність числа у
   відповіді й правильність розпізнавання питання), а третьої — саме про
   цитати — немає, бо рахувати її нічим. Твої перевірки цитати (підрядок +
   перекриття лем) і є та мірка.

## Межі, яких ми не переступаємо

- **Тільки `SELECT`.** Запис у схему `andriy_test` нам не потрібен ні зараз,
  ні потім.
- **Ми не створюємо ролей і не видаємо прав самі**, хоча технічно sudo є:
  база — твоя зона (правило від 25.08). Тому це запит, а не зміна.
- Роль `milidoc_readonly` уже існує й уже працює тільки на читання: у
  з'єднанні стоїть `default_transaction_read_only=on`, і це перевірено живим
  прогоном — `INSERT`/`UPDATE`/`DELETE` відхиляються з
  `ReadOnlySqlTransaction`.

## Якщо схема не має бути видною чату

Тоді краще не GRANT, а **вигляд (view) у публічній схемі** з тим, що чату
справді потрібно — одиниці, їхній текст і адресні мітки. Скажи, який варіант
тобі підходить; ми підлаштуємось під твій, а не наполягатимемо на своєму.
