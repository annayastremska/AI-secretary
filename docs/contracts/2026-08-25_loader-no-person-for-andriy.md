# Андрію: документ без особи валить завантаження (41 нормативний акт)

_25.08.2026, від Ані. Одна правка в `airflow/plugins/ai_secretary_loader.py`.
Зона твоя, тому не комітимо тобі в гілку — ось причина, готовий патч і як
перевірити. У нашій гілці правка вже стоїть (коміт `dc3d54f`), тобто це не
пропозиція «спробуй», а те, що ми вже прогнали на всіх 198 документах._

## Коротко

Твій гард document-only ловить два випадки з трьох. Третій — **документ, у
якого особи немає взагалі** — у гард не потрапляє, і на ньому завантажувач
падає. Це весь нормативний корпус: **41 акт із 198 документів**.

Найгірше не саме падіння, а те, як воно виглядає: помилка йде в лог по
одному документу, цикл завантаження продовжується, код виходу нормальний.
Ми це знайшли **не з логу**, а звіркою бази з незалежним підрахунком по
`.md` — у базі було 157 документів замість 198. Тобто без звірки ця
поломка тиха.

## Чому падає — по кроках твого ж коду

`ai_secretary_loader.py`, рядок 553:

```python
person_incomplete = subject.get("person_complete") is False
if meta.get("status") == "unresolved" or person_incomplete:
    ...  # лише документ + review_queue, особу не створюємо
```

Нормативний акт (постанова, наказ МОУ, НД ТЗІ) виглядає так:

```
status: confirmed          # шаблон впізнано, документ у порядку
facts: []                  # фактів про особу немає й не має бути
create_subject_object: false
subject: {}                # ані surname, ані person_alias
```

Отже: `status` не `unresolved`, `person_complete` не `False` (його просто
немає) → **гард не спрацьовує**, і код іде далі, у рядок 563:

```python
person_object_id, is_new_person = get_or_create_person(
    cur, subject.get("surname"), subject.get("given_name"),
    subject.get("patronymic"), document_id,
    person_alias=subject.get("person_alias"))
```

Усі чотири — `None`. Далі в `get_or_create_person`:

1. `canonical = person_alias or " ".join(...)` → **порожній рядок**;
2. `resolve_or_create_object('', 'person', ...)` створює об'єкт-фантом із
   `canonical_name = ''`;
3. `INSERT INTO people (object_id, last_name, ...) VALUES (%s, NULL, ...)`
   → **NotNullViolation на `people.last_name`**, транзакція документа гине.

Тобто навіть якби `NOT NULL` там не стояв, результат був би не кращий: у
реєстрі осіб з'явився б фантом із порожнім ім'ям на кожен нормативний акт.

## Правка

Додати третю умову в той самий гард. Повний фрагмент після правки:

```python
            person_incomplete = subject.get("person_complete") is False
            # Документ БЕЗ особи взагалі: нормативний акт має
            # status=confirmed, facts=[], create_subject_object=false і
            # порожній subject. Попередній гард ловив лише
            # unresolved/person_incomplete, тому такий документ доходив до
            # get_or_create_person із чотирма None і падав на NOT NULL
            # people.last_name -- усі 41 акт не завантажувались.
            # Документ без особи -- законний запис ЛИШЕ в documents: текст
            # для дороги Б (нормативний пошук), без особи й без фактів.
            no_person = not ((subject.get("person_alias") or "").strip()
                             or (subject.get("surname") or "").strip())
            if (meta.get("status") == "unresolved" or person_incomplete
                    or no_person):
                if queue_type:
                    cur.execute(
                        "INSERT INTO review_queue (document_id, queue_type) "
                        "VALUES (%s, %s)",
                        (document_id, queue_type),
                    )
                conn.commit()
                return {"document_id": document_id, "doc_state": doc_state,
                        "already_existed": False, "facts_inserted": []}
```

Дві деталі, які ми обрали свідомо:

- **перевіряємо `person_alias` І `surname`**, а не `create_subject_object`:
  прапорець описує намір пайплайна, а гард мусить дивитись на те, що
  фактично приїхало. Якщо колись прапорець і вміст розійдуться, гард має
  повірити вмісту;
- **`.strip()`**: порожній рядок і рядок із пробілу мусять означати те
  саме, інакше фантом усе одно проліземо.

## Як перевірити, що спрацювало

```bash
# 1. Прогнати нормативний корпус через пайплайн (41 акт, без LLM),
#    якщо виходу під рукою немає:
python run_pipeline.py --input data/eval/samples/normative --no-llm

# 2. Залити у базу і подивитись САМЕ на нормативні:
psql -d milidoc -c "select count(*) from documents where domain = 'normative'"
# мусить бути 41

# 3. Головна перевірка -- фантомів немає:
psql -d milidoc -c "select count(*) from objects where coalesce(canonical_name,'') = ''"
# мусить бути 0

# 4. І що нормативний акт не приніс фактів про особу:
psql -d milidoc -c "
  select count(*) from facts f
  join documents d on d.id = f.source_doc_id
  where d.domain = 'normative'"
# мусить бути 0
```

На живій базі (сервер, `milidoc`) зараз саме так: 198 документів, з них 41
нормативний, фантомів 0. Тобто правка вже перевірена на повному наборі, а
не на одному файлі.

## Чому це важливо саме зараз

Наша гілка й твоя зійдуться. Якщо базу колись заливати **з нуля твоїм
кодом** (чисте розгортання, демо на іншій машині, перезбирання після зміни
схеми) — 41 акт знову зникне молча, а разом із ним **уся дорога Б**:
нормативний пошук працює по `documents.text_content`, тобто без цих 41
документа чат на питання «яка процедура» чесно скаже «не знайшла» і буде
формально правий.

## Ще дві наші правки в тому ж файлі — на твій розсуд

Обидві теж у нашій гілці, теж прогнані:

1. **NUL-байт із PDF** (`f916aa6`, `fcb9cc8`). `pypdf` на НД ТЗІ віддає
   текст із `\x00`, а Postgres `text` його не приймає — документ не
   вставляється. Ми чистимо на спільному виході текстів у пайплайні, і
   **захисно** ще в завантажувачі: `_recognized_text` робить
   `.replace("\x00", "")`. Захисна половина твоя — сміття може приїхати і
   з чужого джерела.
2. **`validity_model` факту** (`bbcc6de`). Ти вже зробив свою половину
   (`9120f78` — брати з факту, а не з локальної копії реєстру), дякую. З
   нашого боку значення їде в **кожному** факті, тобто копію
   `FACT_TYPE_VALIDITY` можна прибрати повністю. Поки вона є, у нас стоїть
   тест-детектор дрейфу (`eval/tests/test_registry_divergence.py`): він
   впаде, якщо копії розійдуться **новим** кодом, а не тим, що вже відомий.
   Прибереш копію — скажи, приберемо детектор.
