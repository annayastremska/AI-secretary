## Раунд звірки на живій базі (24.08, вечір) — 5 розбіжностей розібрано

Корінь шукався по локальній резервній копії 198 записів
(`backups-local/output-demo-2026-08-24.tar.gz`); дзеркало звірки зійшлося з
усіма шістьма контрольними числами етапу 0 (198 документів / 133 особи /
1219 = 25 + 1194 фактів / 152 звання) — тобто очікуваний бік доведено
правильний, і рішення по кожній розбіжності приймалось по конкретному запису.
Коміт: 7a06988.

1. **list_by_state 129→128 (виправлено в шаблонах)**: DEMO-06 = docx
   (фігурний ’) + фото (OCR дав прямий ') → «відпустка у зв'язку з
   навчанням» Приймака Єлисея (29.08–11.09) двома рядками. Ключ дедуплікації
   всіх спискових шаблонів тепер нормалізує гліф апострофа
   (`translate(f.value, '''', '’')`), показане значення — як у документі.
2. **count_by_reason (виправлено рендер, бакети не склеєно)**: гліф-варіанти
   лишаються ДВОМА бакетами навмисно — це знахідка про дані (OCR міняє
   апостроф), її має бути видно. NULL-значення — явний бакет
   «(без значення)» і в SQL, і в дзеркалі.
3. **unconfirmed_count 118/17 ≠ 112/16 (НЕ шаблон)**: SQL — плоский COUNT(*)
   без JOIN-ів, губити факти не може; звірка 0.3 при завантаженні зійшлась
   (118). Отже 6 unconfirmed-фактів одного документа змінили статус у базі
   ПІСЛЯ завантаження. Кандидати з рівно 6: DEMO-07.docx, DEMO-07.pdf,
   BULK-001, BULK-032, BULK-056. Скрипт тепер друкує діагностику по
   файлах-джерелах; на сервері перевірити:
   `SELECT source_doc_id, COUNT(*) FROM facts WHERE status='unconfirmed'
   GROUP BY 1 ORDER BY 2 DESC;` — і хто/коли міняв: `review_log`.
   Той самий дрейф пояснює і відсутній у базі confirmed-факт DEMO-06.png
   (прямий апостроф): при завантаженні він був (1194=1194).
4. **normative_search QueryCanceled (виправлено в шаблоні)**: ранг по
   `left(text_content, 20000)` — свідома межа якості рангу заради швидкості;
   WHERE тепер дослівно повторює вираз GIN-індексу
   (`coalesce(text_content, '')`), без цього індекс не використовувався.
   Таймаут читача не чіпався.

### Додано в «потребує рішення»

- **Дрейф бази після завантаження** (п.3): звірку ганяти одразу після

  зміни в базі, не на шаблон.

## Раунд «реальний формат сліду» (25.08) — коміт dc8aebf

Наживо корекція бакетів count_by_reason не спрацювала: реальний
`review_log.old_value` від dedupe-скрипта — рядок `'дубль фактів [id]'`,
значення злитого факту в review_log немає взагалі. Моя симуляція
перевірялась на описі формату, а не на самому форматі — урок засвоєно і
записано в докстрінги, щоб не повторився.

Переписано без вгадування: вцілілий факт читається з бази через
`rl.fact_id` (значення/статус/особа/дати; old_value із запиту прибрано);
злите значення відновлюється з .md-двійників епізоду (особа + вимір +
період). Розходяться значення (docx ’ проти png ') → бакет невцілілого
значення −1 з явним друком «двійники розходяться значенням: X (вижив, з
бази) проти Y (злито)»; однакові — no-op; кілька файлів одного епізоду —
корекція один раз. Перевірено на копії 198 записів зі слідом у реальному
форматі: усі числа = живій базі. Очікування на переганку: 0 розбіжностей.
