## Що з пам'яті треба ВИПРАВИТИ, а не переносити

**`feedback_dont_over_secure_internal_test_api_keys.md` — шкідливе правило.**
Воно каже: «для внутрішніх тестів вписувати ключ прямо в ноутбук». Саме
такий ключ OpenRouter, вписаний у `llm_testing.ipynb` 08.08, сьогодні знайшло
push protection GitHub при публікації репозиторію — після того, як мій
власний прилад його проґавив. Ключ довелося відкликати. Тобто «низькі ставки»
виявились неправдою: ноутбук потрапив у git, git став публічним.

Правило треба замінити на протилежне: **ключі — лише в `.env` і ніколи в
файлах, які може взяти git**, незалежно від того, наскільки тестовим виглядає
контекст. Зручність запуску вирішується `.env.example`, не вписаним значенням.

## Де це має жити — рекомендація

Claude Code читає інструкції з трьох рівнів, і правило одне: **чим ширше
діє — тим вище лежить.**

| Рівень | Файл | Що туди |
|---|---|---|
| **Глобальний** (усі проєкти) | `~/.claude/CLAUDE.md` | Групи **А, Б** і загальна частина **Г**: стиль відповідей, дозволи, зворотний шлях, чужі зони, тексти без води. Це твої правила як людини, вони не залежать від проєкту |
| **Проєктний** (цей репозиторій) | `CLAUDE.md` у корені | вже є й актуальний. Додати дві речі з групи **В**, яких там немає: «після кожної правки — регресія, після раунду — абляція» і «LLM лише де невизначеність» |
| **Пам'ять** (автоматична, проєктна) | `~/.claude/projects/…/memory/` | лишити як є — це журнал «чому», з датами й цитатами. **Виправити один файл** про ключі |
| **Скіл** | `~/.claude/skills/<name>/SKILL.md` | **не потрібен** для правил поведінки. Скіл — це процедура, яку викликають («зроби мені аудит хардкоду»), а не правило, яке діє завжди. Правила в скілі не читаються, доки скіл не викликано |

**Чому не все в один глобальний файл.** Глобальний `CLAUDE.md` читається на
початку кожної сесії будь-якого проєкту. Туди має іти тільки те, що правда
завжди: «коротко», «питання ≠ дозвіл», «зворотний шлях спершу». Правила про
базу Андрія чи сервер Антона там були б шумом для іншого проєкту.

**Чому не скіли.** Твої вимоги — це не «як зробити X», а «як поводитись
завжди». Скіл спрацьовує лише на виклик. Єдина річ, яка справді могла б бути
скілом, — **аудит хардкоду абляцією** (група В): це повторювана процедура з
кроками й приладом. Але вона вже описана в пам'яті й у `DECISIONS.md`, і
викликається словами; окремий скіл — коли робитимеш це в другому проєкті.

**Чужий скіл `concise-output`** дублює твою групу А англійською й загально.
Після появи глобального `CLAUDE.md` він зайвий: два джерела одного правила —
рівно те, чого ти не любиш.

## Формат глобального файла

Той самий, що вже працює в проєктному `CLAUDE.md`: **правило одним рядком
жирним → чому одним реченням → як застосовувати**. Без цитат (вони в пам'яті),
без історії, українською. Приблизно 60–80 рядків: більше не читається, а
довший файл сам порушує твоє ж правило про воду.

Ключова відмінність від пам'яті: пам'ять пояснює **чому** (з датою й твоєю
фразою), глобальний файл каже **як** (без пояснень). Обидва потрібні, і вони
не дублюють одне одного.

## Що НЕ записувати

- одноразові рішення продукту («рахувати нормативні як confirmed», «прибрати
  метрику 35/35») — це проєкт, воно вже в `DECISIONS.md`;
- те, що вже стоїть у проєктному `CLAUDE.md` — не дублювати в глобальний;
- емоційні маркери самі по собі — вони сигнал повтору, не правило. Правило —
  те, що стоїть за ними.
