### C-02 — `supersession_note` давав `supersedes` зі згадки в тексті [ЗАКРИТО]

Файли: `pipeline/schemas/leave_ticket.yaml`,
`pipeline/schemas/deployment_certificate.yaml`.

**Репро ДО** (LEAVE-001 + один дописаний абзац, повний ланцюг через
`process_file`):

```
'ВПД анульовано, видано нові.'                       confirmed=True  supersedes evidence='анульовано'
'Порядок анульовання квитків визначено інструкцією.' confirmed=True  supersedes evidence='анульовання'
'Відпустка перервана достроково не була.'            confirmed=True  supersedes evidence='перервана'
```

**Фікс:** позначка мусить стояти в ДУЖКАХ і бути окремим словом
(`\((?P<value>[^()]{0,120}?\b(?:…)\b[^()]{0,120}?)\)`). Дужки — не
косметика: на всіх трьох парах еталона позначка надрукована саме в дужках, а
згадка в суцільному тексті — ні. Значенням стає весь вміст дужок, тобто
рев'юер бачить позначку так, як вона надрукована.

**Репро ПІСЛЯ:** усі три штучні випадки — `document_links = []`; справжні пари
лишились:

```
LEAVE-014 supersession_note='перервана, відкликаний з відпустки'         № None
LEAVE-016 supersedes_document_number='157' + note='виданий замість анульованого квитка № 157'
TRIP-014  supersedes_document_number='254' + note='переоформлено замість посвідчення № 254'
```

Лишається відкритим (звужено, не закрито): згадка В ДУЖКАХ усередині
суцільного тексту правило пройде.

### C-03 — реквізити чужого наказу як підтверджені факти [ЗАКРИТО]

Файли: `pipeline/extraction/extract.py` (`extract_field_regex`,
`AMBIGUOUS_MATCH_METHOD`), `pipeline/build_record.py` (raw_text для рев'юера).

**Репро ДО** (LEAVE-001 + «Відповідно до наказу командира № 777/К від
01.01.2020 р.»): `document_number = 777/К` (правильно 102),
`document_date = 2020-01-01` (правильно 2026-05-09), обидва
`method=matched, resolved=True, confidence=0.9`, і обидва доїжджають у
`facts` ОКРЕМИМИ рядками з `confirmed=true`.

**Фікс:** `pattern.search` → `finditer`; більше одного РІЗНОГО збігу одного
варіанта → `None, "ambiguous_multiple_matches:<кандидати>"`. Однакові збіги
неоднозначністю не є. Правило загальне для всіх regex-полів, а не для двох:
«бери перший збіг у документі» ніде не було обґрунтоване, воно дісталось від
`search()`.

**Репро ПІСЛЯ:**

```
document_number  method='ambiguous_multiple_matches:777/К, 102'      resolved=False  raw_text='777/К, 102'
document_date    method='ambiguous_multiple_matches:01 01 2020, 09 05 2026'  resolved=False
facts із source_field document_number/document_date: []
базовий LEAVE-001: номер=102, дата=2026-05-09, confirmed  (без змін)
```

**Регресія:** 226 passed; 224/224; 183/183; нормативний корпус 41/1.

### C-06 — хибний ДОКАЗ порожнечі слота [ЗАКРИТО]

Файли: `pipeline/extraction/blank_form.py` (`printed_skeleton_repeats`,
`MIN_REPEATED_CUTTERS`), `pipeline/extraction/extract.py`
(`empty_proof_allowed` на всіх чотирьох місцях, де оголошується
`confirmed_empty_slot`).

**Репро ДО** (LEAVE-001 + дописаний порожній примірник полів того самого
бланка): `actual_return_date`, значення якого В ДОКУМЕНТІ Є (2026-05-23),
отримує `method='confirmed_empty_slot:empty_pattern'`, тобто «ДОВЕДЕНО, що на
бланку цього немає».

**Чому мінімальна версія з пропозиції не працює:** «скелет порожнечі
збігається більше одного разу» цей випадок НЕ ловить — заміряно, збіг рівно
один (`порожній бланк: 1, LEAVE-001: 0, LEAVE-001 + примірник: 1` на кожному з
чотирьох полів зі скелетом). Дискримінатор інший і без порогу «на око»:
скільки РІЗАКІВ бланка стоять у документі частіше, ніж у самому бланку.
Замір на всіх 34 docx/pdf обох корпусів (включно з порожніми бланками й чужою
редакцією) — надлишок **рівно 0** на кожному; штучний документ із другим
примірником — **25 з 27**. Порівнюється саме з бланком, бо бланк сам друкує
частину рядків двічі (5 із 27 у квитку, 8 із 27 у посвідченні).

**Фікс:** доказ порожнечі (обидва рівні, П5-А і П5-Б) не оголошується, якщо
скелет бланка стоїть у документі двічі АБО якщо форма не впізнана
(`form_recognized=False` — третя частина пропозиції: досі це тримала емпірика
одного файлу, не умова в коді).

**Репро ПІСЛЯ:** те саме поле — `method='ambiguous_label'`, `resolved=False`,
тобто звичайна прогалина з фолбеком, а не доказ. Контроль: LEAVE-011
(справді порожній) зберіг усі 8 `confirmed_empty_slot`; чужа редакція — 0, як
і було.

**Регресія:** 251 passed / 1 xfailed (тести паралельного виконавця вже в
дереві); leave docx 224/224 і pdf 224/224; deployment docx 183/183 і pdf

### A-04 — `normalization` на полях ПІБ мовчки не діяв [ЗАКРИТО]

`extraction: rank_and_name_tokenized` іде власною гілкою `build_record`
(морфологію вибирає `part:`), тож `normalization: nominative_case` там не
читався ніколи. **Фікс:** новий перелік
`EXTRACTION_DISPATCHED_BEFORE_NORMALIZATION` (`rank_and_name_tokenized`,
`derived_from`) → оголошення `normalization` на такому полі стало `error`
валідатора; шість мертвих оголошень прибрано з двох схем (по три на схему) з
коментарем, чому вони були мертві. **ПІСЛЯ:** валідатор ловить оголошення,
чинні схеми — 0 помилок, цифри не змінились.

### C-07 — `consistency` для number-полів [ЗАКРИТО як вимога валідатора]

Заземлення числа перевіряє лише «чи є це число в документі», тому день,
місяць і хвіст номера проходять однаково з правильним значенням; другий шар
(`consistency`) був ЗБІГОМ КОНФІГУРАЦІЇ. **Фікс:** `type: number` без
`consistency` — `error`, якщо поле може прийти від моделі
(`llm_fallback` не `false` і `extraction` не `derived_from`). Автору схеми
лишається реальний вибір: правило узгодженості або `llm_fallback: false`
(відмова краща за вигадку). **ПІСЛЯ:** чинні схеми — 0 помилок; копія схеми
без `consistency` на `duration_days` — error; та сама копія з
`llm_fallback: false` — чисто.
