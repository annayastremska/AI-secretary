## 1. Висновок

**Витік НЕ від Vulkan. На чистій CPU-збірці він той самий: +160 МБ на документ,
монотонно, без повернення.**

| | Vulkan, `-ngl 99` (w6) | CPU, `-ngl 0` (w7) |
|---|---|---|
| приріст пам'яті сервера на документ | +143…166 МБ (RSS) | **+160 МБ (commit)** |
| МБ на 1000 токенів | 27 ± 3 | **~33–36** |
| стартовий слід сервера | 3.21 ГБ RSS | **1.15 ГБ RSS / 2.53 ГБ commit** |
| вільна RAM на старті прогону | 4.30 ГБ | **8.71 ГБ** |
| медіана на документ (той самий прилад) | 93.4 с = **1.56 хв** | **264 с = 4.4 хв** |
| генерація токенів (лог сервера, `tg`) | медіана 16.8 т/с, макс 26.8 | **медіана 8.0 т/с, макс 15.2** |
| `ErrorDeviceLost` | 3 випадки за попередні прогони | **0** |
| `failed to parse grammar` | є (розд. 4.2 того дослідження) | 0 (запасний шлях не викликався) |

**Тобто гіпотеза «витік — це кеш скомпільованих графів/шейдерів Vulkan»
відкидається.** Vulkan лишається причиною *смерті* пристрою
(`vk::ErrorDeviceLost` — рядок є тільки у Vulkan-сегментах логу), але
*накопичення* від бекенда не залежить.

**Переходити на CPU-збірку постійно не варто:** платимо 2.8× швидкості
(4.4 хв/док проти 1.56 хв/док на тому самому приладі) і не отримуємо за це
головного — витік лишається з тим самим нахилом. Єдина реальна вигода CPU —
нижчий стартовий слід (1.15 ГБ проти 3.21 ГБ), тобто пакет доживає до тієї
самої стіни довше. Це не варте 2.8×.

для хв/док беруться і всі 8 (медіана 264 с), і окремо трійка 6–8 при ≥5 ГБ
вільної RAM (медіана 244.5 с). Різниця між ними — 8%, тобто **на CPU швидкість
майже не залежить від вільної RAM**, і це відмінність від Vulkan-прогонів, де
залежність була головним фактором.

## 3. Витік: чому міряний commit, а не RSS

На CPU-збірці **RSS перестає бути мірою накопичення**. Windows під тиском
пам'яті обрізає робочий набір процесу, і RSS падає, поки сторінки просто
переїжджають у своп: у таблиці вище RSS сервера робить 1.73 → 1.15 ГБ між
документами 3 і 4 при вільній RAM 0.15 ГБ. Це не «пам'ять звільнилась».

Тому паралельно писався `commit` (`pagefile` у psutil — зарезервована пам'ять
процесу), `pipeline/scripts/llama_mem_sampler.py`, раз на 30 с. Вікно семплера —
документи 5–8 (той самий сервер pid 75376, ~1000 с):

| сек | RSS, МБ | commit, МБ |
|---:|---:|---:|
| 3 | 1174 | 2528 |
| 333 | 1860 | 2743 |
| 574 | 2072 | 2892 |
| 814 | 2260 | 3033 |
| 994 | 2415 | 3190 |

Commit іде **плато-східцями**: 2528 → 2742 → 2892 → 3032 → 3190. Чотири
східці за чотири документи, **~160 МБ на східець**, жодного повернення. Це
рівно те саме, що заміряно на Vulkan (+143…166 МБ RSS на документ), і рівно те
саме в перерахунку на токени: документи цього прогону дали 5155–6772 токени
(лог сервера, `stop processing: n_tokens`), тобто **~33–36 МБ на 1000 токенів**
проти 27 ± 3 на Vulkan.

Метрики різні (commit проти RSS), тому точну цифру порівнювати не можна; але
питання стояло «зникає чи ні», і відповідь однозначна: **не зникає, нахил той
самий**.

## 4. Побічна знахідка: два прогони Surya ділять ОДИН сервер

Це важливо не для витоку, а для валідності будь-якого майбутнього заміру.

Механізм — у самій Surya, з рядком коду
(`surya/inference/backends/spawn.py`):

```
# 1. Probe sentinel without lock (read-only fast path)
existing = _read_sentinel(backend)
...
logger.info(f"Attaching to existing {backend} server on port {port}")
```

Сентинель — `~/.cache/datalab/surya/llamacpp_server.json`, у ньому порт і pid
уже піднятого сервера. Тобто **другий процес Surya не піднімає свій сервер, а
під'єднується до чужого — з чужим `-ngl`.** Доказ у цьому прогоні: сентинель
після падіння нашого сервера містив `{"port": 62431, "pid": 69212, ...}`, а
командний рядок 69212 — `-ngl 99`.

Наслідок, який треба тримати в голові: **прогін із заданим `-ngl` дійсний лише
тоді, коли на машині немає іншого процесу Surya.** Інакше налаштування
втрачається молча, і в звіті це видно тільки як зміну pid у колонці `llama`
(тому колонка й друкує pid, а не лише суму).

Причину зупинки самого прогону приписувати серверу не можна: у CPU-сегменті
логу **нуль** рядків `ErrorDeviceLost`, `failed to parse grammar`,
`truncated = 1`, `no slot available`. Останній рядок сегмента —
`srv stop: cancel task`, тобто обірвався клієнт, а не сервер.

## 5. Що з цього робити

### Рекомендація: не CPU, а перезапуск сервера за обсягом

Цифра N виведена із заміру, а не вгадана.

* приріст: **0.16 ГБ на документ** (обидва бекенди);
* стартовий слід сервера: 3.21 ГБ (Vulkan) / 1.15 ГБ (CPU);
* заміряна межа виживання: w3 стартував із 1.84 ГБ вільної RAM і вмер на
  5-му документі при ~0.4–0.9 ГБ вільної; w6 стартував із 4.30 ГБ і пройшов
  16/16, закінчивши на 0.64 ГБ.

Звідси бюджет до стіни ≈ `вільна_RAM_на_старті − 1.0 ГБ` (запас, нижче якого
Vulkan уже вмирав), а порог перезапуску:

```
N = (вільна_RAM_на_старті_ГБ − 1.0) / 0.16
```

| вільна RAM на старті | N документів до перезапуску | перевірка на заміряному |
|---|---:|---|
| 1.84 ГБ (w3) | **5** | w3 справді вмер на 5-му |
| 4.30 ГБ (w6) | 20 | w6 пройшов 16/16 без смерті |
| 8.71 ГБ (w7) | 48 | — |

**Ціна перезапуску заміряна тут же: 10.9 с на завантаження моделі** (рядок
`# модель завантажена за 10.9 с` у звіті) — близько 12% часу одного документа
на Vulkan. Тобто на пакеті з 20 документів перезапуск коштує ~0.5 хв, а
перехід на CPU коштував би ~+57 хв.

Точніше рахувати не в документах, а в токенах (документ, що зірвався в цикл
повторів, з'їдає бюджет за трьох — розд. 2 попереднього дослідження): порог
`~ (вільна_RAM_ГБ − 1.0) * 1000 / 0.033` токенів.

**Реалізації тут навмисно немає** — мандат заміру. Пропозиція: лічильник
токенів у нашому шарі + перезапуск за порогом, з логуванням причини.

### Чого цей замір не перевірив

1. **Повних 16 документів на CPU** — дійсних рядків 8. Нахил витоку на 4
   східцях ідеальний, але це 4 точки, не 15.
2. **Чи впаде CPU-збірка взагалі колись.** Смерті пристрою на CPU бути не
   може за визначенням, але інший механізм смерті (OOM самого сервера) на 8
   документах не перевірений.
3. **Що саме тримає ці 160 МБ.** Як і раніше, жодного рядка в логу про це
   немає, тому кандидати (фрагментація KV, буфери mmproj) причиною не
   називаються. Тепер лише відомо, чого це **не** є: не кеш Vulkan.
4. **Реальні бланки** — жодного разу, усе на синтетиці (A8).
