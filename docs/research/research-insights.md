## Чи підходить класичний RAG (пошук за подібністю) для задач агрегації?

**Головний інсайт:** Ні. Звичайний RAG (класифікація/пошук фрагментів за embedding-подібністю + LLM рахує по знайденому) погано справляється саме із задачами типу "скільки/хто" — тобто з головним сценарієм нашого проєкту.

**Примітки/деталі:** Бенчмарк GlobalQA (спеціально створений для задач підрахунку/сортування/екстремумів по всьому корпусу, а не по кількох фрагментах) показав, що найкращий існуючий підхід дав лише 1.51 F1 на задачах підрахунку. Рецензоване дослідження Stanford RegLab показало галюцинації 17-33% навіть у комерційних RAG-систем на реальних професійних запитах.

**Рекомендація:** розділити систему на два шари — (1) класифікація/маршрутизація документів embedding-подібністю (для сортування вхідних документів), (2) відповідь на запит — через структуровану екстракцію полів у базу даних (люди/техніка/місії як таблиці), де підрахунок робить код (SQL), а LLM лише розбирає запит на параметри фільтру і формулює фінальну відповідь. Це прибирає ризик, знайдений бенчмарком.

**Джерела:**
- GlobalQA benchmark (arXiv, 2025) — https://arxiv.org/abs/2510.26205 — препринт, методологічно детальний, ще не рецензований.
- Magesh et al., "Hallucination-Free? Assessing the Reliability of Leading AI Legal Research Tools," Journal of Empirical Legal Studies (2025) — https://onlinelibrary.wiley.com/doi/full/10.1111/jels.12413 — рецензоване дослідження.

## Скільки серверів потрібно для локальної LLM?

**Головний інсайт:** Один централізований сервер — стандартний і рекомендований підхід, поки обрана модель поміщається на одну GPU. Розподілення на кілька серверів виправдане лише для дуже великих моделей (70B+) і додає складність і мережеві затримки.

**Примітки/деталі:** Орієнтовно: 7-14B модель — одна GPU 24-48GB; 70B — 48GB (INT4) чи 80GB+ (fp8/bf16). Якщо LLM використовується мінімально (лише розбір запиту й формулювання відповіді, а не читання великих обсягів документів — див. інсайт вище), потрібна модель і сервер можуть бути суттєво меншими. Головний ризик при низькій частоті запитів (100-300 користувачів, не постійний чат) — переплата за простоюючу GPU, а не брак пропускної здатності.

**Примітка від Validation agent:** джерела описують паралелізм/sizing як технічну документацію, а не пряму нормативну рекомендацію "один сервер — стандарт" — висновок є нашим синтезом, а не прямою цитатою. Не переверифіковано повторно.

**Джерела:**
- vLLM, офіційна документація з паралелізму — https://docs.vllm.ai/en/stable/serving/parallelism_scaling/
- NVIDIA, офіційний гайд з sizing — https://docs.nvidia.com/vgpu/toolkits/fine-tunning-llms/latest/sizing.html
- NVIDIA, системна картка Llama-3.3-70B (вимоги VRAM) — https://build.nvidia.com/meta/llama-3_3-70b-instruct/systemcard

## Наскільки точний OCR для рукописних державних документів?

**Головний інсайт:** Навіть із сучасним AI-OCR потрібна ручна перевірка — повністю автоматична диджиталізація рукописного тексту ненадійна.

**Примітки/деталі:** NARA (перепис населення США 1950) використала AWS Textract для розпізнавання рукописних імен і прямо зазначає, що результат "не 100% точний" через рукописні розчерки — тому поєднали автоматичний OCR із краудсорсинговою людською корекцією. Цифри 95-99% точності з блогів вендорів (Hyperscience, ABBYY, Revolution Data Systems) — маркетинг без незалежного підтвердження, довіряти без власного тестування на реальних типах документів не варто.

**Застереження щодо надійності:** цей інсайт спирається лише на ОДНЕ джерело (нехай і сильне, Tier 1) — за власним правилом agent-pipeline.md (мінімум 2 незалежних джерела рівня 1-2 для статусу "підтверджено") це технічно не досягає планки. Перед тим, як закладати це в остаточний дизайн, варто знайти друге незалежне підтвердження.

**Джерела:**
- NARA, перепис 1950 — https://www.archives.gov/research/census/1950/faqs

## Який метод класифікації документів за відомим набором шаблонів найкращий?

**ВИПРАВЛЕНО після незалежної перевірки (Validation agent виявив об'єднання двох непов'язаних досліджень — див. нижче).**

**Головний інсайт:** Дотренований класифікатор (навіть на 10-100 прикладах/клас) обходить embedding+KNN — це підтверджено ОДНИМ рецензованим дослідженням (ICPR 2024, класифікація типів документів). Твердження "BM25 краще за embedding" НЕ підтверджене — це окреме, нерецензоване дослідження на медичних документах, де BM25 лише ЗРІВНЯВСЯ з embedding-методом (MiniLM), а не переміг його. Попередня версія цього запису помилково об'єднала два дослідження в одне твердження.

**Примітки/деталі:** У контрольованому дослідженні (ICPR 2024) дотренований Mistral-7B+LoRA дав 72.5-83.4% точності при 10-100 прикладах/клас, тоді як embedding+KNN — лише 53-68% за тих самих умов (це саме дослідження BM25 не тестувало взагалі). Окреме нерецензоване дослідження на медичних документах показало BM25 нарівні з семантичним embedding — не як переможця. **Важливо для надійності:** моделі без прикладів (zero-shot) часто повертають невалідну відповідь (17-56% помилок), що різко падає навіть з одним прикладом на клас.

**Рекомендація:** дотренований легкий класифікатор — обґрунтована рекомендація (1 рецензоване джерело). BM25 як альтернатива — не спростовано, але й не доведено кращим за embedding; тестувати обидва.

**Джерела:**
- ICPR 2024, порівняння методів класифікації документів — https://arxiv.org/pdf/2412.13859 — рецензоване.
- Порівняння BM25 vs embedding на медичних документах — https://arxiv.org/html/2505.11582v2 — препринт.

## Наскільки надійна структурована екстракція полів для підрахунку/фільтрації?

**Головний інсайт:** Критичний ризик — LLM-екстрактор може мовчки підставляти "типове" значення замість чесного "невідомо/незрозуміло", навіть якщо в тексті немає підстав для такого висновку. Regex майже ніколи не вигадує значення, але вимагає ручного налаштування під кожне поле і ламається при зміні формату.

**Примітки/деталі:** У дослідженні порівняння regex vs дотренований Qwen2.5-14B на стандартизованому полі точність практично однакова (89.2% vs 87.7%), але LLM систематично уникав відповіді "незрозуміло" — це напряму загрожує точності підрахунку (COUNT/GROUP BY). Для менш стандартизованих/шумних полів LLM, навпаки, суттєво кращий за regex. Структуровані схеми виводу (напр. OpenAI Structured Outputs) гарантують ФОРМУ відповіді (100% валідний JSON), але НЕ гарантують правильність значень — це різні речі.

**Рекомендація:** гібрид — regex/правила для чітко стандартизованих полів (статус, дата), LLM зі структурованою схемою — лише для шумних/вільних полів, з обов'язковим explicit-статусом "невпевнено → на ручний розгляд" замість здогадки. **Застереження:** пряме порівняння такого гібриду саме на військових документах не знайдено — це залишається прогалиною, яку варто закрити власним пілотним тестом, а не подальшим пошуком в інтернеті.

**Джерела:**
- Порівняння regex vs LLM-екстракції (medRxiv, стандартизоване поле) — https://www.medrxiv.org/content/10.1101/2025.06.01.25328636.full.pdf — препринт, надійна методологія.
- OpenAI Structured Outputs (офіційна документація) — https://openai.com/index/introducing-structured-outputs-in-the-api/

## Яка локальна LLM найкраще підходить для української мови?

**Головний інсайт:** Qwen (наш початковий приклад-заглушка) НЕ має підтвердженого дослідження якості на малих розмірах для української мови — лише на найбільшій версії (235B). Натомість сімейство Gemma (і його україномовний варіант MamayLM) має найкраще задокументоване покриття для малих моделей (4-12B) саме на українських задачах.

**Примітки/деталі:** MamayLM (на базі Gemma, INSAIT/ETH Zürich) на 4-12B параметрах, за ЗАЯВОЮ САМИХ РОЗРОБНИКІВ, обходить набагато більші загальні моделі (Gemma2-27B, Llama-3.1-70B, Qwen2.5-72B) на українському шкільному іспиті ЗНО — **незалежна перевірка (Validation agent) підтвердила: це самозаявлений результат без незалежного відтворення, статус — "заявлено вендором, не підтверджено", а не факт.** Дотренований LLaMA-3.2-3B/Gemma-2-9B на ~2000 прикладах українських ЗНО-завдань перевершує GPT-4o-mini (окреме дослідження). Gemma-3-4B дає 100% валідного JSON у задачах структурованого виводу — важливо саме для нашої архітектури. Aya (Cohere) також офіційно заявляє підтримку української, але є нез'ясована згадка про недопредставленість української мови в навчальних даних Aya.

**Рекомендація:** тестувати Gemma-родину (зокрема MamayLM) як основний кандидат замість Qwen; Aya — як другий кандидат для порівняння.

**Джерела:**
- MamayLM, офіційний реліз — https://huggingface.co/blog/INSAIT-Institute/mamaylm
- Дотренування малих моделей на українських задачах — https://arxiv.org/abs/2503.13988 — рецензоване.
- Порівняння function-calling/JSON-виводу малих моделей — https://arxiv.org/pdf/2511.22138

## Який OCR найкращий для українського/кириличного тексту (друкованого й рукописного)?

**Головний інсайт:** Для друкованого тексту — PaddleOCR (94.3% точність на кирилиці, офіційно заявлено). Для рукописного — модель Transkribus "Ukrainian generic handwritten" (4.2-4.57% CER, рецензована публікація) — найкраще задокументований варіант, набагато кращий за загальні кириличні TrOCR-моделі (~25% CER).

## Як організувати контроль доступу та аудит-лог для класифікованої системи?

**Головний інсайт:** Міжнародна практика (NIST RBAC, СNSSI 1253) і українські НД ТЗІ повністю узгоджуються: ролі за принципом мінімально необхідного доступу + класифікаційні мітки/грифи поверх ролей + обов'язковий захищений від підробки аудит-лог (хто/що/коли/результат).

**Примітки/деталі:** Український НД ТЗІ 2.5-005-99 класифікує автоматизовані системи (актуально для атестації нашої 100-300-користувацької системи), а НД ТЗІ 2.5-004-99 прямо вимагає "реєстрацію (аудит)" як окрему сертифіковану функціональну послугу — це напряму пов'язано з вимогою атестації КСЗІ, вже зафіксованою в security-constraints.md. Найкраща практика для самого логу — WORM-зберігання + криптографічне хеш-ланцюжкування (щоб будь-яка підробка була математично видимою) і розділення повноважень (той, хто пише лог, не може його видаляти).

**Джерела:**
- НД ТЗІ 2.5-005-99 — https://tzi.ua/assets/files/%D0%9D%D0%94-%D0%A2%D0%97%D0%86-2.5-005--99.pdf
- НД ТЗІ 2.5-004-99 — https://tzi.com.ua/downloads/2.5-004-99.pdf
- CNSSI No. 1253 (US, аналогічний стандарт для класифікованих систем) — https://rmf.org/wp-content/uploads/2022/10/CNSSI_1253_2022.pdf

## Ліцензії кандидатів на локальну LLM — чи справді безкоштовні для нашого використання?

**Головний інсайт:** НІ, не всі однаково вільні. Aya (Cohere) — CC-BY-NC, **виключно некомерційне використання**, для державної/військової частини це реальна блокуюча умова без окремої угоди з Cohere. Gemma/MamayLM — власні "Gemma Terms of Use" (не чистий opensource, Google лишає за собою право змінювати/припиняти умови), дозволяє комерційне використання, але не так чисто, як Apache 2.0. Qwen (моделі <35B) і Mistral 7B — Apache 2.0, найчистіша ліцензія, без обмежень.

**Примітки/деталі:** Це змінює попередню рекомендацію — MamayLM лишається лідером за якістю української мови, але Qwen/Mistral мають кращу ліцензійну чистоту. Це реальний trade-off, не однозначна відповідь: якість vs. чистота ліцензії. Aya виключається з розгляду, доки не підтверджено окремий дозвіл від Cohere.

## Чи є прецеденти впровадження AI в документообіг поза військовою сферою — і які уроки?

**Головний інсайт:** Найважливіший повторюваний патерн провалів — коли вихід класифікатора/AI-системи почали сприймати як остаточну істину без незалежної перевірки чи механізму оскарження, і помилки накопичувались непомітно у важливих агрегованих рішеннях.

**Примітки/деталі:** Приклади: скандал з дитячими виплатами в Нідерландах (класифікатор помилково звинуватив ~26,000 родин у шахрайстві, офіційне розслідування уряду підтвердило дискримінаційні змінні у моделі); скандал Post Office Horizon у Великій Британії (~20 років довіри системі всупереч запереченням людей, 900+ неправомірних судових переслідувань); IBM Watson for Oncology (згорнуто після ~$62M, небезпечні рекомендації через нерепрезентативні дані для навчання). Окреме дослідження (arXiv) показало, що помилки класифікації переходять в агреговані підрахунки НЕ випадково, а систематично (напрямлено) — тобто підрахунки типу "скільки людей у статусі Х" можуть бути стабільно завищені/занижені, а не просто "трохи неточні". Позитивний приклад: технологічно-асистований огляд документів (TAR) в e-discovery дав 76-77% recall проти ~60% у ручного перегляду (рецензоване дослідження) — AI-допомога працює, коли є методологія й перевірка.

**Рекомендація:** обов'язковий шлях ручного перегляду/оскарження для агрегованих відповідей, періодична перевірка класифікатора на систематичну похибку, не сприймати вихід системи як остаточну істину.

**Джерела:**

- Post Office Horizon — https://www.economicsobservatory.com/trust-and-technology-what-went-wrong-with-the-post-office
- IBM Watson for Oncology — https://www.statnews.com/2018/07/25/ibm-watson-recommended-unsafe-incorrect-treatments/

## Чи існує готовий фреймворк для всього конвеєра (OCR+класифікація+екстракція+БД), чи потрібно збирати з нуля?

**Головний інсайт:** Жоден готовий фреймворк не покриває весь конвеєр одразу. Але **Paperless-ngx** (реальний opensource-проєкт) — готовий прецедент, що вже поєднує легкий класифікатор (офіційна документація описує його лише як "нейромережа під капотом" — не TF-IDF, як помилково зазначалось раніше) + опціональну LLM-екстракцію — можливо, варто оцінити як основу замість повністю власної розробки.

**Примітки/деталі:** Docling має ПІДТВЕРДЖЕНО зламану кириличну підтримку (відкритий issue на GitHub) — уникати для нашого випадку. Haystack підтримує класифікацію за довільними власними категоріями офлайн — корисний будівельний блок. Для бази даних: уникати EAV-схеми (погана для агрегації), використовувати типізовані колонки + JSONB для рідкісних полів, патерн SCD Type 2 чи темпоральні таблиці для історії змін статусу, окрема колонка впевненості (confidence score) + проміжна "чернеткова" таблиця для непевних записів перед підтвердженням.

**Джерела:**
- Paperless-ngx, документація — https://docs.paperless-ngx.com/advanced_usage/
- Docling, відкритий issue про кирилицю — https://github.com/docling-project/docling/issues/3433
- EAV — погана практика для агрегації (PostgreSQL) — https://www.cybertec-postgresql.com/en/entity-attribute-value-eav-design-in-postgresql-dont-do-it/

## Скільки реально коштуватиме залізо?

**Головний інсайт:** Повноцінний робочий сервер під невелику локальну модель (4-9B) на одній GPU 16GB — орієнтовно $1,500-2,200 (реальні ціни компонентів, не абстрактна оцінка). Усе програмне забезпечення в рекомендованому стеку (PaddleOCR, PyLaia, Qwen/Gemma, PostgreSQL) — безкоштовне з відкритим кодом.

**Примітки/деталі:** RTX 4060 Ti 16GB — $300-425 (реальні ціни). RTX 4090/3090 (24GB, для більших моделей) — суттєво дорожче ($1,200-2,800) і, ймовірно, не потрібні при вибраній архітектурі з малою моделлю.
