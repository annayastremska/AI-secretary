# Вибір embedding-моделі для дороги Б

Дата: 2026-08-08

**Рішення відкладене — модель не фіксуємо зараз.**
**Векторний пошук підключаємо тільки якщо повнотекстовий пошук (FTS) не витягне на реальному корпусі.**
**Наступний крок — не вибір моделі, а eval FTS.**

Далі в тексті ці слова трапляються постійно. Пояснення тут, у тексті вже без розшифровки.

| Слово | Що означає |
|---|---|
| **Embedding (ембеддинг)** | Спосіб перетворити текст на набір чисел так, щоб близькі за змістом тексти дали близькі числа. Завдяки цьому «вайфай не пускає» знаходить документ, де написано «бездротова мережа» |
| **Embedding-модель, ембеддер** | Програма, яка це перетворення робить. Окрема від тієї моделі, що пише відповіді |
| **Retrieval (пошук)** | Знайти потрібний документ серед усіх. Не відповідь скласти, а саме знайти, звідки її брати |
| **Dense-вектор** | Той самий набір чисел фіксованої довжини. «Щільний» — бо всі числа заповнені. Стандартний, найпростіший формат |
| **Розмірність вектора** | Скільки чисел у наборі. У наших кандидатів 1024. Менше — індекс легший і швидший |
| **pgvector** | Розширення PostgreSQL, яке вміє зберігати ці числа і шукати схожі. Окрема база не потрібна |
| **FTS, повнотекстовий пошук** | Звичайний пошук по словах, який PostgreSQL уміє сам. Дешевий, але не бачить синонімів |
| **HNSW, IVFFlat** | Два способи побудувати індекс, щоб пошук серед векторів був швидким. Обидва мають ліміт 2000 чисел на вектор |
| **R@1, R@3 (Recall@1, Recall@3)** | Мірило якості пошуку. R@1 — як часто правильний документ виявився першим. R@3 — як часто він у трьох перших. Більше = краще |
| **Бенчмарк** | Набір питань із заздалегідь відомими правильними відповідями. На ньому міряють моделі |
| **Ablation** | Перевірка «а що буде, якщо цю деталь прибрати». Так знаходять, яка частина системи справді працює |
| **Файнтюн (fine-tune)** | Донавчання готової моделі під свої дані. Дорого і довго; ми цього не робимо |
| **Reranker** | Друга модель, яка перебирає знайдене і переставляє в правильному порядку. Вмикається після пошуку |
| **Контекст (у токенах)** | Скільки тексту модель здатна прочитати за раз. Наш розділ наказу має влізти цілком |
| **Токен** | Шматок тексту, яким модель рахує довжину. Приблизно склад або коротке слово. Кирилиця дорожча за латиницю |
| **Footprint** | Скільки місця на диску і памʼяті модель займає під час роботи |
| **CPU / GPU / VRAM** | Звичайний процесор / відеокарта / памʼять відеокарти |
| **Квантизація (INT8, Q8, fp16)** | Стиснення моделі: числа зберігаються грубіше, модель важить менше і працює швидше, якість падає трохи |
| **ONNX, GGUF** | Формати, у яких модель запаковують для швидкого запуску. GGUF розуміє Ollama |
| **Ollama** | Програма, яка запускає моделі локально однією командою. У нас на ній уже стоїть генеративна модель |
| **sentence-transformers** | Стандартна бібліотека Python для ембеддерів. «Працює з коробки» означає саме через неї |
| **MRL (Matryoshka)** | Прийом, який дозволяє обрізати вектор до коротшого без переучування моделі |
| **RoPE** | Технічний прийом, завдяки якому модель може прочитати більше тексту, ніж її вчили. Здатність є, але не тренована |
| **trust_remote_code** | Модель при завантаженні виконує чужий код. Для закритого контуру — ризик |
| **Decoder-only** | Тип моделі, яка вміє писати текст, але не вміє робити ембеддинги. Саме тому ембеддер завжди окремий |

## Вердикт

Якщо векторний шар знадобиться — беремо **`snowflake-arctic-embed-l-v2.0`**.

Підстави:

1. Перша в єдиному знайденому прямому порівнянні ембеддерів на українських
   retrieval-задачах, з найбільшим відривом саме на QA-по-документах — найближчому
   до нашого сценарію.
2. Apache 2.0 без застережень. Замовник — військова частина, ліцензія з
   use restrictions означає юридичне тертя в договорах.
3. Контекст 8192 токени → чанкувати можна цілим розділом наказу.
4. Звичайний 1024-dim dense-вектор, `sentence-transformers` і ONNX працюють без
   обхідних шляхів. MRL-трункація до 256 як запас, якщо HNSW треба буде прискорити.

**План Б: `multilingual-e5-small`**, якщо CPU-інференс виявиться болючим. 118M і
384 dim реально живуть на CPU, і модель уже показала себе на українській.
Оскільки весь векторний шар — fallback за FTS, індексацію можна ганяти офлайн,
де швидкість некритична.

**Рівноцінна заміна: `bge-m3`**, якщо захочеться hybrid dense+sparse в одній
моделі або максимальна сумісність із `bge-reranker-v2-m3`.

**Reranker, якщо дійде до нього: `bge-reranker-v2-m3`** — найкращий в обох
українських роботах, і саме він у системи, що взяла 2-ге місце UNLP 2026.

**Ціна помилки низька.** У Arctic і BGE-M3 однакова розмірність (1024), однакова
вага (568M), обидві проходять по ліцензії, обидві є в офіційній бібліотеці Ollama.
Заміна одної на іншу — це переіндексація десятків документів, не переробка системи.

## Жорсткі вимоги, з яких виходили

- Повністю self-hosted, без інтернету, без хмарних API. HuggingFace /
  `sentence-transformers` / ONNX — так. Будь-який embeddings-API — ні.
- Прод — один сервер з однією відеокартою. Дев-машина зараз **без GPU**, тестуємо на CPU.
- Генеративна модель (MamayLM-Gemma-3-12B через Ollama) — decoder-only, embedding-режиму
  не має. Embedding-модель — завжди окрема модель.
- Дорога А (факти → Postgres → SQL) embeddings не потребує взагалі. Це питання
  стосується тільки дороги Б.

## Головні дані: пряме порівняння на українській

Nosenko & Kilko, «RAG Pipeline Strategies for Ukrainian Multi-Domain Document
Understanding Task», UNLP 2026, 3-тє місце — https://aclanthology.org/2026.unlp-1.21/

Єдине знайдене пряме порівняння шести ембеддерів на трьох українських
retrieval-задачах. Recall@1 / Recall@3, %:

| Модель | Belebele-uk | WebFAQ-uk | UNLP-QA |
|---|---|---|---|
| **Arctic-Embed-L-v2.0** | 87.33 / 94.89 | **71.71 / 83.73** | **65.18 / 80.57** |
| Multilingual-E5-Large | **90.44 / 97.44** | 71.04 / 82.67 | 61.34 / 78.75 |
| BGE-M3 | 88.00 / 95.67 | 69.26 / 81.39 | 61.34 / 78.34 |
| Jina-Embed-v5-small | 88.78 / 95.56 | 68.62 / 81.00 | 59.11 / 78.14 |
| Qwen3-Embedding-0.6B | 82.67 / 92.11 | 61.19 / 73.80 | 53.44 / 72.27 |
| Octen-Embedding-0.6B | 82.44 / 92.33 | 62.17 / 74.34 | 54.25 / 74.09 |

Числа звірені з PDF статті — збігаються точно. Кандидати автори брали з
Multilingual RTEB leaderboard (моделі до 2B параметрів), залізо — один
RTX 5060 Ti 16 GB. У фінальну систему взяли Arctic-Embed-L-v2.0.

**Відрив Arctic скромніший, ніж виглядає з першого рядка:** +3.84 R@1 на UNLP-QA,
+2.45 на WebFAQ, −0.67 на Belebele. Це один бенчмарк однієї команди, і з reranker
розрив стискається.

Побічні висновки з їхніх ablations:

- чанк на цілу сторінку кращий за дрібні чанки — **але тут є артефакт метрики:**
  у датасеті організаторів відповідь завжди лежить на одній сторінці;
- чистий dense побив hybrid (dense + BM25) на цьому датасеті;
- найкращий reranker — `bge-reranker-v2-m3` (Accuracy_doc 99.78).

### Відсіяні й чому

| Модель | Причина |
|---|---|
| Qwen3-Embedding-0.6B | Найслабша в UA-порівнянні (53.44 R@1 на UNLP-QA проти 65.18 в Arctic), попри Apache 2.0 і 32K контексту |
| gte-multilingual-base | Провал на українській: 0.6074 doc-id, гірше за character TF-IDF. Плюс `trust_remote_code=True` |
| jina-embeddings-v3 / v5-small | **CC-BY-NC-4.0** — комерційне і державне використання потребує окремої ліцензії від Jina. Не проходить по вимозі |
| EmbeddingGemma-300m | Ліцензія **Gemma Terms of Use** — кастомна, з use restrictions, які треба протягувати в договори. Публічних українських замірів немає. Плюс дослівно в model card: «activations do not support float16» |
| LaBSE | Модель для bitext mining (пошук перекладних пар), не для семантичного retrieval. У жодному українському замірі не фігурує |
| lang-uk/ukr-paraphrase-multilingual-mpnet-base | Єдиний знайдений український fine-tune (Apache 2.0, 768 dim, UNLP 2023). Тюнилась під word sense disambiguation, не під retrieval, retrieval-бенчмарків немає. `max_seq_length: 128` — два абзаци, не розділ. База (paraphrase-mpnet, 2021) застаріла |

**Українських спеціалізованих ембеддерів для retrieval фактично не існує.**
У спільнотах lang-uk і awesome-ukrainian-nlp свіжіших немає. Жодна з трьох робіт
UNLP 2026 не використала UA-специфічний ембеддер — нішу закрили мультимовні моделі.

## Головний ризик: контекст Arctic

Контекст 8192 у model card підтверджений, **але файнтюн моделі йшов на 512 токенах.**
8192 — успадкована через RoPE здатність від `bge-m3-retromae`, увімкнена лише на
оцінці (стаття Arctic 2.0, https://arxiv.org/abs/2412.04506). BGE-M3 натомість
тренована під довгі документи.

Для нас це прямо в ціль: одиниця індексу — цілий розділ наказу, тобто саме той
режим, у якому Arctic не тренувалась.

Контраргумент є: на довгодоковому CLEF Arctic бʼє BGE-M3 (54.3 проти 41.3 nDCG).
Але це бенчмарк самого Snowflake, тобто вендорський.

Це причина, чому вердикт вище не є остаточним фіксованим вибором.

### Розбір: що насправді в референсній роботі

Trokhymovych, Oliinyk, Nyzhnyk, «An End-to-End Ukrainian RAG for Local Deployment»,
UNLP 2026, 2-ге місце — https://arxiv.org/html/2604.22095v1

| Роль | Модель |
|---|---|
| Ембеддер (dense, doc + page level) | `pplx-embed-context-v1-0.6b` (Perplexity, MIT) |
| Лексичний пошук | BM25Okapi + українська лематизація + стоп-слова |
| Fusion | RRF |
| Reranker (document level) | `jina-reranker-v3` |
| Reranker (page level, top-8) | кастомний cross-encoder на базі `BAAI/bge-reranker-v2-m3` |
| Генерація | MamayLM-12B, LoRA, 4-bit GGUF |

Чанкінг: синтаксичний по Markdown-структурі, до 500 символів, 10% overlap, у межах
однієї сторінки. Залізо — одна P100, ліміт 9 годин на інференс. Метрики: page-level
recall@3 = 0.92 на dev, фінальний скор 0.942 на приватному тесті. Розмірність вектора
в статті не вказана.

**Звідки взялась плутанина:** у статті є `bge-reranker-v2-m3`, але це інший чекпоінт —
cross-encoder для реранкінгу, не BGE-M3 як ембеддер.

## Чого досі бракує

1. **Жодного виміру на власному корпусі.** Усі докази — з чужих бенчмарків, де
   одиниця індексу сторінка або пасаж, а не цілий розділ наказу.
2. **Поведінка на розділах довше ~500 токенів** — головний непокритий ризик Arctic.
   Публічних даних на українських довгих текстах немає ні в кого.
3. **Терміни поза загальними даними** (АСКОД, СЕДО, ВЛК, «Армія+») — у бенчмарках їх
   немає. Ризик частково знімає архітектура: лексику ловить FTS, переформулювання
   робить генеративна модель.
4. **Швидкість на CPU** — публічних чисел немає для жодної з трьох моделей.
5. **Якість запитів після переформулювання.** Від неї залежить, чи взагалі
   знадобиться векторний шар.

## Що потрібно від команди

**Власний тест на нашому корпусі.** Це єдине, що закриває пункт 1 і пункт 2 з
«чого досі бракує», і без нього вердикт лишається на чужих бенчмарках.

Що зробити:

- 20–30 реальних питань **розмовною українською** — так, як їх ставить людина,
  не так, як написано в наказі
- Еталон до кожного — конкретний **розділ наказу або інструкції**, а не сторінка
  і не абзац. Одиниця індексу в нас саме розділ
- Прогнати Arctic проти BGE-M3, порівняти R@3

Оцінка: день роботи.

**Хто це робить — не призначено.** Питання й еталони — це контент, а прогін і
підрахунок R@3 — інфраструктура, тож задача лягає між ділянками. Власника
визначає Денис.

Той самий набір потім працює як eval для FTS, тобто робота не пропаде, навіть
якщо векторний шар не знадобиться.
