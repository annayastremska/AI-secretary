# Чи страшно писати свій харнес: що каже галузь

_24.08.2026, на запит Ані («мене турбує, що ми самі пишемо свій харнес»).
Третє дослідження серії: перше — наші харнеси (Коля), друге — готові чужі
(`2026-08-24_chat-harness-options.md`), це — як галузь радить будувати власні
й чи наш дизайн цим порадам відповідає._

## 0. Головний висновок

Занепокоєння «пишемо своє» спирається на хибне уявлення, що своє — це
відхилення від норми. **Норма якраз протилежна.** Два найавторитетніші
джерела з побудови LLM-систем кажуть одне й те саме:

- **Anthropic, «Building Effective Agents»**: «найуспішніші реалізації не
  використовували складні фреймворки — вони будувались із простих
  композованих патернів»; фреймворки «додають шари абстракції, які
  приховують промпти й відповіді». Починати з **workflow** (наперед
  визначені шляхи коду), а не з «агента»; **routing — один із п'яти
  канонічних патернів** — і це дослівно наш дизайн;
- **12-Factor Agents** (HumanLayer, найпопулярніший практичний гайд на
  GitHub): «own your prompts», «own your context window», «own your control
  flow» — тобто володій промптами, контекстом і потоком керування сам, а
  «tools are structured outputs»: модель видає структуру, виконує код.

Тобто те, що ми робимо, називається не «свій харнес із нуля», а **канонічний
routing-workflow зі ~100 рядками клею** — і саме це галузь рекомендує для
задач нашого масштабу. Фреймворк тут не знімає роботу, а замінює клей
адаптерами того самого розміру плюс шар абстракції.

## 1. Наш дизайн проти чек-листа 12-Factor Agents

Це і є «врахуємо»: аудит нашого плану проти галузевого чек-листа.

| фактор (12-Factor Agents) | наш стан |
|---|---|
| 1. Natural language → tool calls | ✓ питання → вибір шаблону + слоти (структура, не текст) |
| 2. **Own your prompts** | ✓ промпт фолбека — наш код у репо, не надра фреймворку |
| 3. **Own your context window** | ✓ план 4.3: останні N ходів + розв'язані слоти, не вся історія |
| 4. **Tools are structured outputs** | ✓ ядро дизайну: модель видає JSON під GBNF, SQL виконує код |
| 5. Unify execution & business state | ✓ журнал відповідей (5.5): питання, маршрут, шаблон, параметри, час |
| 6. Launch/pause/resume APIs | — не потрібно: діалог 1–3 ходи, не довгі процеси |
| 7. Contact humans with tool calls | ~ наш аналог: вихід гейта «уточнення» (5.3) |
| 8. **Own your control flow** | ✓ явний гейт із 4 виходами, жодного чорного ящика |
| 9. Compact errors into context | ~ збій моделі → чесна відмова (llm_error), без ретраїв — свідомо: 43 с/спроба |
| 10. **Small, focused agents** | ✓ рівно одна задача моделі: «який шаблон і що змінилось» |
| 11. Trigger from anywhere | — не потрібно для демо (один вхід — апка) |
| 12. Stateless reducer | ✓ відповідь = f(питання, слоти, база); слоти — явний стан у сесії |

**9 із 12 виконано дизайном, 3 непотрібні для нашого масштабу.** Жоден пункт
не вимагає фреймворку.

## 2. Ландшафт фреймворків, яких не було в другому дослідженні

Перевірив і клас «агентних» фреймворків — раптом там готовий чат-харнес:

| фреймворк | що це | чому не для нас |
|---|---|---|
| **PydanticAI** (творці Pydantic) | типобезпечні агенти, валідований вивід | будований навколо API провайдерів; llama.cpp — лише через OpenAI-сумісний сервер = ще один процес; вивід валідує те, що наш GBNF **гарантує** на рівні генерації |
| **smolagents** (HuggingFace) | модель пише **код**, код виконується | пряме порушення нашої гарантії (модель не пише ні SQL, ні код) + вимагає пісочниці |
| **LangGraph** | графи станів, пауза/відновлення | уже розглянуто: для діалогу на 1–3 ходи — надлишок (план, розд. 0) |
| **llama-cpp-agent** | структурований вивід + function calling прямо на llama-cpp-python через GGML-BNF | найближчий за механікою — але це малий проєкт, який робить рівно те, що наш перевірений `pipeline/llm/client.py` уже робить на 198 документах |
| **instructor** | ретраї + валідація структурованого виводу, є інтеграція з llama-cpp | ретрай на 27B/CPU = +43 с за спробу; наш GBNF робить невалідний вивід неможливим замість «перепитати» |

Спільний висновок по класу: усі вони розв'язують задачу «дати моделі
інструменти й цикл» — а в нас цикл на один крок і один інструмент (вибір
шаблону). Брати фреймворк заради цього — те, від чого Anthropic прямо
застерігає.

## 3. Що з найкращих практик беремо додатково

Три речі, які дослідження додає до плану (дрібні, але названі):

1. **Промпт фолбека — окремим файлом у репо** з коментарем-обґрунтуванням
   (фактор 2): щоб його можна було читати й правити як код, а не шукати в
   рядках. У пайплайні так уже зроблено (`llm_context/`) — чат робить так само.
2. **Свідома відмова від ретраїв** (фактор 9) — записати як рішення: на GPU
   ретрай безкоштовний і його варто ввімкнути, на CPU він коштує 43 с; GBNF
   робить головну причину ретраїв (невалідну структуру) неможливою.
3. **Формулювання для презентації**: наш харнес — це routing-workflow за
   Anthropic-класифікацією, 9/12 факторів галузевого чек-листа, готові
   компоненти там, де вони існують (semantic-router, GBNF, парсери), і ~100
   рядків власного клею, який довелося б писати з будь-яким фреймворком.

## 4. Чесні межі цього дослідження

- джерела — інженерні гайди й документація, не незалежні бенчмарки;
- «9 із 12» — самооцінка проти чек-листа, а не зовнішній аудит; частина
  пунктів стане перевірною лише коли чат зберуть (етапи 3–5 плану);
- фреймворки оцінені за документацією, не прогоном — як і в другому
  дослідженні, страховка та сама: тест-сет не залежить від вибору.
