## 0. Навіщо цей звіт

Корпус збирали 14 агентів, кожен по своєму типу. Кожен написав собі `README.md` і
`MANIFEST.md`. Проблема: **звіт писав той самий агент, що збирав** — тобто це
самооцінка, а не перевірка. Далі на цьому корпусі стоїть pipeline автовитягу, і якщо
на вході «148 придатних файлів», а насправді 147 з іншим складом — pipeline тихо
пропустить документи.

Тому корпус переміряно **незалежно від README**: кожен файл відкрито утилітами,
жодне число не взяте зі звіту агента. Нижче — що маємо, що зʼясували, чого немає,
що доробити.

**Методика перевірки** — у розділі 7. Її наведено спеціально, щоб команда могла
повторити перевірку самостійно й не вірити на слово вже цьому звіту.

## 2. Що зʼясували — придатність до автовитягу

Тут головна поправка звіту. Заявлена цифра «148 файлів із текстовим шаром» —
завищена, і завищена не через недбалість, а через тонкий технічний ефект.

### 2.1 Мохібейк: 6 файлів, які виглядають придатними, але не є

`pdftotext` на цих файлах **повертає текст** — тому будь-яка автоматична перевірка
«є текстовий шар?» скаже «є». Але це не текст: у PDF гліфи змаповані без таблиці
`ToUnicode`, тобто шрифт малює українські літери, а всередині файлу лежать зовсім
інші коди. Частка кирилиці в отриманому «тексті» — **рівно 0.0 %**.

| файл | тип | що видає `pdftotext` |
|---|---|---|
| `01-…-016.pdf` | 01 | `ɇȺɐȱɈɇȺɅɖɇȺȽȼȺɊȾȱə…` |
| `02-nakaz-bojovyj-014.pdf` | 02 | `ÎÓÍ ³ ÓÏÀ â…` (титул чистий, тіло — ні) |
| `03-rozporyadzhennya-003.pdf` | 03 | `3ArropI3bKA pafronHa AEexABHA…` |
| `10-sluzhbova-zapyska-010.pdf` | 10 | `YnonHoBaxenifi oco6i uy6niqHzx…` |
| `12-vytyag-006.pdf` | 12 | `MIHICTEPCTBO OEOPOHI,I YKPAIHI4…` |
| `14-dovidka-008.pdf` | 14 | `yI{PAiIJA TOAI"IIbCI,K,\ PAJIOI{HA…` |

**Наслідок:** ці 6 файлів треба вести як скани — через OCR (або через ручну таблицю
перекодування, що дорожче й крихкіше).

Два з шести мають супутній `-DECODED.txt`, тобто хтось уже намагався розкодувати:
- `02-014-DECODED.txt` — розкодовано **чисто** ✅
- `01-016-DECODED.txt` — розкодовано **частково**: мохібейк лишився в тексті
  (`КИЇVɋьКИɃІНɋɌИɌУɌ`). Файл виглядає готовим, але не готовий ⚠️
- решта чотирьох таблиці перекодування не мають узагалі

### 2.2 Виправлені числа

| | файлів | унікальних після дедуплікації |
|---|---|---|
| **придатні до автовитягу** | **147** | **132** |
| **потребують OCR** | **28** | **28** |
| md-виписки (не документи) | 68 | 68 |
| **разом** | 243 | 228 |

Склад «придатних до автовитягу, 147»: 132 чистих PDF + 10 `.docx` + 2 `.doc` + 3 `.txt`.
Склад «потребують OCR, 28»: 21 скан-PDF + 6 мохібейк-PDF + 1 `.png`.

### 2.3 Окремий випадок: шумний OCR-шар

`11-sluzhbovyj-lyst-012.pdf` (48 МБ, 30 стор.) — текст витягується, але це вже
OCR-ений скан невисокої якості: **3,4 % кирилічних токенів містять латиницю
всередині слова** (`35 і-49-20`, `Фако те.п..`, `Мітстерстао оЬоронн`).

Формально придатний до автовитягу. Практично: витягувати можна, **вірити реквізитам
не можна** — номер, дата, ПІБ у такому шарі спотворюються систематично. У pipeline
його треба або переOCR-ити, або промаркувати як low-confidence.

Решта корпусу за цією метрикою чиста: у всіх інших файлах частка змішаних токенів
≤ 1 %, що є нормою (латинські абревіатури, URL, номери).

### 2.4 Поділ text / scan виявився надійним

Це важливо для довіри до цифр. Порогова величина — 100 знаків на сторінку. Фактичний
розподіл не має сірої зони:

- **усі 21 скан** віддають **рівно 0 символів** — не «мало», а нуль
- **найбідніший файл із текстовим шаром** — 103,5 знака/сторінку
  (`03-rozporyadzhennya-blank-001.pdf`, порожній бланк — там і має бути мало тексту)

Тобто класифікація не «висить» на порозі: якби ми взяли поріг 10 або 500 — числа
не змінилися б.

### 5.1 Типи 02 і 04 фактично дублюють один одного

Це не косметика, а змістовна проблема покриття.

**З 12 файлів типу 04 «Бойове розпорядження», що мають текстовий шар, вісім — це
байт-у-байт копії файлів типу 02 «Наказ бойовий».**

```
04-…-001 = 02-…-016      04-…-006 = 02-…-006
04-…-003 = 02-…-001      04-…-007 = 02-…-007
04-…-004 = 02-…-002      04-…-008 = 02-…-005
04-…-005 = 02-…-004      04-…-009 = 02-…-017
```

Тобто тип 04 на дві третини складається з документів іншого типу. Реально своїх
документів у типі 04 — чотири, а не дванадцять. Обидва README рапортують повне
покриття незалежно один від одного.

**Що з цим робити — рішення команди.** Дублікат може бути легітимним: один документ
іноді містить і наказ, і бойове розпорядження, тож обидва типи справедливо на нього
посилаються. Але тоді це має бути **зафіксовано явно** (`duplicate_of` у MANIFEST),
а не читатися як два незалежні набори. Інакше метрика покриття завищена вдвічі.

## 6. Де README розходиться з фактом

READMEs у цілому чесні — це варто сказати прямо. Мохібейк-клас агенти визнали самі
(типи 01, 02, 10, 12, 14), включно з висновком «потребує OCR так само, як скан».

### 🔴 Тип 07 «Стройова записка» — issue #26

**README каже:** «Формат: усі — текстовий PDF… Скани-зображення: **0 з 6** — усі

Це не обман — README описує формат **джерела на Scribd**, а не те, що лежить на
диску. Але читається як «6 текстових PDF». Тип 07 має **нуль документів**, і рядок
«скани: 0 з 6» технічно правдивий у найгіршому сенсі: сканувати нічого, бо файлів
немає.

### 🔴 Тип 08 «Звіт / зведення» — issue #27

**Факт:** 19 / 4 / 2 = 25.

Окремо: файл `004`, який README рахує сканом («растрова таблиця»), — це **`.md`**.

не може містити зображення. README читається як «є у вигляді скану, треба OCR»,

## 7. Методика перевірки — щоб команда могла повторити

Жодне число вище не взяте з README чи MANIFEST. Усе переміряно на файлах.

| Що перевіряли | Чим | Критерій |
|---|---|---|
| кількість сторінок | `pdfinfo` | поле `Pages` |
| наявність текстового шару | `pdftotext -q file -` | знаків (без пробілів) на сторінку |
| скан vs текст | те саме | `< 100 знаків/стор.` → скан |
| мохібейк | частка символів у діапазоні `U+0400–U+04FF` серед усіх літер **по всьому документу** | `0 %` → мохібейк |
| шумний OCR | частка кирилічних токенів (≥4 симв.), що містять латинську літеру всередині | `> 3 %` → low-confidence |
| docx | розпакування `word/document.xml`, зняття теґів | `> 200` знаків → є текст |
| doc (Word 97) | `textutil -convert txt -stdout` | текст читається |
| дублікати | `md5` по всіх 178 не-md файлах, групування за хешем | однаковий хеш → дублікат |
| md-виписки | парсинг YAML-frontmatter: `source_url`, `original_format` | наявність і унікальність |

**Ключовий вибір методики:** мохібейк детектується **не** за наявністю тексту (текст
є!), а за часткою кирилиці. Це єдиний спосіб відрізнити «PDF, з якого можна витягти
український текст» від «PDF, з якого витягається сміття, що виглядає як текст».
Будь-яка перевірка типу «чи є текстовий шар» дасть на цих 6 файлах хибне «так».

**Артефакти перевірки** (машинний інвентар по кожному файлу: клас, сторінки, символи,
частка кирилиці, частка змішаних токенів, md5) зібрані й доступні на запит — не
включені в цю папку, щоб не плутати з даними корпусу.
