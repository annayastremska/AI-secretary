# upload_app — демо «завантажив фото → воно в базі»

Виконання запиту команди БД
([`docs/contracts/2026-08-14_upload-app-task-for-pipeline-team.md`](../../docs/contracts/2026-08-14_upload-app-task-for-pipeline-team.md)):
локальна веб-апка, у якій людина завантажує фото/скан/docx документа,
бачить, що витягнув пайплайн, і **окремою кнопкою** записує це в PostgreSQL.

Головне архітектурне правило дотримано: апка **не дублює мапінг**.
Рівно два виклики:

1. пайплайн — subprocess `python run_pipeline.py --config demos/upload_app/config-app.yaml --input <файл>`;
2. запис у базу — `ai_secretary_loader.load(md_path, original_path)` імпортом
   з `airflow/plugins/` (той самий модуль, що в CLI-обгортки
   `db/scripts/load_ai_secretary_output.py`; обидва шляхи перевірено, імпорт
   обрано, щоб віддати у UI структурований результат без парсингу stdout).

YAML-шапку вихідного `.md` апка читає **лише для показу людині** (таблиця
«поле → значення → впевненість/провенанс») — жодного власного SQL і жодного
«яке поле в яку таблицю» в апці немає.

## Запуск з нуля на чистій машині (Windows)

Усе локально: жодних хмарних сервісів, CDN чи зовнішніх запитів.
Порядок перевірено на цій машині 15.08.2026.

### 1. Конфіги зі зразків

```powershell
# з кореня репозиторію
copy .env.example .env          # заповнити паролі
copy config.example.yaml config.yaml   # для апки НЕ обов'язково: вона має свій конфіг
```

**Важливо:** у `.env` треба ДОДАТИ рядок, якого немає в `.env.example`
(без нього і `alembic`, і лоадер падають з KeyError — див. «Що передати
команді БД»):

```
DATABASE_URL=postgresql+psycopg://<APP_DB_USER>:<APP_DB_PASSWORD>@localhost:<POSTGRES_PORT>/<APP_DB_NAME>
```

### 2. База: Docker → міграції

```powershell
db\scripts\start-docker-safe.ps1        # або просто запустити Docker Desktop
docker compose up -d postgres minio minio-init   # Airflow для апки не потрібен
python -m alembic upgrade head
```

**Відома пастка на Windows (двічі впіймана тут):**

- `db/init/001_users_and_db.sh` приїжджає з git із CRLF-переносами →
  усередині контейнера `/bin/bash^M: bad interpreter`, init мовчки не
  виконується, і `alembic` далі падає з `password authentication failed`
  (ролі просто не створені). Обхід, який спрацював:

  ```powershell
  docker exec milidoc-postgres sh -c "tr -d '\r' < /docker-entrypoint-initdb.d/001_users_and_db.sh > /tmp/init.sh; AIRFLOW_DB_NAME=airflow AIRFLOW_DB_USER=airflow_app AIRFLOW_DB_PASSWORD=<пароль з .env> bash /tmp/init.sh"
  ```

  (AIRFLOW_-змінні передані вручну, бо docker-compose їх у сервіс postgres
  не пробрасыває — теж у списку для команди БД.)

- Якщо Docker Desktop не стартує з «filename, directory name … incorrect» —
  саме для цього і є `db/scripts/start-docker-safe.ps1`.

Сіди реєстру осіб (`db/seeds/unit_roster.csv`) окремого кроку завантаження
в БД не мають (міграції його не читають) — лоадер створює особи сам через
`resolve_or_create_object`, для демо цього достатньо.

### 3. Залежності Python (легка частина)

```powershell
pip install -r requirements.txt                 # пайплайн (корінь репо)
pip install -r demos/upload_app/requirements.txt  # fastapi, uvicorn, python-multipart
pip install "psycopg[binary]" minio python-dotenv alembic sqlalchemy  # для лоадера й міграцій
```

Саме `psycopg[binary]`: голий `pip install psycopg` на Windows падає в
рантаймі з «no pq wrapper available» (немає libpq).

### 4. ВАЖКИЙ крок: моделі й OCR (розміри й час — щоб не з'ясовувати в останній вечір)

| Що | Розмір | Коли вантажиться |
|---|---|---|
| MamayLM-Gemma-3-12B Q4_K_M (GGUF) | **~6.8 ГБ** | вручну, один раз; шлях у `config-app.yaml` → `llm.model_path` |
| `pip install -r requirements-optional.txt` (surya-ocr + torch) | ~2-3 ГБ пакетів | один раз |
| Ваги Surya (surya-2.gguf + mmproj) | ~1.5 ГБ | самі, при першому OCR-запуску (кеш `~/.cache/datalab/surya`) |
| llama-server (llama.cpp) | ~50 МБ | `winget install ggml.llamacpp`, шлях у `config-app.yaml` → `ocr.llama_server_path` |

Особливості Windows/CPU, уже вшиті в `config-app.yaml`:

- `ocr.llama_server_path` — Surya всередині запускає llama.cpp-сервер; на
  Windows простіше дати готовий бінарник winget-збірки, ніж збирати з джерел.
  Сервер слухає **лише 127.0.0.1** (перевірка в `pipeline/ocr/surya_reader.py`
  відмовляється працювати з нелокальним URL — зображення не покидають машину).
- `ocr.n_gpu_layers: 0` — обов'язково на цій машині: дефолт Surya (99 шарів
  на GPU) означає Vulkan на вбудованій графіці, де внутрішній сервер вмирає
  з `vk::ErrorDeviceLost` (заміри:
  `docs/research/2026-08-14_ocr-ngl0-control-run.md`).
- Кореневий `config.yaml` (з `ocr.engine: none`) апка не чіпає — у неї свій
  `demos/upload_app/config-app.yaml`, який передається через `--config`.
  На іншій машині поправте в ньому два шляхи: `llm.model_path` і
  `ocr.llama_server_path`.

### 5. Одна команда запуску апки

```powershell
# з кореня репозиторію
python -m uvicorn demos.upload_app.app:app --host 127.0.0.1 --port 8000
```

Відкрити http://127.0.0.1:8000. Тимчасові завантаження йдуть у
`data/inbox/upload_app/` (гітігнорено), результати пайплайна — у стандартне
`data/output/`.

## Перевірено (наскрізні прогони через API апки, 15.08.2026)

Усі три файли пройшли повний шлях «upload → пайплайн → перегляд → запис у
Postgres → відповідь з document_id» саме через API апки, не в обхід.
OCR-прогони — по одному (в апці це гарантує глобальний лок).

### 1. `TRIP-002.docx` (синтетика, швидкий шлях без OCR)

- Кроки: завантаження 0 с → пайплайн **7.9 с** → запис у базу **1.2 с**.
- Статус: `confirmed`. Витягнуто правильно все: ПІБ + звання (старший
  солдат УСИК Валентин Вартоломійович), місце (м. Ужгород), дати
  22–28.05.2026, 7 діб, мета, наказ-підстава, № і дата документа.
  Прогалини — лише порожні в самому бланку необов'язкові поля.
- У базі: documents.id=1, **10 фактів confirmed**, review_queue:
  `new_person` (нова особа в реєстрі — штатна перевірка).

### 2. `LEAVE-002.png` (синтетичний рендер, через OCR)

- Свіжа обробка: **~40 с** цілком (OCR 10 блоків/980 символів + витяг;
  розпізнавач уже був прогрітий). Повторне завантаження того самого файлу
  апка чесно показала як «Уже оброблявся» і за **7.1 с** віддала наявний
  запис (дедуплікація за хешем вмісту).
- Статус: `confirmed`. Витягнуто правильно: солдат РУБЕЦЬ Яків
  Богуславович, відпустка за сімейними обставинами, м. Івано-Франківськ,
  05–09.05.2026, 5 діб, фактичне повернення 10.05, № 109 від 03.05,
  частина А0000. На синтетичному рендері OCR практично ідеальний —
  очікувано (чистий шрифт, рівний аркуш).
- У базі: documents.id=2, 8 фактів confirmed, review_queue: `new_person`.

### 3. `відпускний_фото1.jpg` (РЕАЛЬНЕ фото) — чесний результат

- Повний цикл: **23.5 хв** (1410 с) — OCR реального фото + 12 полів через
  LLM-фолбек на CPU при майже вичерпаній RAM (див. «Відомі межі»).
- Статус: **`needs_review`**, причина `foreign_form_edition`: друкований
  текст збігся з оголошеним бланком лише на 5 з 27 рядків (0.19 < 0.50) —
  реальний квиток справді іншої редакції, ніж синтетичний бланк-опора.
  Це штатний шлях, не помилка: всі значення збережені, але непідтверджені.
- Що прочиталось ПРАВИЛЬНО (звірено з розпізнаним текстом): капітан
  ОМЕЛЯН Володимир Володимирович, щорічна основна відпустка,
  о. Крит/Греція, 21.07–06.08.2023, 17 діб, № 473. OCR якісний
  (15 блоків/519 символів, «УКРАЙНИ» — єдина груба помилка розпізнавання).
- Що НЕ вийшло: ПІБ не зіставився з реєстром осіб (реальна людина,
  у синтетичному реєстрі її нема) → критичні прогалини
  surname/given_name/patronymic; `unit_to_report` модель заповнила
  сміттям («о. Крит, Греція» замість в/ч); дата документа не знайдена.
  Уся довіра LLM-полів — 0.6, жодне не confirmed.
- У базі: documents.id=3, 6 фактів (5 unconfirmed + 1 rank confirmed — див.
  п. 6 «Що передати команді БД»), review_queue: `unknown_type` (питання

## Що передати команді БД

Розбіжності, знайдені при звірці контракту (вихідний `.md` пайплайна ↔ що
читає `airflow/plugins/ai_secretary_loader.py`) і при піднятті стека.
У лоадері/`db/` **нічого не правлено** — це ваша зона:

1. **`.env.example` не містить `DATABASE_URL`**, але і `app/db/env.py`
   (alembic), і `ai_secretary_loader.get_dsn()` при запуску з хосту читають
   саме його через `os.environ["DATABASE_URL"]` → KeyError на чистій машині.
   Пропозиція: додати рядок-зразок у `.env.example`.
2. **`db/init/001_users_and_db.sh` ламається на Windows-клоні**: git
   checkout дає CRLF, контейнер каже `/bin/bash^M: bad interpreter`, init
   мовчки пропускається. Пропозиція: `.gitattributes` з `*.sh text eol=lf`.
3. **Той самий init-скрипт використовує `AIRFLOW_DB_NAME/USER/PASSWORD`,
   але docker-compose не передає ці змінні в сервіс postgres** — навіть з
   LF init упав би на `CREATE DATABASE ;` (порожня підстановка) через
   `set -e`. Пропозиція: додати три змінні в environment сервісу postgres.
4. **Лоадер не читає гейт `create_subject_object` / `subject_kind`.**
   Пайплайн явно пише (коментарі в `pipeline/run.py`, `blank_meta`):
   «завантажувач мусить перевіряти обидва ключі — `create_subject_object`
   і `subject.person_complete`». Лоадер перевіряє лише
   `person_complete`/`unresolved`. Наслідок: документ зі статусом
   `needs_review`, повним ПІБ, але `subject_kind: unknown`
   (`create_subject_object: false`) все одно створить об'єкт особи в
   реєстрі. Для двох поточних доменів (leave/deployment) це не стріляє —
   стрельне на першій схемі не-person (equipment).
5. Дрібне, до відома: поля виходу, які лоадер свідомо ігнорує зараз —
   `facts[*].status` («current», інша вісь, ніж facts.status у БД),
   `facts[*].superseded_by_document_id`, `document_links`,
   `consistency_problems`, `ocr_blocks`/`ocr_chars`. Якщо щось із цього
   потрібне в базі — за вашим же принципом дописуєте ви, не апка.
6. **Факт «звання» обходить гейт статусу документа.** Лоадер синтезує
   rank-факт із `subject.rank` і бере `confirmed` з ВЛАСНОГО provenance
   звання (`field_provenance.rank.resolved`), свідомо не успадковуючи
   статус документа. Але після рев'ю 14–15.08 пайплайн гарантує
   «needs_review → `confirmed:false` на всіх фактах у `facts[]`», а
   rank-факту в `facts[]` немає — і виходить: документ №3 (реальне фото,
   needs_review, бланк під питанням, звання від LLM з довірою 0.6) дав у
   базі **1 confirmed-факт** (rank) поруч із 5 unconfirmed. Перевірено на
   живій базі. Якщо звання від моделі на непідтвердженому документі не
   має входити в підрахунки — гейт треба додати у ваш `load()`
   (наприклад, `confirmed = resolved and метод != llm` або успадкування
   документного вердикту для rank).
7. Решта контракту зійшлась: усі ключі, що їх читає
   `parse_frontmatter`/`load()` (`file_hash`, `id`, `template`,
   `source_kind`, `status`, `uploaded_at`, `domain`, `storage_key`,
   `review_queue`, `subject.person_alias/person_complete/rank`,
   `facts[*].fact_type/value_code/date_start/date_end/confirmed/confidence/source_field/additional_info`,
   `field_provenance.rank`, `identification`, `unknown_critical_fields`,
   `confirmed_empty_fields`, `warnings`, `date_range_error`,
   `unresolved_values`), у сьогоднішньому виході пайплайна є і мають
   очікувану форму — звірено на реальному прогоні TRIP-001.docx, не по
   пам'яті. Нове правило «`facts[*].confirmed` завжди узгоджений зі
   статусом документа» (рев'ю 14-15.08) лоадеру нічого не ламає — він і
   так бере `confirmed` пофактово.

## Відомі межі

- **Це демо-стенд, не продакшн**: задачі живуть у пам'яті процесу
  (перезапуск апки — прогрес зник, але результати пайплайна й база цілі);
  один користувач; без автентифікації; слухає лише 127.0.0.1.
- **OCR-прогони строго по одному** (глобальний лок): два паралельні
  llama-server на CPU не поміщаються в пам'ять.
- **RAM — головний ризик демо.** На машині з 16 ГБ під час фази LLM-витягу
  лишалось 0.3–0.5 ГБ вільної памʼяті (OCR-сервер ~2 ГБ + MamayLM 12B
  ~4-6 ГБ + Docker/WSL). Один раз процес сервера апки на цьому загинув
  посеред прогону; сам прогін пайплайна при цьому вижив і зберіг результат,
  повторне завантаження файлу показало його як «Уже оброблявся». Перед
  демо закрити все зайве (інші контейнери, браузерні вкладки), або
  перейти на меншу модель MamayLM-4B (~2.5 ГБ, один рядок у
  config-app.yaml).
- **Повний цикл на фото — хвилини, не секунди** (див. таблицю часів вище).
  Для живого демо: docx показувати наживо, фото — або заздалегідь прогріте
  (другий прогін того самого фото = `duplicate`, миттєво), або з чесним
  очікуванням під секундомір на екрані.
- Відомий витік у llama-server (~27 МБ на 1000 токенів, заміряно в B1):
  на довгій сесії демо процес пайплайна завершується після кожного файлу,
  тож витік не накопичується між документами.
- Час кроку «пайплайн» апка міряє як ціле (subprocess): окремих цифр
  OCR/LLM зсередини одного прогону вона не бачить — розбивку по стадіях
  дає `pipeline/scripts/ocr_batch_diag.py`, це його робота, не апки.
