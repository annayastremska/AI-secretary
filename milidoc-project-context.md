# Контекст проєкту: система обробки військових документів (кодова назва milidoc)

Документ для передачі контексту між сесіями/акаунтами. Останнє оновлення: 2026-08-06.

---

## 1. Що це за проєкт

Команда (Андрій + колеги) розробляє **демо-версію** системи обробки документів для військового підрозділу. Замовник — військові, точний контакт і процес фідбеку ще уточнюються.

Ціль демо: показати робочий прототип, який можна дорощувати до повноцінного продукту без переписування архітектури з нуля.

Джерело вимог: два документи —
1. `project-expectations.md` — початкове ТЗ (обробка фактологічних документів у структуровану БД).
2. `ТЗ_AI-секретар.md` + `normative-docs-subsystem.md` — оновлення ТЗ, що додає другу підсистему: "second brain" для нормативних документів.

Файл `ТЗ_AI-секретар (1).md` фізично лежить у корені репозиторію — це повний текст документа №2 вище, прочитаний і опрацьований (не лише короткий переказ). Звідти взято конкретний перелік 5 типів документів (розділ 6 нижче) і офіційні колонки штатної книжки.

## 2. Що поза скоупом команди (робить хтось інший / окремий трек)

- КСЗІ-атестація та інша сертифікація безпеки (Держспецзв'язку) — юридична вимога.
- Фізична й мережева ізоляція інфраструктури (розміщення сервера, сегментація мережі, air-gap).
- Захищений канал (VPN/шлюз) для мобільного доступу з будь-якої точки країни — реалістично майже неможливо зробити ідеально захищеним, і це вже воєнна інфраструктура, не наша компетенція.
- Юридичні питання: ліцензії моделей, експортні обмеження — потребують консультації юриста.
- Пряма технічна інтеграція з АСКОД/Армія+ — публічного API немає. Тільки ручний експорт документа й завантаження в нашу систему. Чатбот **ніколи** не підключається до АСКОД напряму.

## 3. Дві підсистеми проєкту

### 3.1. Фактологічний конвеєр (оригінальне ТЗ)

Документи (накази, довідки тощо) → структуровані факти в реляційній БД → відповіді через фіксовані SQL-шаблони.

### 3.2. Нормативна підсистема / "second brain" (нове ТЗ)

Нормативні документи (інструкції, положення, накази загального характеру) → зберігаються як текст із метаданими → відповіді через пошук і цитування, **ніколи не через факти**.

Ключова відмінність: фактологічний конвеєр видає **числа/статуси** (скільки людей у відпустці), нормативний — видає **цитату з посиланням на джерело і статус чинності документа** (як подати заяву на відпустку, зі скасуванням, якщо норму вже змінили).

Ці дві підсистеми **паралельні, не вкладені одна в одну**. Запит користувача спершу класифікується (агрегація vs процедура), і йде в одну з двох гілок пайплайну.

## 4. Технічний стек (рішення прийняті)

| Компонент | Вибір | Причина |
|---|---|---|
| СУБД | PostgreSQL 16, self-hosted у Docker | Без хмари, узгоджено з вимогою локальності |
| Міграції схеми | Alembic, чистий SQL у міграціях (без ORM autogenerate) | Версійність схеми, повторюваність на будь-якій машині |
| Об'єктне сховище | MinIO (S3-сумісне) | Оригінали сканів, синтетика, шаблони, нормативні MD-файли |
| Оркестрація | Apache Airflow (LocalExecutor) | Симуляція джерел даних, пайплайн обробки, метрики |
| Мова / бібліотеки | Python 3.11+, `psycopg` v3, SQLAlchemy Core (без ORM), `python-dotenv`, `pytest` | — |
| OCR (друковані документи) | **Surya** — мультимовний, підтримує українську, CPU/GPU. **Встановлено** (`surya-ocr` у `.venv-ml`) | Обрано після оцінки; рукописні документи через Surya не проходять — окрема ручна черга |
| Генеративна LLM | **MamayLM-Gemma-3-12B-IT-v2.0** (INSAIT) — "основна шишка". **Встановлено й перевірено** через Ollama (GGUF Q4_K_M) | Найкраща відкрита українська LLM, локальний запуск, вільна ліцензія (Gemma Terms) |
| Embedding-модель (якщо дійде до векторного пошуку) | Ще не обрано остаточно; кандидат — **BGE-M3** (BAAI, MIT, 100+ мов, 8192 токени контексту) | MamayLM — генеративна, вбудованого embedding-режиму не має; embeddings завжди окрема модель |
| Reranker (якщо буде retrieval-пайплайн) | Кандидат — `bge-reranker-v2-m3` | Використано в опублікованому дослідженні українського RAG (arxiv 2604.22095) з тим самим MamayLM для генерації |
| Повнотекстовий пошук | PostgreSQL FTS — **потребує перевірки** конфігурації для української (`pg_ts_config`), можливо Hunspell-словник | Дешевший перший крок перед pgvector |
| Векторний пошук (майбутнє, не в демо спочатку) | pgvector | Розглядати, тільки якщо FTS виявиться недостатнім на реальному корпусі |

### Важливе уточнення про MamayLM
MamayLM — decoder-only генеративна модель (архітектура Gemma), **не має embedding-варіанту**. Для векторного пошуку завжди буде потрібна окрема модель (encoder-тип, напр. BGE-M3). Знайдено реальний прецедент — опублікована робота "An End-to-End Ukrainian RAG for Local Deployment" (arxiv 2604.22095): пайплайн dense embeddings + BM25 + Reciprocal Rank Fusion + BGE-reranker-v2-m3 → топ-3 сторінки цілком → MamayLM-12B (LoRA fine-tuned) тільки для генерації відповіді з номером сторінки. Це підтверджує обраний розподіл ролей (MamayLM = генерація, окрема модель = пошук) і варте детальнішого вивчення як референс-архітектура.

### Surya і MamayLM — РЕАЛІЗОВАНО локально (2026-08-07)

**Окреме `.venv-ml`** (не той самий, що для БД/Alembic — важкий ML-стек з torch/transformers конфліктував би із легким `venv` для БД). Залежності зафіксовано в `requirements-ml.txt` (`pip freeze`). На цьому ноуті **нема дискретної GPU** (тільки Intel UHD, без CUDA) — усе рахується на CPU.

- **Surya**: `pip install surya-ocr` у `.venv-ml`, CLI перевірено (`surya_ocr --help` відповідає).
- **MamayLM**: обрано **Ollama + GGUF** замість важкого `transformers`/`torch` завантаження повних ваг — без GPU повний fp16 12B (~24ГБ) на CPU неможливий, а квантований GGUF (Q4_K_M, 7.3ГБ, `INSAIT-Institute/MamayLM-Gemma-3-12B-IT-v2.0-GGUF`) реалістично працює через `llama.cpp`-бекенд Ollama. Модель створена (`ollama create mamaylm -f Modelfile`, `models/mamaylm/Modelfile` — у git, сама `.gguf`-вага — ні, `*.gguf` в `.gitignore`), **перевірено живим запитом українською** — відповідь коректна й по темі.
- **Ollama модель зберігається на `D:\ollama-models`**, не в дефолтному `%USERPROFILE%\.ollama` на C: — свідоме рішення через інцидент нижче.

**Інцидент: C: диск заповнився вщент під час завантаження моделі.** Ollama за замовчуванням копіює моделі в профіль користувача на C:, який був майже повний (~19ГБ, потім взагалі 0 байт). Це **одночасно вивалило і Ollama, і Docker Desktop** (той самий симптом, що вже бачили раніше — побиті unix-socket файли `dockerInference`/`docker-secrets-engine\engine.sock`, "The filename... syntax is incorrect" — але цього разу справжня причина була не `EnableDockerAI`, а буквально брак місця на диску під час запису). Виправлення:
1. Видалити недокопійований сирітський blob, звільнити місце.
2. `setx OLLAMA_MODELS "D:\ollama-models"` — назавжди переносить сховище моделей Ollama на D:. **Важливо**: `setx` оновлює лише реєстр, не поточну сесію — якщо термінал уже відкритий, треба передавати `OLLAMA_MODELS` явно в змінних середовища при запуску (`OLLAMA_MODELS="D:\ollama-models" ollama.exe serve`), доки сесію не перезапущено.
3. Docker Desktop — той самий рецепт, що й раніше: `taskkill` усіх docker-процесів, `wsl --shutdown`, перейменувати `%LOCALAPPDATA%\Docker\run` і `%LOCALAPPDATA%\docker-secrets-engine` (не видаляти напряму — read-only файли з WSL9P блокують видалення, перейменування спрацьовує), перезапустити.

**C: досі критично заповнений** (~9.5ГБ вільно з 183ГБ станом на зараз) — це системний ризик, не одноразовий збіг: Docker Desktop і Ollama обидва можуть впасти знову, якщо щось ще запише великий файл на C:. `C:\Users\Admin\Downloads` — 9ГБ, найбільший очевидний кандидат на розчищення, **свідомо не трогав** — це особисті файли користувача, рішення лишається за ним.

## 6. Структура БД (фактологічний конвеєр) — РЕАЛІЗОВАНО, не просто план

4 міграції в `db/migrations/`, застосовані до локальної БД (`alembic upgrade head`):
1. `9e5e83de546b_enable_extensions` — pgcrypto, pg_trgm, btree_gin.
2. `1283dc745daa_reference_tables` — довідники (нижче).
3. `60ea874484ed_core_tables` — основні таблиці (нижче).
4. `9337860eac54_core_functions` — `resolve_or_create_object`, `next_document_for_processing`.

### Довідники

- **`document_types`** — 5 типів, підтверджені ТЗ_AI-секретар.md розділ 2.6 (більше не відкрите питання):
  `staff_roster` (Штатна книжка), `vacation_report` (Рапорт на відпустку), `equipment_record` (Облік техніки), `business_trip_order` (Відрядження), `monetary_allowance` (Грошове забезпечення — **важливо**: суми фіксуються ЩОДЕННО окремим записом, а не одним значенням на весь період, на відміну від інших типів).
- **`dimensions`** — виміри фактів. Засіяно: `rank` (Звання), `position` (Посада) — підтверджені офіційною формою штатної книжки як історія з датами й наказами (не статичні поля). Решта вимірів (відпустка, стан техніки тощо) — досі відкрите питання, свідомо не вигадані заздалегідь.
- **`dimension_values`** — допустимі значення на вимір, де застосовно. Порожня (чекає на dimensions).
- **`object_kinds`** — засіяно: `person`, `equipment`, `task`.
- **`sources`** — засіяно: `askod_synthetic`, `mobile_photo`, `unit_export`.

### Основні таблиці

`objects` — **розбито по видах** (окрема таблиця на людину/техніку/завдання, бо поля надто різні), через спільний "якір": `objects.id` = `PK` кожної деталь-таблиці (`people.object_id`, `equipment.object_id`, `tasks.object_id`) — паттерн shared-PK / class-table-inheritance. `facts` і `object_aliases` посилаються тільки на `objects(id)`, не знають, людина це чи техніка.

```sql
documents (
  id, type_id FK, source_id FK,
  source_kind,        -- 'electronic' (синтетика/АСКОД) | 'photo' (реальне фото, йде через OCR)
  status,             -- uploaded | text_ready | classified | extracted | failed
  raw_uri, text_content,
  uploaded_at, processed_at, expires_at, checksum
)

objects (
  id, kind_id FK object_kinds, canonical_name, created_at
)

-- статичні поля людини з офіційної форми штатної книжки.
-- Звання/посада НЕ тут — вони "стан", що змінюється в часі з наказами, тобто йдуть у facts.
people (
  object_id PK/FK objects,
  service_id,
  last_name, first_name, patronymic,
  rnokpp,                                    -- офіційна назва (не "ІПН")
  id_document_type, id_document_series, id_document_number,
  birth_date, birth_place, gender, education,
  service_type,                              -- вид служби
  contract_start_date, contract_end_date, conscription_period,
  enrollment_date, enrollment_order_date, enrollment_order_number,
  arrived_from,                              -- звідки прибув
  service_entry_date, service_entry_authority,  -- ким і коли призваний(а)
  relatives_info, additional_info
)

equipment (
  object_id PK/FK objects,
  inventory_number, equipment_type, model
)

tasks (
  object_id PK/FK objects,
  task_type, description
)  -- мінімально, найменш деталізований вид об'єкта в ТЗ

object_aliases (
  id, object_id FK objects, alias UNIQUE, first_seen_in_doc FK documents, created_at
)
-- UNIQUE(alias) — запобіжник від гонок при одночасному резолві псевдонімів

facts (
  id, object_id FK objects, dimension_id FK dimensions, value,
  valid_from, valid_to NULLABLE,             -- CHECK valid_to >= valid_from
  source_doc_id FK documents, confidence, status,  -- confirmed | unconfirmed | rejected
  created_at, version                        -- version — для оптимістичного блокування
)

review_queue (
  id, document_id FK, fact_id FK, queue_type,  -- unknown_type | unconfirmed_fact | handwritten | qa_sample
  created_at, assigned_to, resolved_at, resolution
)

review_log (
  id, fact_id FK, changed_by, changed_at, old_value, new_value, action  -- INSERT-only аудит
)
```

### Функції (реалізовано, PL/pgSQL, migration `core_functions`)

- **`resolve_or_create_object(alias, kind_code, doc_id)`** — швидкий шлях: якщо псевдонім відомий, повертає `object_id`. Інакше створює кандидата в `objects`, атомарно намагається закріпити псевдонім (`ON CONFLICT (alias) DO NOTHING RETURNING`). Якщо гонку програно — видаляє свій "осиротілий" рядок `objects` і повертає id переможця. Перевірено на ідемпотентність (той самий псевдонім → той самий id). **Справжня конкурентна гонка (дві сесії одночасно) не тестувалась одноразовим скриптом** — свідомо залишено для майбутнього Airflow-стрес-тесту (розділ 9).
- **`next_document_for_processing(worker_id, status_from)`** — `SELECT ... FOR UPDATE SKIP LOCKED LIMIT 1`. **Важливо для використання:** викликати в тій самій транзакції, що й наступний `UPDATE` статусу документа — інакше лок знімається одразу після виклику й захист від паралельного захвату не працює.
- **View `confirmed_facts` — ЩЕ НЕ СТВОРЕНО**, це наступний крок (був у плані розділу 12, не встигли).

Для стрес-тестів (окремі таблиці, не створені): `db_metrics`, `pipeline_events`, `race_events` (лічильник спрацювань `ON CONFLICT` при резолві псевдонімів).

### Синтетична штатна книжка

## 7. Уявлення про структуру нормативної підсистеми (second brain)

Формат зберігання: `.md` файли з **YAML-шапкою** (не JSON — свідомо змінили з початкової специфікації, бо YAML — нативний формат frontmatter, який розуміють інструменти типу Obsidian, і простіше парситься `python-frontmatter`).

Приклад шапки:
```yaml
---
id: instr-leave-2024-145
title: Порядок подання заяви на щорічну відпустку
doc_type: instruction   # instruction | regulation | order | template
doc_number: "145"
issue_date: 2024-03-01
issued_by: "..."
status: unverified       # current | superseded | cancelled | probably_superseded | unverified
status_source: none       # declared | inferred | manual | none
supersedes: []
superseded_by: null
related: []
access_level: internal
last_verified: null
---
```

Дзеркальна таблиця в Postgres для фільтрації (сам текст лишається у файлі, не дублюється в БД):
```sql
normative_docs (
  id text PRIMARY KEY, title, doc_type, doc_number, issue_date,
  issued_by, status, status_source, last_verified, access_level,
  file_uri,   -- посилання на MinIO
  created_at
)

normative_doc_relations (
  from_doc_id FK, to_doc_id FK, relation_type  -- 'supersedes' | 'related'
)
```

### Ключові принципи (з нового ТЗ)
- **Читати документ цілком, не chunks** — для процедурних текстів порядок кроків критичний, chunking ламає інструкцію (можна отримати "крок 3" без "кроку 1").
- **Три рівні довіри до статусу чинності**: `declared` (документ сам заявляє, що скасовує інший — LLM-екстракція з фіксованою JSON-схемою), `inferred` (евристика — той самий номер + новіша дата, свідомо позначається як непідтверджений сигнал, не факт), `manual` (людина підтвердила), `none` (невідомо).
- **Система ніколи не позначає документ чинним самостійно** — та сама філософія, що й "не вигадувати значення" у фактологічному конвеєрі, перенесена в новий контекст.
- **Курація відбувається в момент завантаження** документа людиною (два питання під час аплоаду), а не постфактум.
- Гібридні документи (містять і факти, і процедурний текст) — явно визнані можливими; один `document_id` може мати рядки і в `facts` (через `object_id`), і в `normative_docs` одночасно. Таблиці лишаються незалежними одна від одної.

### Маршрутизація запиту (заміняє стару логіку "шаблон/відмова")
Тепер трирівнева:
1. LLM класифікує запит: агрегація (факти) чи процедура (нормативка) чи не підходить ні під що.
2. Агрегація → стара логіка: обрати SQL-шаблон, підставити параметри, виконати на `confirmed_facts`.
3. Процедура → пошук кандидатів у нормативці (спершу фільтр за шапками / FTS, пізніше можливо pgvector), прочитати документ цілком, згенерувати відповідь-цитату з обов'язковими елементами: джерело, дата, статус чинності.
4. Якщо жоден шлях не підійшов — чесна відмова, не імпровізація.

Це змінює Epic 7 (чатбот) зі старого беклогу — стару логіку "Fallback 'не знаю'" стає третім кроком, не другим.

### Відкриті питання нормативної підсистеми
- Чи потрібна українська FTS-конфігурація в Postgres "з коробки" чи треба ставити Hunspell — **не перевірено, треба зробити на локальній БД** (`SELECT cfgname FROM pg_ts_config;`).
- `access_level` у шапці вже є полем, але RBAC явно поза скоупом демо у старому ТЗ — нестиковка, потребує явного рішення: чи це просто поле-заглушка в демо.
- Ретенція 30 днів для оригіналів — мотивована персональними даними у фактологічних документах; для нормативки, ймовірно, виняток (нормативка зазвичай не містить персональних даних) — рекомендовано зафіксувати як рішення, не як відкрите питання.
- Колізія номерів документів (однаковий номер від різних органів) — рівень 2 довіри (евристика) потребує явного тесту на цей кейс.
- Точність маршрутизації запитів (агрегація/процедура/відмова) варто рахувати як окрему метрику, не тільки бінарний pass/fail.

## 9. Синтетичні дані та Airflow — задум

Два незалежні потоки навантаження на БД, щоб під час стрес-тестування побачити, як вона поводиться під конкурентним записом:

- **Потік A (синтетика / АСКОД)**: DAG-и генерують **готовий текст** документа одразу (симулюють електронний експорт з АСКОД, а не фото) — **OCR тут не потрібен і не запускається**. Джерела: `source_mobile_trickle` (часто, малими партіями), `source_batch_unit_export` (вечірня пачка), `source_askod_daily_dump` (ранкова пачка), `source_burst_stress` (стрес-сплеск).
- **Потік B (реальні фото)**: окремий DAG `photo_ocr_ingest`, підбирає фото з бакета, справді ганяє через Surya OCR. Повільніший, окремий від потоку A.

Обидва потоки пишуть у ту саму БД одночасно — мета навмисно спровокувати гонки (особливо на резолві псевдонімів об'єктів) і виміряти, чи система коректно і швидко це витримує. План стрес-тестів: спокійний фон → ранкова хвиля → змагання за псевдоніми → аномальний сплеск. Метрики збираються в `db_metrics`/`pipeline_events`/`race_events`.

**Ще не реалізовано** — жодного DAG-файлу, генератор синтетичних документів (крім штатної книжки, розділ 6). MinIO й Airflow-інфраструктура вже піднято (нижче) — залишилось написати самі DAG-и.

### Airflow — РЕАЛІЗОВАНО (docker-compose.yml, поки без жодного DAG)

4 сервіси в `docker-compose.yml`: `airflow-init` (одноразовий — `airflow db migrate` + створення admin-юзера, `|| true` щоб не падати при повторному запуску), `airflow-webserver`, `airflow-scheduler`. Всі — `apache/airflow:2.10.4`, executor — `LocalExecutor` (як і вирішено в розділі 4), часовий пояс `Europe/Kyiv`.

- **Метадані Airflow — окрема БД `airflow` в тому самому Postgres-контейнері** (не окремий контейнер), роль `airflow_app` — щоб не плутати оркестрацію зі схемою фактологічного конвеєра. Створено і в `db/init/001_users_and_db.sh` (для майбутніх свіжих розгортань), і вручну застосовано на вже працюючому кластері (init-скрипти Postgres виконуються лише при першій ініціалізації, не на живій БД).
- **Порт вебсервера — 8081, не 8080** — типовий 8080 вже зайнятий старим контейнером `astro_01a289-api-server-1` (те саме Astro CLI-залишок, що й змусив Postgres піти на 5433). Той самий паттерн конфлікту повторився й тут.
- Volumes: `./airflow/dags`, `./airflow/logs` (в `.gitignore`, руантайм-логи), `./airflow/plugins`.
- `AIRFLOW__CORE__FERNET_KEY` і `AIRFLOW__WEBSERVER__SECRET_KEY` — реальні згенеровані значення в `.env` (не порожні/дефолтні), в `.env.example` — інструкція, як згенерувати (`python -c "import secrets; print(secrets.token_hex(24))"` і `base64.urlsafe_b64encode(os.urandom(32))` відповідно).
- Перевірено живим запитом: `curl http://localhost:8081/health` → 200, scheduler підняв `LocalExecutor` без помилок у логах.
- **DAG-и — папка порожня** (`.gitkeep`), жодного DAG ще не написано — це наступний крок (генератор синтетики + `source_mobile_trickle`, розділ 12).

### MinIO — РЕАЛІЗОВАНО (docker-compose.yml)

Два сервіси додано до `docker-compose.yml`: `minio` (сам сервер, порти `MINIO_PORT`/`MINIO_CONSOLE_PORT` з `.env`, дані в `./data/minio`) і `minio-init` (одноразовий `minio/mc`-контейнер, створює бакети при старті, `depends_on: minio: condition: service_healthy`, завершується `exit 0` після виконання — це очікувано, не помилка).

Бакети (усі створені, перевірено `mc ls`):
- `templates/` — порожні бланки/текстові шаблони + YAML-конфіги полів, шрифти, приклади.
- `raw-photos/` — реальні фото. **TTL 30 днів застосовано через MinIO ILM** (`mc ilm rule add --expire-days 30`), не тільки задокументовано — перевірено `mc ilm rule list`.
- `synthetic-text/` — текстові версії від Airflow-синтетики.
- `ground-truth/` — правильні відповіді для метрик (пайплайн доступу не має, тільки скрипти оцінки).
- `ocr-output/` — структурований вивід OCR (hOCR/ALTO), якщо потрібен.
- `manual-review-cache/` — прев'ю для UI рев'ю. TTL **не встановлено** (свідомо — точна тривалість "короткого TTL" ще не вирішена, не вигадана довільно).
- `exports/` — звіти, демо-артефакти.

Облікові дані MinIO — окремі нові змінні в `.env`/`.env.example`: `MINIO_ROOT_USER`, `MINIO_ROOT_PASSWORD`, `MINIO_PORT` (9000, S3 API), `MINIO_CONSOLE_PORT` (9001, веб-консоль).

## 10. Про OLAP/дублювання даних (обговорене й відхилене поки що)

Питання: чи потрібен окремий OLAP шар, бо OLTP погано тягне аналітику. Відповідь: **ні, поки що не потрібен**. Обсяг даних для демо (тисячі-десятки тисяч рядків) не виправдовує складність окремої системи й ETL-затримки. Замість повного OLAP:
- **Materialized views** для агрегатів дашборду, оновлювані по розкладу через окремий Airflow DAG (`REFRESH MATERIALIZED VIEW CONCURRENTLY`) — це і є "дублювання", тільки без нової СУБД.
- **Read replica** (нативна Postgres streaming replication) — якщо навантаження дашборду/чатбота реально почне заважати запису — розділяє read/write без переходу на іншу технологію.
- **Партиціонування `facts` за часом** (`PARTITION BY RANGE`), якщо обсяг виросте.

Рекомендація: додати до Epic 8 P1-історію "materialized views для агрегатів дашборду" і згадати read replica в розділі "ідеальний світ" документа очікувань.

Перевіряти командою `docker inspect <container> --format '{{json .Mounts}}'` — Source має вказувати на актуальний шлях.

**Окремо**: під час цього ж інциденту Docker Desktop кілька разів падав з `An unexpected error occurred` через побитий unix-socket файл (`dockerInference`, `docker-secrets-engine\engine.sock` — помилка `The filename... syntax is incorrect`). Це виявилось пов'язаним з новою фічею **Docker AI/Inference**, не з переносом файлів. Виправлено назавжди: `EnableDockerAI: false` у `%APPDATA%\Docker\settings-store.json`. Якщо Docker Desktop знову почне падати з подібною помилкою про `.sock`-файл — спершу перевірити цей прапорець, а не ганяти по колу перейменування зіпсованих socket-файлів.
