# demo-story — набір документів до презентації

Логічно зв'язана історія «від А до Я» плюс масовка для обсягу бази. Мета не
«багато рядків», а показати те, чого не дасть звичайний SQL: склад відповіді
(дата зрізу, знаменник, скільком непідтверджено), зв'язок документ→документ
(скасування) і різницю «підтверджений факт / чернетка».

Усе синтетичне. Особи -- **зі штатки** `db/seeds/unit_roster.csv` (звання, ПІБ
і посада дослівно), тому кожен документ зіставляється з наявним об'єктом
реєстру, а не створює нову особу. Частини, міста, номери документів і наказів
вигадані.

| що | де | скільки |
|---|---|---|
| історія, `.docx` | `story/` | 17 |
| та сама історія, `.pdf` (текстовий шар) | `story-pdf/` | 5 |
| та сама історія як «знімок телефоном» | `story-photo/` | 4 |
| масовка, `.docx` | `bulk/` | 130 |
| резерв «не заливати в базу» | `live/` | 3 (docx + pdf + фото) |
| еталони до історії та резерву | `data/eval/demo-story/per-document/` | 20 |

Формати -- ті самі дві форми, які пайплайн уже вміє: відпускний квиток
(Додаток 30) і посвідчення про відрядження (Додаток 28). Документи збираються
заливкою значень у порожні бланки `../leave/відпускний_шаблон.docx` і
`../deployment/посвідчення_відрядження.docx` -- у ті самі комірки, що й корпус
`synthetic-2026-05`. Нових бланків набір не вводить навмисно: демо показує
наскрізний шлях, а не нову форму.

Чого в наборі свідомо немає:

- **підрозділів**: у документах друкується лише військова частина (рішення
  Ані -- «підрозділ усе один»), тому питань «скільком у 2 роті» набір не
  ставить і зв'язку особа→підрозділ не потребує;
- **повних тезок**: у штатці немає двох осіб з однаковим прізвищем І ім'ям,
  тому пара однофамільців -- це Приймак Остап Русланович і Приймак Єлисей
  Романович (спільне прізвище, різні ім'я та по батькові). Повна тезковість
  у реєстрі не трапилась;
- **заповненого зворотного боку**: відмітки про вибуття/прибуття лишаються
  порожніми (нормальний стан документа на момент видачі; жодне поле схем їх
  не читає).

Масовка (`bulk/`): ті самі дві форми, інші 130 осіб штатки, періоди в межах
[сьогодні−90; сьогодні+30] (для 28.08.2026 це червень–вересень 2026), 78
відпусток і 52 відрядження. Кожен восьмий документ -- із порожнім критичним
полем (місце / дати / ПІБ), щоб «непідтверджених» у чаті не було нулем.

`live/` у базу **не заливається**: це резерв, щоб на демо провести документ
живцем -- по одному в кожному форматі (docx, pdf, фото).

## Як згенерувати заново

```bash
# усе (17 docx + 5 pdf + 4 фото + 130 масовки + 3 резерву + еталони)
python data/eval/samples/demo-story/generate_demo_story.py --today 2026-08-28

# окремі частини
python data/eval/samples/demo-story/generate_demo_story.py --only story,pdf
python data/eval/samples/demo-story/generate_demo_story.py --only bulk --bulk-count 200
```

`--today` без значення = системна дата. `--seed` фіксує масовку (дефолт
20260822), тому повторний прогін дає ті самі документи. Потрібні `python-docx`,
`PyMuPDF`, `Pillow`, `numpy`.

Якщо змінити `--today`, **перерахувати відповіді** в `demo-questions.md`: усі
дати зсуваються.

## Як прогнати

```bash
# історія: 16 confirmed + 1 needs_review (DEMO-07), жодного unresolved
python run_pipeline.py --no-llm --dry-run --reprocess --input data/eval/samples/demo-story/story

# pdf -- те саме, що docx
python run_pipeline.py --no-llm --dry-run --reprocess --input data/eval/samples/demo-story/story-pdf

# масовка: ~14% needs_review
python run_pipeline.py --no-llm --dry-run --reprocess --input data/eval/samples/demo-story/bulk

# фото -- лише з OCR (config: ocr.engine: surya)
python -m eval.evaluate --input data/eval/samples/demo-story/story-photo --no-llm --ocr surya
```

Прилад (`eval/evaluate.py`) читає еталон із
`data/eval/synthetic-2026-05/per-document/` -- це його константа `EVAL_DIR`.
Щоб він узяв ЦЕЙ набір, треба або перевизначити `EVAL_DIR` у пам'яті обгорткою
(`ev.EVAL_DIR = "data/eval/demo-story"`), або додати приладу відповідний
параметр. Заміряно такою обгорткою:

| набір | результат |
|---|---|
| `story/` (17 docx) | поля 231/231, шаблон 17/17, статуси confirmed=16, needs_review=1 |
| `story-pdf/` (5 pdf) | поля 69/69, ті самі значення, що на docx |
| `story-photo/DEMO-01.jpg` (Surya) | поля 14/14 |

Базова лінія наявних корпусів після цієї роботи не зрушилась: leave 224/224,
deployment 183/183, `python -m pytest eval/tests -q` -- 224 passed.

## Фото: чому воно погане навмисно

`story-photo/` -- не чистий рендер, а імітація знімка телефоном: поворот
1.6–3°, нерівне освітлення з м'якою тінню на частині аркуша, гаусове
розмиття, шум сенсора, обрізаний край, JPEG-артефакти. `DEMO-10.jpg`
**навмисно гірший за решту** (розмиття 2.6, якість 32) -- щоб було видно, де
межа OCR. Профілі -- `PHOTO_PROFILES` у генераторі.

Цифри якості на фото тут не збираються: повний прогін OCR/LLM іде на сервері
(H100), локально перевіряється лише те, що формат не битий.
