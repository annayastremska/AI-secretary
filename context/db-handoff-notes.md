# Стик пайплайна екстракції з БД: що вже узгоджено і що треба вирішити

Записано після адаптації виходу пайплайна під `schema_dump.sql` +
`ai_secretary_loader.py`, які надіслала команда БД. Мета файлу -- щоб питання
до них не переказувались по пам'яті, а мали одне місце з формулюваннями.

## 1. Що пайплайн віддає тепер (контракт)

YAML-шапка кожного `data/output/documents/<domain>/<id>.md`. **Форма однакова
для всіх статусів** (`confirmed` / `needs_review` / `unresolved` /
`duplicate`): відсутнє значення -- `null` або порожня колекція, але ключ є
завжди. Раніше форм було шість, і `meta["template"]` / `meta["facts"]` у
завантажувачі падали `KeyError` на першому ж дублікаті в папці.

| ключ | тип | куди в БД |
|---|---|---|
| `id` | uuid | -- (їхній `documents.id` свій) |
| `file_hash` | sha256 | `documents.checksum` (UNIQUE) |
| `source_file` | str | `documents.original_filename` |
| `source_kind` | `electronic` \| `photo` | `documents.source_kind` (CHECK) |
| `status` | `confirmed`/`needs_review`/`unresolved`/`duplicate` | див. п. 3 |
| `template` | код схеми | через `TEMPLATE_TO_DOC_TYPE` -> `document_types` |
| `subject.surname/given_name/patronymic` | str | `people.last_name/first_name/patronymic` |
| `subject.person_alias` | str | `object_aliases.alias` / `resolve_or_create_object` |
| `subject.person_complete` | bool | попередження: `false` = вставка в `people` впаде |
| `subject.rank` | `{code,label}` | факт виміру `rank` |
| `subject_kind` | `person`/`equipment`/`task`/`unit`/`none`/`unknown` \| null | `object_kinds.code` (**зараз не читається**, хардкод `'person'`) |
| `subject_kind_source` | `schema`/`domain_map`/`llm` \| null | -- (надійність визначення) |
| `subject_kind_reason` | str \| null | -- (чому не вийшло надійніше) |
| `create_subject_object` | bool | **гейт**: `false` = об'єкт у `objects` НЕ створювати |
| `facts[]` | список | `facts` (один рядок = один вимір) |
| `facts[].fact_type` | код | `dimensions.code` |
| `facts[].value_code` | str | `facts.value` |
| `facts[].date_start/date_end` | ISO date \| null | `facts.valid_from/valid_to` |
| `facts[].confirmed` | bool | `facts.status` confirmed/unconfirmed |
| `facts[].confidence` | 0..1 \| null | `facts.confidence` (**зараз не читається**) |
| `review_queue` | `unknown_type`/`unconfirmed_fact`/`handwritten`/`qa_sample` \| null | `review_queue.queue_type` |
| `field_provenance` | dict по полях | -- (для аудиту, не для БД) |
| `date_range_error` | str \| null | попередження про CHECK `valid_to >= valid_from` |

**Гарантії, на які завантажувач може спиратися:**

1. `facts[0]` -- завжди ОСНОВНИЙ факт шаблону (`schema.fact_type`). Їхній код
   уже бере `meta["facts"][0]["date_start"]` як `valid_from` для звання, тож
   порядок зафіксовано навмисно, а не випадково.
2. `date_start <= date_end` перевірено на нашому боці. Якщо ні -- документ
   ніколи не буде `confirmed`, а причина в `date_range_error`.
3. Дати -- рік у межах 1900..2100 і календарно існуючі (31 лютого відкинуто).
4. `create_subject_object: false` -> об'єкт у `objects` створювати НЕ треба, і
   `subject` для нього не є джерелом рядка в реєстрі. Це не «поле не зчиталось»,
   а відповідь: або суб'єкта в документі немає (`subject_kind: none` --
   нормативна інструкція), або вид не визначено (`unknown`).

### 1.1. `subject_kind` -- вид суб'єкта документа (нове, 13.08.2026)

Реалізовано `pipeline/subject_kind.py`; порядок і обґрунтування --
`extraction-pipeline-prototype.md`, розділ «Визначення суб'єкта документа».

```
є схема               -> subject_kind зі схеми (ОГОЛОШЕННЯ, не висновок)
немає схеми:
  домен визначений    -> мапінг «домен -> вид» з dictionaries/domain_keyphrases.yaml
  домен не визначений -> LLM, закритий enum + обов'язковий "unknown" (вимкнено)
вид none / unknown    -> об'єкт НЕ створюється, документ у чергу рев'ю
```

Що з цього важливо саме для завантажувача:

- **`person`/`equipment`/`task`/`unit`** -- це рядки їхнього `object_kinds`,
  тобто перелік у нас закритий за їхньою таблицею, а не за нашим бажанням.
  `unit` -- той, що вони додали на нашу пропозицію; він потрібен для
  `registry: military_unit` (`destination_org`, `unit_to_report`), яке досі
  йшло текстом у `facts.value`.
- **`none` vs `unknown` vs `null`** -- три різні речі, і дія різна:
  `none` = суб'єкта в документі немає (відповідь, рев'ю не потрібне);
  `unknown` = визначити не вдалося (рев'ю потрібне, `review_reason:
  unknown_subject_kind`, `review_queue: unknown_type`);
  `null` = до питання не дійшли взагалі (`duplicate`, нечитабельний файл).
- **`create_subject_object` -- НЕ той самий прапорець, що
  `subject.person_complete`.** Це дві незалежні осі, і читати треба обидві:
  `subject_kind` каже, ЧИ ТРЕБА об'єкт і в якому реєстрі; `person_complete` --
  чи вставиться конкретний рядок `people` (їхні `last_name`/`first_name` --
  NOT NULL). Кон'юнкцією їх робити не можна: у техніки прізвища немає за
  визначенням, тому `person_complete: false` для неї -- норма.
- **Статус документа від `none` не псується.** Примусове рев'ю там означало б,
  що кожен нормативний документ назавжди висить у черзі без жодної дії, яку
  людина може виконати.

## 2. Що змінилось у нас через їхню схему

- **Поля з `db_target: additional_info` тепер стають окремими фактами.** У
  `facts` немає JSON-колонки, а завантажувач вставляє лише `value_code`, тому
  посада, мета відрядження, номер і дата наказу **мовчки губились**. Тепер
  поле в схемі може оголосити `dimension: <код>`, і воно йде окремим рядком
  `facts`. Коди: `position` (уже насіяний у них), `deployment_org`,
  `deployment_days`, `deployment_purpose`, `order_date`, `order_number`,
  `leave_days`, `leave_actual_return`, `unit_to_report`.
- **`facts.confidence` заповнюється.** Не ймовірність, а порядок довіри до
  СПОСОБУ отримання: `matched` 0.9, `derived` 0.8, `llm` 0.6,
  `llm_split_vote` 0.3, зі стелею за станом морфології (`not_a_name` 0.3,
  `inflect_failed` 0.4, `no_morphology` 0.5, `ambiguous_case` 0.7).
  Впевненість факту = мінімум по полях, що його утворюють.
- **`source_kind`** визначається за фактом інжесту, не за розширенням:
  сканований PDF (сторінки без текстового шару пішли в OCR) це `photo`, PDF з
  текстовим шаром -- `electronic`.
- **`--reprocess`**: документ, який пішов у `unresolved` через відсутню схему,
  раніше назавжди повертав `duplicate` (його хеш уже в індексі). Після
  додавання схеми його тепер можна перепрогнати.

## 3. Питання й попередження до команди БД

Впорядковано за наслідками, не за складністю виправлення.

**Стан на 11.08.2026** (їхня відповідь -- `response_to_db_handoff_notes.md`,
наша -- `response-to-db-team.md`): п. 2 ЗАКРИТО -- вони додали
`unresolved -> review_queue.queue_type = 'unknown_type'` і прибрали створення
фантомної особи з трьох `None`. Також додали `documents.domain` і
`documents.pipeline_meta` (JSONB) -- це закриває більшу частину розділу 6.
Решта пунктів чинна.

1. **Ідентичність особи -- і роздування, і злиття.** `get_or_create_person`
   зіставляє за точним `canonical_name`, а `object_aliases.alias` UNIQUE
   глобально; `resolve_or_create_object` у них написана, але не викликається,
   тому `object_aliases` не наповнюється взагалі.
   *Роздування:* прізвище, що лишилось у відмінку джерела, дає другий об'єкт
   на ту саму людину. ВИПРАВЛЕНО в нас: блокерами `confirmed` тепер є не лише
   `inflect_failed`/`not_a_name` (вони й раніше давали `needs_review`), а й
   `no_morphology` (pymorphy3 недоступний -- тоді НЕ нормалізовано жодного
   ПІБ) та `ambiguous_case` без свідчень про відмінок. Лишається шлях
   "відсутнє по батькові": `canonical_name` з двох токенів не збігається з
   тим самим іменем із трьох.
   *Злиття, і воно виправляється тільки в них:* двоє однофамільців з
   однаковим ПІБ стають ОДНИМ об'єктом, бо дискримінатора немає.
   `people.service_id`, `rnokpp`, `birth_date` існують, але не пишуться й не
   порівнюються, а в бланках цих реквізитів немає. Це занижує підрахунок і
   змішує факти двох людей.

   **Доповнено 13.08.2026 (наш бік оцінив, що МОЖЕ зробити -- відповідь:
   нічого понад уже зроблене).** LEAVE-012 еталона (`unknown_person`) виходить
   `confirmed`, бо з документа відсутність особи в реєстрі невідома й
   невідомою лишиться: бланк не знає стану реєстру. Реєстру осіб у нас немає
   як даних (`dictionaries/` містить лише `military_rank`, `leave_type`,
   `fact_type_registry`, `domain_keyphrases`), а `registry: person` у схемах
   оголошений і не реалізований. Ми вже віддаємо весь потрібний вхід:
   `subject.person_alias` (канонічний рядок для `resolve_or_create_object` /
   `object_aliases`) і `subject.person_complete`.

   **Прошу з вашого боку, конкретно:**
   а) викликати `resolve_or_create_object` з `subject.person_alias` -- без
      цього `object_aliases` лишається порожньою й зіставлення йде за точним
      `canonical_name`;
   б) якщо об'єкт СТВОРЮЄТЬСЯ (а не знаходиться), не залишати документ
      `confirmed` мовчки: додати рядок у `review_queue` з новим
      `queue_type` (пропоную `new_person`) і позначку на самому об'єкті
      "особа не підтверджена". Причина -- шляху видалення особи в
      завантажувачі немає, тобто помилку неможливо відкотити;
   в) сказати, чи ви хочете, щоб ознаку "нова особа" віддавали МИ. Ми
      можемо, але лише якщо отримаємо номінальний список частини як дані --
      питання до командира вже сформульоване
      (`open-questions.md`, розділ «Реєстр осіб»).
2. **`unresolved` не просто не попадає в чергу -- він не завантажується
   взагалі.** До рядка з `review_queue` виконання не доходить: у
   `unresolved`-записі `subject` порожній, тому `get_or_create_person(None,
   None, None)` дає `canonical_name = ''` і вставку в `people` з
   `last_name = NULL` при NOT NULL -- транзакція відкочується цілком. Тобто
   жоден документ невідомого типу не має ні факту, ні рядка в `documents`, ні
   рядка в черзі. Ми віддаємо для нього `review_queue: unknown_type`, у них цей
   `queue_type` у CHECK уже є.
3. **`review_queue.queue_type` хардкоджений.** Вони пишуть
   `'unconfirmed_fact'` для будь-якого `needs_review`, ігноруючи наш
   `review_queue`. Через це `handwritten` (фото/скан) не відрізняється від
   помилки на електронному документі, хоч розбирати їх треба різними
   інструментами.
4. **`facts.confidence` не вставляється.** Колонка є, значення ми віддаємо,
   у `INSERT` її немає. Без неї неможливо відсортувати чергу рев'ю за
   найгіршими записами.
5. **`valid_from` факту звання беруть із дати початку відрядження.**
   `first_fact.get("date_start")` -- звання не почалось у день відрядження.
   Для `validity_model: current_state` коректніше `document_date` або NULL.
6. **Неправильний тип документа, і ризик подвійного обліку в майбутньому.**
   (Подвійного обліку СЬОГОДНІ бути не може: схеми рапорта не існує, у
   `schemas/` лише два шаблони.)
   `TEMPLATE_TO_DOC_TYPE` мапить наш `leave_ticket` на їхній `vacation_report`
   (рапорт на відпустку). Це два РІЗНІ документи одного епізоду: рапорт --
   заявка, відпускний квиток -- виданий документ. Якщо обидва потраплять у
   базу, та сама відпустка порахується двічі. Треба або окремий
   `document_type` для квитка, або таблиця зв'язку документ->документ (її
   зараз немає).
7. **`people.last_name` / `first_name` NOT NULL.** Ми віддаємо
   `person_complete: false`, коли прізвища чи імені немає -- це не запис із
   прогалиною, а падіння вставки. Потрібне рішення: пропускати такі документи
   в чергу чи послабити NOT NULL.
8. **`dimensions.name` для нових вимірів.** `get_or_create_dimension` бере
   назву з `FACT_TYPE_LABELS`, а для невідомого коду ставить сам код. Вісім
   наших нових кодів там відсутні (`position` уже насіяний, тому його це не
   стосується), тож у таблиці з'являться рядки з назвою "deployment_org".
   ВИПРАВЛЕНО в нас наполовину: усі 8 кодів тепер зареєстровані в
   `dictionaries/fact_type_registry.yaml` з `label` і `validity_model` (до
   цього реєстр не завантажувався жодним рядком коду, тож ми віддавали факти,
   для яких навіть на нашому боці не було сказано, чи вони `ranged`,
   `current_state` чи `permanent_event`). Лишається їхня частина: читати
   назву звідти або додати у `FACT_TYPE_LABELS`.
9. **`documents.status` -- вони вже відповіли кодом.** `unresolved` ->
   `failed`, усе інше -> `extracted`, з коментарем "status -- стадія
   КОНВЕЄРА, а не статус запису". Тобто `confirmed` і `needs_review` у
   `documents` не розрізняються зовсім, і єдина ознака "чекає людину" --
   наявність рядка в `review_queue`. Питання перефразовується: погоджуємось,
   що склеювання допустиме?

## 4. Знайдене верифікацією проти їхнього коду (нове)

Усе нижче -- **тихо неправильне**, а не падіння: CHECK і NOT NULL це пропускають.

10. **`documents.source_kind` заповнюється літералом `'electronic'`**, наш
    `source_kind` не читається. Кожне фото зайде в базу як born-digital.
    Виправляється тільки в них.
11. **`documents.source_id` завжди `unit_export`** -- походження документа
    (`mobile_photo` для фото) втрачається, хоч ми його знаємо.
12. **Чинності фактів немає в самій схемі.** У `facts` **немає колонки
    `superseded_by`** взагалі, `version` завжди 1, жодного `UPDATE` у
    завантажувачі немає. Для `validity_model: current_state` (`rank`,
    `position`) це означає N одночасно чинних звань на людину без
    детермінованого способу вибрати останнє. Наші `facts[].status: "current"`
    і `superseded_by_document_id` -- мертві поля контракту.
13. **`--reprocess` не роздуває базу, а заморожує помилку.** Хеш той самий ->
    `ON CONFLICT (checksum) DO NOTHING` -> `already_existed` -> ранній вихід.
    Тобто виправлена версія документа **не потрапляє в БД ніколи**: перший,
    помилковий прохід уже зайняв checksum, а режиму оновлення немає. Це
    стосується прямо нашого сценарію "додали схему -> перепрогнали".
14. **`facts.value` -- одна текстова колонка на чотири різні типи**: код
    категорії (`'soldier'`), число (`'10'`), дата (`'2025-04-10'`), вільний
    текст. `dimensions.value_type` захардкоджено `'text'` навіть для дат і
    чисел, а `dimension_values` порожня й не заповнюється -- тобто мітки
    «рядовий» для коду `soldier` у базі немає ніде, і чатботу нічим її взяти.
15. **`order_number` / `order_date` за суттю не виміри стану людини.** Ми
    заводимо реквізити документа в `dimensions` і пришпилюємо їх до
    `object_id` бійця з `valid_from IS NULL`. Правильне місце -- `documents`,
    де таких колонок немає. Питання: додаєте колонки, чи лишаємо як факти?
16. ~~**`object_kinds` не має виду `unit`**~~ -- **ЗАКРИТО 13.08.2026: вид
    `unit` додано на нашу пропозицію.** Він уже входить у закритий перелік
    `pipeline/subject_kind.py:KNOWN_SUBJECT_KINDS`. Лишається наше:
    `registry: military_unit` (`destination_org`, `unit_to_report`) поки що не
    робить із частини окремий об'єкт -- значення й далі йде текстом у
    `facts.value`, бо `subject` плаский і тримає ОДНОГО суб'єкта на документ.
    Вид суб'єкта відпускного квитка -- `person`; частина в ньому -- адресат, не
    суб'єкт. Окрема задача, не вирішується оголошенням виду.
17. **Факт звання зберігається як `unconfirmed`**, бо його `status`
    успадковується від основного факту документа. Але саме звання зчитане
    детермінованим збігом із довідником (`confidence` 0.9). Якщо запити
    читають лише підтверджені факти, чинне звання людини для них не існує.
18. **`date_range_error` вони не читають.** Ми навмисно лишаємо
    `date_start > date_end` у виході, щоб людина це побачила; завантажувач
    вставляє такі дати без перевірки -> `facts_check` валить транзакцію
    (документ падає повністю, але ізольовано -- окреме з'єднання на документ).

## 5. Виправлено на нашому боці за результатами верифікації

- **Похідні (`dimension:`) факти більше не завжди `confirmed`.** Умова була
  тотожно True, тому документ зі статусом `needs_review` кладав у базу
  підтверджені факти, яких ніхто не переглядав. Тепер успадковують
  підтвердження основного факту.
- **`priority: deferred` більше не знижує критичність поля.** Схема, написана
  поетапно (поле основного факту поки `deferred`), віддавала `confirmed` факт
  зі значенням `null`.
- **Шаблон, обраний LLM, не дає `confirmed`** і йде в чергу як
  `unknown_type` з `review_reason: template_by_llm`.
- **LLM не питають про шаблон, коли не збігся жоден анкор** -- раніше
  документ без схеми (книга обліку техніки, рапорт) віддавався моделі,
  обмеженій переліком чужих шаблонів, і її вибір приймався як остаточний.
- **`no_morphology` і `ambiguous_case` блокують `confirmed`.**
- **Реєстр типів фактів завантажується**, і всі коди з `dimension:` у ньому є.
- **Схеми валідуються при завантаженні**: невідомий режим `extraction`,
  відсутній обов'язковий ключ, невалідний regex, невідомий `db_target` --
  явна помилка до обробки першого документа, а не тихий `null` чи `KeyError`
  посеред `process_file` (де запис у сховище ще не створений).

## 6. Що ми вже віддаємо, а завантажувач не читає (пропозиції для команди БД)

Перевірено grep-ом по `ai_secretary_loader.py`, не по пам'яті. З кожного факту
читаються рівно п'ять ключів (`fact_type`, `value_code`, `date_start`,
`date_end`, `confirmed`); з шапки -- сім (`status`, `file_hash`, `uploaded_at`,
`template`, `review_reason`, `subject`, `facts`). Усе інше ми рахуємо й
зберігаємо, а в базу воно не доходить.

Це не докір: більшість пунктів нижче -- це можливість, про яку вони могли не
знати. Упорядковано за користю для кінцевого запиту, а не за складністю.

### 6.1. Класифікація

1. **`domain`** (`leave` / `deployment` / `equipment` / `staffing`) -- **не
   згадується в завантажувачі жодного разу**. Це найдешевша втрата: доменна
   класифікація вже порахована по кожному документу, а споживача не має. У
   `documents` немає колонки для неї. Пропозиція: додати `documents.domain`
   (або зв'язок на довідник домену) -- це дає групування й фільтрацію
   документів без парсингу тексту.
2. **`identification`** -- яким способом визначено шаблон (`anchors` / `llm` /
   `forced`), бал, і другий кандидат за балом. Практична цінність: шаблон,
   визначений моделлю, а не анкорами, вимагає іншого ставлення (у нас він тепер
   ніколи не дає `confirmed`). Зараз у базі неможливо відрізнити впевнену
   ідентифікацію від здогадки.
3. **`subject_kind` + `create_subject_object`** -- **ВІДДАЄМО з 13.08.2026**
   (було: пропозиція; див. розд. 1.1 вище). Завантажувач і далі жорстко бере
   `object_kinds.code = 'person'`, тому вид зараз не читається, а
   `create_subject_object` не перевіряється -- тобто **нормативний документ,
   у якого суб'єкта немає, все одно створить об'єкт-людину в реєстрі**, і
   шляху видалення в завантажувачі немає. Це найдорожча з нечитаних ознак:
   решта -- втрачена інформація, а ця -- вигаданий рядок у `objects`.
   Мінімальна зміна на їхньому боці: `if not meta.get("create_subject_object"):
   пропустити resolve_or_create_object`, і `kind_id` шукати за
   `meta["subject_kind"]` замість літерала.

### 6.2. Довіра до запису

4. **`facts[].confidence`** -- колонка `facts.confidence` існує, значення ми
   рахуємо, у `INSERT` її немає. Без неї чергу рев'ю неможливо відсортувати за
   найгіршими записами -- людина дивиться документи в довільному порядку.
5. **`field_provenance`** -- по кожному полю: спосіб отримання (`matched` /
   `llm` / `derived` / `no_value` / `llm_error:*`), критичність, чи вирішене,
   стан морфології, `confidence`. Це готовий матеріал для 5%-аудиту: видно не
   лише ЩО неправильно, а ЯКИМ шляхом здобуто. Місця в схемі немає; варіант --
   JSONB-колонка на `documents` або таблиця `fact_provenance`.
6. **`unknown_critical_fields` / `unknown_fields`** -- які саме поля не
   зчиталися. Зараз `review_queue.fact_id` завжди NULL, тому людина бачить "є
   непідтверджений факт" без указання, що саме перевіряти.
7. **`confirmed_empty_fields`** -- поле порожнє, бо документ ПРЯМО так каже
   ("військові перевізні документи -- не видавались"). Це доказ, а не прогалина,
   і зараз ці два випадки в базі не відрізняються.
8. **`not_implemented_fields`** -- поля, які схема оголосила, але ми поки не
   витягуємо (`priority: deferred`). Дозволяє їм не вважати відсутність
   значення помилкою розпізнавання.
9. **`date_range_error`** -- ми навмисно лишаємо суперечливі дати у виході, щоб
   людина побачила; завантажувач вставляє їх без перевірки, і `facts_check`
   валить транзакцію. Прочитати цей ключ дешевше, ніж ловити виняток.
10. **`warnings`** -- зокрема "пропущено N сторінок без текстового шару" і
    "неповний ПІБ". Друге прямо попереджає про падіння вставки в `people`.

### 6.3. Маршрутизація й повнота

11. **`review_queue`** -- ми віддаємо готовий `queue_type` з їхнього ж CHECK
    (`unknown_type` / `unconfirmed_fact` / `handwritten` / `qa_sample`), а вони
    хардкодять `'unconfirmed_fact'`. Через це рукописне/фото не відрізняється
    від помилки на електронному документі.
12. **`source_kind`** -- `electronic` / `photo`, визначене за фактом інжесту
    (сканований PDF -> `photo`). Вони передають літерал `'electronic'`.
13. **`subject.person_alias`** -- канонічний рядок для
    `resolve_or_create_object` / `object_aliases`. Функція в них написана й не
    викликається, тому `object_aliases` порожня, а зіставлення особи йде за
    точним `canonical_name`.
14. **`subject.person_complete`** -- прямий попереджувальний прапорець про
    NOT NULL у `people`.
15. **`extra_subjects`** -- додаткові особи документа (командир, що
    затверджує). Поки в базу не йдуть свідомо (`people` приймає одну особу на
    документ), але значення вже витягнуті й не губляться.
16. **`facts[].additional_info`** -- те, що не стало окремим виміром. У `facts`
    немає JSON-колонки, тому ми перевели головне в `dimension:`-факти; решта
    лишається лише у файлі.
17. **`facts[].source_field`** -- з якого поля схеми походить похідний факт.
    Потрібне, щоб після виправлення схеми знайти й перезаписати саме ці факти.
18. **`id`** (наш uuid) і **`storage_key`** -- зворотне посилання з рядка в БД
    на файл-джерело у сховищі. Зараз зв'язок лише через `checksum`.


## 7. Зв'язок документ -> документ: що ми віддаємо з 13.08.2026

`architecture-proposal.md` розд. 2 п.4 -- погоджене рішення: «Окрема таблиця
зв'язків документ→документ (скасовує/змінює) -- наказ, що скасовує чи змінює
інший наказ, інакше людина назавжди лишається зі старим статусом». У вашій
схемі такої таблиці немає, і в `facts` немає `superseded_by` (п.12 вище).
Наші `facts[].status: "current"` і `superseded_by_document_id` -- мертві поля
контракту.

**Що з'явилось у контракті з нашого боку.** Новий ключ у `meta` (і в
`build_record`), заповнюється з самого тексту документа:

```
meta["document_links"] = [
  {"link_type": "supersedes",
   "target_document_number": "157" | null,
   "source_field": "supersedes_document_number" | "supersession_note",
   "evidence": "<рядок, як у документі>",
   "method": "matched"}
]
```

Порожній список -- норма (58 з 60 документів еталона). Замір по всіх чотирьох
корпусах: 3 документи з ознакою, 0 хибних позитивів.

**Чого ми зробити НЕ можемо, і чому це саме ваш бік:**

1. Скасований документ пари не містить **жодної** ознаки -- він не може знати,
   що його скасують (перевірено на LEAVE-013, LEAVE-015, TRIP-013). Закрити
   старий факт можна лише запитом ПО ВСІХ документах; ми обробляємо по одному
   файлу.
2. `target_document_number` буває `null`: LEAVE-014 друкує «(перервана,
   відкликаний з відпустки)» без номера. Пару тоді шукають за особою й датами.
3. **Номер НЕ ідентифікує документ.** LEAVE-015 і LEAVE-016 мають однаковий
   `DOC_NUMBER` = 157 (анульований квиток і новий, виписаний тим самим
   номером; дати видачі 17.05 і 20.05). Тому в таблиці зв'язків цільовий
   документ треба **шукати** трійкою (номер + особа + дата видачі), а не
   тримати зовнішнім ключем на номер.

**Прошу з вашого боку:** таблицю зв'язків документ→документ і колонку
`superseded_by` (або версіонування) на `facts`. Без другого навіть знайдена
пара нічим не закривається.

## 8. Нове в контракті `meta` з 13.08.2026 (коротко)

Обидва ключі присутні ЗАВЖДИ (як і решта `blank_meta`), порожні значення --
норма:

| ключ | тип | що означає |
|---|---|---|
| `consistency_problems` | `{поле: причина}` | значення суперечить іншим полям документа (`consistency_error`) або не має чим підтвердитись (`unverifiable_dependency` -- напр. тривалість відпустки без дат початку й кінця). Поле при цьому НЕ вважається вирішеним, і похідний факт із нього в базу не йде |
| `document_links` | список | див. розд. 7 |

Плюс нові значення в `field_provenance[поле]["method"]`, які раніше були
неможливі, бо значення приймалось беззастережно:
`printed_label_in_value`, `type_mismatch`, `blank_value` (значення з верстки
бланка не пройшло перевірку -- `extract.validate_block_value`) і
`ungrounded_llm_value` (модель віддала значення, якого в документі немає --
`extract.ground_llm_value`). Усі чотири означають те саме для вас: поле не
вирішене, сирий текст лишається в `unresolved_values`.
