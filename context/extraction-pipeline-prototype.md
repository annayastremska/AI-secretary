# Пайплайн екстракції полів з документів

Реалізація кроку 2 з `architecture-proposal.md` ("Обробка вхідних документів") — не окрема ініціатива, а робочий код погодженого підходу (regex-first + LLM зі схемою для шумних полів), перевірений на реальних зразках з `data/samples/`.

**Запускається локально, без Colab:** `python run_pipeline.py`. Код: `pipeline/*.py`, схеми `schemas/*.yaml`, довідники `dictionaries/*.yaml`, конфіг `config.yaml`.

**Межі цієї частини роботи:** файл на вході → структурований запис у локальному сховищі. Зовнішнє сховище (MinIO) і база даних — не тут; вихід спроєктований так, щоб їх можна було приєднати пізніше, але жодного коду під них у цій частині немає.

## Мета

Перетворити вхідний файл (фото/скан бланка або `.docx`) на структурований запис для БД: `subject` (особа), `facts` (тип, значення, діапазон дат, `additional_info`), `document_meta` (повна YAML-шапка з провенансом кожного поля). Двигун генеричний — новий тип бланка додається новим `schemas/<template>.yaml`, без нового Python-коду.

## Потік

```
файл (.docx / .pdf / фото) з папки-приймача (config: paths.input_dir)
  → хеш вмісту (SHA-256) → якщо такий уже оброблено: status=duplicate, далі не йдемо
  → інжест (pipeline/ingestion/ingest.py)
      docx  → параграфи + клітинки таблиць + header/footer (без OCR)
      pdf   → текстовий шар: блоки З КООРДИНАТАМИ через PyMuPDF (без OCR)
              скан у PDF: рендер сторінок → OCR
      фото  → Surya OCR → впорядкування блоків за bbox (зверху-вниз, зліва-направо)
  → визначення ШАБЛОНУ (pipeline/identification.py)
      скоринг усіх схем за їхніми блоками identification: (заголовок ×5, якорі ×2)
      нічия або нижче min_score → LLM-тайбрейк (grammar, з явним "unknown")
      нічого → status=unresolved, у чергу на розгляд, без спроби екстракції
  → екстракція (pipeline/extraction/extract.py + schema_grammar.py)
      1) детермінований прохід: regex / значення-перед-лейблом / токенізація звання+ПІБ
      2) прогалини → групи по batch_size → grammar-constrained LLM-виклик на групу
  → нормалізація (pipeline/normalization/normalize.py): дати → ISO, категорія → {code,label}
  → збірка (pipeline/build_record.py): subject + facts[] + field_provenance
  → вихід: YAML-шапка + текст → .md у локальне сховище (data/output)
  → сам вхідний файл переноситься з приймача: data/processed/<дата>/ або,
    якщо unresolved, data/failed/<дата>/ -- щоб приймач спорожнявся
```

Папка-приймач сканується **не рекурсивно**, і про пропущене (підпапки, файли
непідтримуваного типу) CLI повідомляє явно — раніше такі файли зникали
безслідно, і людина, що поклала папку з документами, бачила лише «не знайдено
файлів» без пояснення. Файл, переданий явно через `--input`, **не**
переміщується: інакше прогін на `data/samples/` виносив би зразки з
репозиторію.

## Очікування (інваріанти)

- **Вихід існує завжди** — `confirmed` / `needs_review` / `unresolved` / `duplicate`, ніколи голий крах без сліду.
- **Категоріальні поля** — завжди `{code, label}` з довідника, незалежно від того, яким шляхом отримані (LLM під grammar видає код, детермінований шлях — алиас; `resolve_category` приводить обидва до однієї форми).
- **`confirmed` рахується лише по КРИТИЧНИХ полях** — некритична прогалина (вільнотекстовий опис) не блокує запис, інакше в черзі ручного рев'ю опинявся б кожен документ і черга стала б безглуздою.
- **Збій одного LLM-виклику ізольований** до своєї групи полів; детерміновані значення й інші групи не втрачаються.
- **Провенанс кожного поля** (`matched` / `llm` / `no_value` / `llm_error:*` / `deferred` + критичність) зберігається в записі — без цього неможливо ні таргетувати 5%-аудит, ні перерахувати документи після виправлення схеми.

## Ключові технічні рішення

**Ідентифікація на рівні ШАБЛОНУ, не домену.** Схема прив'язана до `template`, а один домен містить багато бланків — перевірка "домен схеми == домен класифікації" не відрізнить "правильний домен, неправильний бланк". Кожна схема сама описує, як її впізнати (блок `identification`), тому вибір схеми став частиною пайплайна, а не ручною дією людини в діалозі завантаження. Це те, що робить пакетний режим (папка-приймач із `project-expectations.md`) можливим. Рівний бал двох схем — це `ambiguous`, а не перемога того, хто перший у списку.

**Гібрид: детермінований прохід, потім LLM лише на прогалини.** Regex/label-пошук дешевий і детерміністичний там, де верстка бланка стабільна й підтверджена на реальному зразку. LLM підключається вибірково.

**Групи по `batch_size` полів, не "по одному" й не "все одразу".** Один виклик на поле — багато викликів (повільно на CPU); один виклик на весь документ — збій одного виклику втрачає всі LLM-поля разом. Групи ізолюють збій до кількох полів.

**Два види прогалин з різним контекстом.** Локалізовані (місце знайдено, не вдався лише розбір рядка — напр. прізвище не ВЕЛИКИМИ літерами) отримують у промпт **лише цей рядок**: на реальному прогоні це 34 символи проти 227 символів повного тексту, а на справжньому документі різниця ще більша. На CPU довжина промпту — головна стаття витрат. Нелокалізовані (місце не знайдено взагалі) отримують повний текст, бо іншого немає. Кандидат, відхилений denylist-ом, підказкою **не** стає — це саме неправильний текст, і передавати його означало б підштовхувати модель до тієї самої помилки.

**JSON Schema → GBNF grammar замість вільного тексту.** Категоріальне поле фізично не може отримати неіснуючий код. Кожне поле nullable навмисно — інакше модель під grammar змушена вигадати значення там, де його немає. Grammar гарантує **форму**, не правдивість.

**Дедуплікація за хешем вмісту.** Ручний експорт людиною з АСКОД/Армія+ гарантує повторні завантаження того самого документа; подвійні факти подвоюють саме ті підрахунки, заради яких будується система. Реалізовано як append-only індекс `index/processed.jsonl` (хеш вмісту → ключ запису).

**5%-вибірка на аудит — детерміністична від хешу**, не `random`: те саме рішення при повторному прогоні того самого документа, жодного стану генератора між запусками.

## Виправлені баги (усі підтверджені прогоном, не гіпотетичні)

### За зовнішнім код-рев'ю (08.08.2026)

Крахи, що валили ВЕСЬ пакетний прогін, а не один документ:
- `int(year)`/`int(day)` без перевірки на цифри: grammar не обмежує дати
  шаблоном цифр, тож `{"day": "невідомо"}` від LLM кидало `ValueError` вгору;
- `KeyError` на неповному записі в `domain_keyphrases.yaml`;
- виклик LLM під час ідентифікації шаблону без `try/except`;
- відсутність `try/except` навколо обробки одного файлу в батчі — тепер це
  остання лінія захисту гарантії «вихід існує завжди».

Мовчки неправильні значення (найгірший клас для проєкту, де людина
підтверджує факти):
- **нічия при self-consistency** тепер видима як `llm_split_vote`: переможець
  при рівних голосах визначався порядком у списку, а виглядав як одноголосний;
- **неоднозначний лейбл** (два схожі лейбли в документі — звання заявника й
  звання командира) більше не «беремо перше входження», а `ambiguous_label`;
- **денай-лист** порівнював кандидата точним рівнянням, тому багаторядковий
  кандидат (заголовок + номер наступним рядком) мовчки проходив — тепер
  перевіряється кожен рядок;
- **підказки різних полів** склеювались в один контекст без прив'язки, і LLM
  могла приписати підказку одного поля іншому — тепер групування за самою
  підказкою;
- **прізвище видалялось зі списку імені за значенням, не позицією**: дубльований
  OCR-токен прибирав обидва входження й зсував по батькові в поле імені;
- **підрядкові збіги без межі слова** в анкерах схем і фразах доменів;
  межа вимагається на початку, але не в кінці — інакше зламались би свідомі
  стеми довідника («відрядж», «особов»);
- **нічия домену** взагалі не детектувалась — брався перший за порядком YAML.

Покриття й інжест:
- дати без «р./року» і числові (`15.05.2025`, `01/06/2025`) не розпізнавались
  узагалі — систематична прогалина, не окремий випадок;
- дедуплікація header/footer через `id()` без сильних посилань — той самий
  клас бага, який уже був знайдений і виправлений для клітинок таблиць;
- рішення «текстовий шар чи скан» у PDF приймалось на весь документ, тому
  сторінка-скан усередині текстового PDF ніколи не йшла в OCR;
- вкладені таблиці всередині клітинок не читались;
- багатосторінковий TIFF читався лише першим кадром.

Інше: мертвий LLM-фолбек класифікації домену прибрано (template-level
tie-break у `identification.py` — і є той LLM-шлях); `inference_parallel`
піднято в конфіг; `config.yaml` тепер шукається і відносно кореня проєкту, а
не лише CWD (запуск із планувальника мовчки падав у дефолтний режим);
stdout/stderr примусово UTF-8 (редірект у файл на Windows міг кинути
`UnicodeEncodeError` ПІСЛЯ успішної обробки); лок у `LlamaClient`; верхні межі
версій у `requirements.txt`; `download_model.py` більше не вибирає файл
алфавітно й обробляє обрив мережі.

### Раніше


- **`regex`-поля не мали LLM-фолбеку взагалі** — найкрихкіший режим (паттерн під конкретну верстку) був єдиним без страховки. Тепер їхні провали теж ідуть у прогалини.
- **`rank` мав дві різні форми** залежно від шляху: `{code,label}` з довідника проти `'soldier'` (рядок) від LLM — у БД це два різні типи в одній колонці. Виправлено `resolve_category`.
- **Текст клітинок docx дублювався 4-6 разів**: `python-docx` повертає об'єднану клітинку окремо для кожної колонки сітки. Тіло реального посвідчення: 104 → 60 рядків. Це не косметика — роздутий текст це довший промпт, тобто прямі витрати часу на CPU.
- **Перша версія цього ж фіксу зламала дати**: дедуплікація через `id()` на lxml-елементі ненадійна, бо проксі може бути зібраний GC, а `id` перевикористаний іншим елементом. Виправлено утриманням сильних посилань.
- Раніше: багаторядкове значення перед лейблом обрізалось до одного рядка; заголовок документа потрапляв у поле "прізвище"; прізвище малими літерами зсувало `given_name`/`patronymic` на тихо неправильні значення; схема/довідники визначались за назвою файлу; `.lstrip(prefix)` замість зняття префікса-рядка; docx header/footer не читались.

## Локальний запуск

```bash
python run_pipeline.py                      # уся папка data/inbox
python run_pipeline.py --input <файл>        # один документ
python run_pipeline.py --no-llm              # лише детермінований прохід
python run_pipeline.py --template leave_ticket   # примусова схема (для тестів)
python run_pipeline.py --dry-run             # нічого не зберігати
```

Пайплайн **працює й без моделі** (`--no-llm` або `llm.enabled: false`) — детермінований прохід дає результат, прогалини чесно позначені. Це корисно для швидкої перевірки логіки, але це НЕ повний режим: поля з `extraction: llm` (напр. `destination_points`, `purpose`) лишаються порожніми, тому запис виходить `needs_review`, а не `confirmed`.

### Заміряно на цьому ноутбуці (CPU, MamayLM-12B Q4_K_M, `n_gpu_layers: 0`)

| що | час |
|---|---|
| завантаження ваг (6.8 ГБ, **одноразово на процес**) | ~257 с |
| документ із 1 LLM-групою (3 поля, повний текст у контексті) | **~56 с** |
| той самий документ "з нуля" разом із завантаженням ваг | ~313 с |

Тобто папка з 20 документів ≈ 257 с + 20 × 56 с ≈ 21 хв, а не 20 × 313 с — саме тому `build_resources` створює клієнта один раз на процес, а не на кожен файл. Документ із більшою кількістю прогалин коштує пропорційно більше груп.

Якщо 12B заповільний — є менша офіційна `MamayLM-Gemma-3-4B-IT-v1.0-GGUF` (~2.5 ГБ), зміна одного рядка в конфізі. `n_gpu_layers: -1` віддає шари GPU, якщо він з'явиться — код той самий.

## Вихід, придатний до приєднання сховища й БД пізніше

Ключі пласкі й передбачувані (`documents/<domain>/<id>.md`), а вся витягнута
інформація лежить у YAML-шапці одним об'єктом (`subject`, `facts`,
`field_provenance`), не розкидана по тілу файлу. Тому `data/output` можна
перелити в зовнішнє сховище або розкласти в таблиці, коли за це візьметься
відповідна частина команди — без змін у самому пайплайні.

`facts` навмисно список, хоч зараз завжди з одного елемента: один документ
може дати кілька фактів (кілька зупинок у посвідченні, рядки книги обліку),
і форма запису вже це передбачає.

## Обмеження, що свідомо лишаються

- **Жоден реальний заповнений `leave_ticket` не перевірений** (лише порожній шаблон), на відміну від `deployment_certificate`.
- **Один документ, один прогін — не статистика.** Те, що LLM правильно витягла 3 поля з одного посвідчення, не є виміряною точністю: для цього потрібна вибірка документів і саме той механізм ручної звірки, що описаний в `architecture-proposal.md` розд. 4.5.
- **Один документ → один факт.** `facts` уже список (форма запису правильна), але екстракція `multiple: true` полів не реалізована. Для `deployment` це зупинки на звороті — у реальному зразку вони **заповнені** ("Вибув із в/ч UNIT-0252, м. Київ" / "Прибув до смт Десна"), тобто дані є й їх можна дістати. Для домену `equipment` (книга обліку техніки) багато рядків на документ буде нормою, не винятком — це наступна велика переробка.
- **`object_ref`-поля не резолвляться** проти реєстру осіб/частин — немає заповненого реєстру. Ототожнення осіб навмисно НЕ автоматичне: вгадувати "той самий Іваненко чи інший" за ПІБ означало б саме той клас тихої помилки, від якого застерігає `architecture-proposal.md` розд. 7.
- **Морфологічна нормалізація ПІБ** реалізована через `pymorphy3` (словник uk):
  «БЕВЗЕНКА Юстима Едуардовича» → «БЕВЗЕНКО Юстим Едуардович», регістр джерела
  зберігається. Статус іде в провенанс (`morphology`): `normalized` /
  `already_nominative` / `not_a_name` / `inflect_failed` / `no_morphology` —
  останні три означають, що значення лишилось у відмінку джерела, і це видно,
  а не виглядає як успішна нормалізація. Український словник pymorphy3 датований
  2022 р., тож на рідких прізвищах якість не гарантована — саме тому статус
  зберігається пофайлово.
- **Багатосторінкові документи** як єдина логічна одиниця не підтримуються: кожен файл обробляється незалежно.
- **5%-вибірка на аудит існує лише як позначка в записі** (`review_reason: random_audit`); окремої черги/таблиці немає — це вже частина роботи з БД.
- Colab-ноутбук `notebooks/pipeline_trial_leave_colab.ipynb` **застарів** — він викликає старий API `extract_document`. Канонічний шлях тепер `run_pipeline.py`.

## Зв'язок із рештою проєкту

Це крок 2 з `architecture-proposal.md`, доведений до коду. Питання ліцензій (Surya OpenRAIL-M, MamayLM/Gemma Terms of Use, можливий EAR-ризик) і рішення "рукописне не обробляється автоматично" з `open-questions.md` стосуються цього пайплайна напряму — жодне не вирішене на рівні коду, лише позначене як залежність.

Що потребує відповіді офіцерів (впливає прямо на код): **які поля критичні для підрахунків**. Зараз критичність виводиться з `db_target` (особа, значення факту, дати — критичні; решта — ні), і кожне поле можна перевизначити явним `criticality:` у схемі, але правильний поділ знають лише вони.
