# Архітектурна пропозиція

Явно: Claude/Cowork/Claude Code на жодному етапі — ні розробки, ні продакшн-роботи — не торкаються реальних документів. Уся продакшн-система самостійно розгортана (self-hosted), локально.

## 1. Загальна ідея

Документи → структуровані записи в базі даних. Агреговані/лічильні відповіді — через SQL-запит до бази, не через вільний пошук LLM. Будь-яка відповідь користувачу подається як орієнтир/приблизна оцінка, не точний факт.

## 2. Обробка вхідних документів

1. OCR: друкований текст — **Surya (VLM-based OCR)**, за результатами власного пілоту на 4 реальних документах (порівняно з Tesseract, EasyOCR, PaddleOCR-cyrillic-v3) — точніша за змістом на найважчому реальному кейсі (фото документа з тінями/редагуванням), зокрема зберегла юридично значущі речення, які Tesseract втратив повністю. Два відкриті моменти, що не блокують пілот, але потрібні перед продакшном:
   - **Ліцензія ваги моделі — OpenRAIL-M** (модифікована): безкоштовно для дослідження/особистого використання/стартапів з доходом чи фінансуванням до $5M; ширше комерційне використання потребує платної ліцензії від Datalab. Той самий тип питання, що й у Gemma — потребує окремої юридичної перевірки, не наша компетенція.
   - **Галюцинація — задокументований ризик для VLM-based OCR**, підтверджений і на нашому пілоті: два прогони одного й того ж (важкого) зображення дали різні, обидва сильно вигадані результати — на відміну від детермінованого класичного OCR. Вимагає посиленого варіанту вже запланованої випадкової 5%-перевірки (розділ 3 нижче), а не скасовує її.
   - Рукописні документи **не обробляються автоматично системою** (рішення Анни, за результатами пілоту — жоден з протестованих інструментів, включно з Surya, не показав прийнятної надійності на реальному рукописному зразку; шлях через Transkribus/PyLaia розглядався, але вимагає окремого контракту з Transkribus On-Prem і не має публічного підтвердження умов — розглянути окремо, якщо колись знадобиться).
2. Класифікація в відомий набір категорій: легкий дотренований класифікатор (72-83% проти 53-68% у embedding-similarity, одне рецензоване дослідження). BM25 не доведено кращим за embedding-схожість — лише альтернатива, варта пілотування, не більше.
3. Екстракція полів: regex-first для стандартизованих полів; LLM зі схемою — лише для шумних/вільнотекстових полів (raw-точність LLM і regex статистично однакова, 89.2% проти 87.7%, але LLM має небезпечний режим — тиха підстановка "найпоширенішого" значення замість "невідомо"). Обов'язковий явний статус NULL/NA замість здогадки. **Впевненість ≠ правильність:** випадкова вибірка (~5%) автоматично прийнятих записів усе одно йде на ручну перевірку — інакше рівень помилки невідомий і непомітний (той самий механізм, що в кейсах Horizon/Нідерланди). Пороги різні за важливістю поля: статус/дата/підрозділ (впливають на підрахунки) — суворіше, довільний опис — менш суворо.
4. БД (PostgreSQL): типізовані колонки + JSONB для рідкісних/змінних полів (не EAV). Колонка рівня впевненості на кожному записі; чернеткова таблиця для непідтверджених записів до ручного підтвердження. Історія змін статусу — SCD Type 2 / темпоральні таблиці, з датою завершення саме з тексту документа (не лише "немає закриваючого документа" — це б'ється, якщо закриваючий документ просто ще не оцифрований). Окрема таблиця зв'язків документ→документ (скасовує/змінює) — наказ, що скасовує чи змінює інший наказ, інакше людина назавжди лишається зі старим статусом. **Вирішено (Анна):** для хибного ототожнення особи (identity-merge) дозволено фізичне видалення — виняток із загального append-only принципу реєстру осіб. За замовчуванням: видаляється сам запис ідентичності/ототожнення, а факти (`subject_state`), що спираються на інші, дійсні документи цієї людини, переприв'язуються на правильний `subject_id`, а не зникають разом з видаленням. Потребує підтвердження Анни, якщо механізм має бути іншим (напр. каскадне видалення всіх пов'язаних фактів).
5. **Вирішено (Анна):** копія документа-джерела (фото/скан) — ретенція 30 днів, потім видаляється. **OCR-текст і всі витягнуті факти зберігаються назавжди**, включно з повним текстом медичного діагнозу з довідок ВЛК (не лише резолюцією/висновком) — свідоме рішення Анни. Це обмежує ефект 30-денної ретенції: чутливий вміст документа живе в БД постійно, а не лише у файловій копії. Впливає на обсяг атестації й вимоги до захисту самої БД — вона, а не лише тимчасове файлове сховище, стає постійним носієм чутливого/медичного контенту.
6. Готового фреймворку "все в одному" немає. Docling — уникати (підтверджено зламана кирилична OCR-інтеграція). Haystack — придатний блок для офлайн-класифікації. Paperless-ngx — оцінити як готову основу.
7. Цифрові документи з СЕДО/АСКОД/Армія+ (без API): людина з легітимним доступом експортує документ вручну (кнопка "завантажити" в програмі) → файл потрапляє в папку-приймач/форму завантаження нашої системи → далі той самий автоматичний конвеєр (текстовий шар PDF/DOCX → пряме витягування без OCR; скан-картинка → OCR) → класифікація → екстракція. Єдина ручна дія — сам експорт, не передрук даних. **Уточнити на пілоті:** чи реальний експорт — цифровий файл із текстовим шаром (OCR не потрібен для цієї гілки) чи скан-PDF (OCR потрібен для всього) — суттєво змінює вагу OCR-роботи в проєкті.
8. **Уточнити на пілоті (фото з телефону):** попередня обробка (вирівнювання, обрізка, контраст, тіні) впливає на результат сильніше, ніж вибір OCR-рушія. Також не визначено: багатосторінкові документи, кілька документів на одному фото, змішаний друк+рукопис в одному бланку.

## 3. Відповідь на запит

Агреговані/лічильні запити — фіксований whitelist параметризованих запитів (напр. "порахувати записи де категорія=Х і статус=Y за період Z"); LLM лише обирає, яка форма підходить, і заповнює параметри — ніколи не пише довільний SQL сама (безпечніше, всі можливі відповіді наперед перевірювані). Нестандартні запити, що не підійшли під жодну форму, — окремий, менш строгий шлях (ширший пошук/RAG, явно позначений як нижчої довіри), а не відмова відповідати.

**Значення параметрів від LLM обов'язково резолвляться в контрольований довідник допустимих значень бази** (наприклад, "у відпустці"/"відпустка"/"щорічна відпустка" → один і той самий довідниковий статус). Якщо термін не резолвиться — відповідь "не розпізнав термін", а не мовчазний 0 (0 не можна відрізнити від "нікого немає"). Так само вибір шаблону запиту — з порогом впевненості; нижче порогу — явне "не можу відповісти на це запитання".

Кожна агрегована відповідь показує: сам результат, знаменник (скільки всього записів проаналізовано), кількість виключених/очікуючих підтвердження записів, і дату найактуальніших даних — наприклад "5 із 47; 3 записи очікують підтвердження; дані станом на 24.07". Без цього чернеткова таблиця стає тихим фільтром, що зміщує саме ті цифри, заради яких будується система. Мітка "орієнтир, не точний факт" лишається, але сама по собі недостатня.

## 4. Модель

**За замовчуванням: Apache 2.0 чекпоінт (Qwen до 35B або конкретно Mistral 7B)** — не узагальнювати на всю родину Mistral (є окремі некомерційні моделі, напр. Large 2/Pixtral Large), фіксувати точний чекпоінт і перевіряти саме його ліцензію.

MamayLM (Gemma-похідна) розглядається лише якщо власний тест на наших завданнях покаже вирішальну перевагу в якості — її заявлена перевага (self-reported, незалежно не відтворено) наразі непідтверджена, тож немає сенсу платити непідтвердженим юридичним ризиком (Gemma містить Prohibited Use Policy щодо зброї/кіберзброї, що діє й офлайн; Google — компанія США, кінцевий користувач — іноземна військова організація ⇒ можлива експортно-контрольна (EAR) експозиція) за непідтверджену перевагу. Якщо тест таки покаже вирішальний розрив — тоді окрема юридична консультація по Gemma.

Aya виключено — CC-BY-NC, некомерційна ліцензія.

## 4.5 Оцінка на реальних даних клієнта

Команда не має доступу до реальних документів — отже, реальну точність (OCR, класифікація, екстракція) ніхто з нашого боку виміряти не може. Рішення: постачаємо клієнту локальний оціночний скрипт, який він сам запускає на своїх реальних документах у власному середовищі; скрипт повертає лише агреговані метрики (CER, частка записів у чернетковій таблиці, precision/recall по полях) — самі документи нікуди не виходять.

## 5. Сервер і вартість

Один централізований сервер достатній, якщо модель вміщується на одній GPU (документація vLLM/NVIDIA, джерело не перевірене незалежно). RTX 4060 Ti 16GB: ~$300-425. Повна робоча станція під модель 4-9B: ~$1,500-2,200 (оцінка по компонентах). Більші GPU (24GB, RTX 3090/4090) для більших моделей: $1,200-2,800+, вживаний ринок нестабільний. Це запит на бюджет, що потребує підтвердження. Все ПЗ у стеку безкоштовне — обладнання єдина реальна стаття витрат.

## 6. Контроль доступу та аудит

RBAC за принципом мінімально необхідного доступу, мітки класифікації на ролях, tamper-evident аудит-лог (WORM + hash-chaining, розділення прав запис/видалення) — вимагається НД ТЗІ 2.5-005-99, 2.5-004-99 і узгоджується з НІСТ RBAC/CNSSI 1253. Конкретні ролі — після відповіді військових. Мобільний доступ з особистих телефонів — захист мережевого каналу поза скоупом команди, команда відповідає лише за логін всередині чат-бота. Той самий принцип поширюється на всю інфраструктуру в цілому: фізичне розміщення сервера й мережева сегментація — відповідальність клієнта, команда відповідає лише за програмний рівень.

## 7. Обов'язкова вимога дизайну: людське рев'ю та апеляція

Цивільні прецеденти (Нідерланди — ~26,000 неправомірно звинувачених родин; UK Post Office Horizon — 900+ неправомірних переслідувань) — спільна причина: автоматичний вивід трактувався як істина без людської перевірки й шляху оскарження. Препринт: помилки класифікації потрапляють в агреговані підрахунки систематично, не випадково — не "усереднюються". Позитивний приклад: TAR в e-discovery (рецензоване TREC-дослідження) — recall 76-77% проти ~60% при ручному пошуку, за умови людського нагляду.

Вимога: будь-яка агрегована/підрахована відповідь — з обов'язковим шляхом ручної перевірки/апеляції. Похибку класифікатора переоцінювати періодично саме на систематичну упередженість, не лише середню точність.

## 8. Ризики

- КСЗІ-атестація юридично обов'язкова (Закон "Про державну таємницю" №3855-XII, Постанова КМУ №180) для систем з держтаємницею — не робота команди, виконує Держспецзв'язку окремо.
- Прецеденту немає: перевірено Сяйво/Gemma, MoD Defense AI Center A1 (відгороджує ДЕЛЬТА від AI), Digital Logistics System (звичайна ERP) — проєкт перший у своєму роді.
- Рукописні документи виключені з автоматичної обробки (рішення Анни) — реальний обсяг таких документів у корпусі клієнта та що з ними робити (ручна транскрипція? повне виключення?) — питання для військових, див. open-questions.md.
- Ліцензія Gemma/MamayLM — непідтверджений EAR-ризик (актуально лише якщо тест покаже перевагу над Apache-2.0 варіантом).
- **Ліцензія Surya (модель OpenRAIL-M)** — непідтверджено, чи військова організація підпадає під безкоштовне використання, чи потрібна платна ліцензія Datalab; Surya зараз базовий вибір для друкованого OCR, тому це питання актуальне вже для пілоту, не лише для гіпотетичного майбутнього.
- **Surya — VLM, генеративна модель, підтверджений ризик галюцинації** на власному пілоті (нестабільний вивід між прогонами на важкому зображенні) — посилена вимога до випадкової ручної перевірки (розділ 3).
- Авторизація фізичним токеном — не підтверджено публічно ні в той, ні в інший бік.
